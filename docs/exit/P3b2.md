## The residual hole of the cross-process race

Written as the plan asks, in the words of D-W3 (copied from PLAN, an exact substring, so the wording is the plan's; [R] marks a recollection in the plan, and invariant V is the plan's rule that the object under a key is its oldest data version, which `get` returns):

> **The race that remains:** two processes (not two threads of one store) putting different bytes under one key at once can both find their own version oldest, because the rank of a version is the server's and a slow upload may rank before a fast one that finished first [R: P13]; both are told `CREATED`. `get` returns the older-ranked version (invariant V), and if the server ranks by request start the answer of `get` can change once while the slower upload is in flight. The ledger keeps the hash of whichever writer reaches `recordObjects` first and fails the other seal closed, so when the writer whose bytes `get` does not return is first, its seal succeeds and gates an effect on bytes the port cannot return (they stay as a non-oldest locked version that the port does not return; reading it needs the raw S3 API with its version id [R]); `verify` reports the key afterwards (`HASH_MISMATCH`, `manifest-hash`). This is a stated residual hole of I10 for that attempt, not closed here: conditional writes (spec 5.2, 11.5 B.1; deferred) would close it, and no other closure was examined; `docs/exit/P3b2.md` says so in these words.

FA2 (`55ec3c4`) added a deterministic demonstration on the fake, with a hook (`FakeS3Server.rankNextPutBelowExisting`): `WormStoreVersionsTest#twoStoresThatAreBothToldCreatedLeaveTheLaterFinishedUploadAsTheObject` records the ledger row by hand and does not drive the seal (test Javadoc, lines 171 to 182). Both tests are in `WormStoreVersionsTest` (local run 18; under these names first in CP-3, which is green; that the class executed there is not observed). `twoStoresRacingWithDifferentBytesLeaveExactlyOneCreatedAndReadAsOne` counts two store objects on two threads; the fake yields exactly one CREATED per round (the final review's records lens: its admission-order ranking cannot produce two), so the count does not exhibit the race. On the service: probe result P13 (8 concurrent PUTs of different bytes to one key: `ok=8 ids=8 versions=8 newestIsLastDone=false oldestIsFirstDone=true`; one run) and probe result P17 (a second PUT with `If-None-Match` creates a second version: `versions=2`). `WormVersionsIT` (run=10, first at CP-3) uses one store object; the race with two store objects was not exhibited on the service. Extra versions after a lost race stay locked (a DELETE of a locked version by id was refused, probe result P7; NOTES section 3 item 9; plan P4). Owner of the hole: the owner, with SP-O and the AWS conditional-PUT point (NOTES section 4).
