## 1. The P-WORM store as built

### 1.1 Module and dependencies

- `regpack-evidence-s3` (package `dev.regpack.evidence.s3`; the client in `dev.regpack.evidence.s3.client`) has two compile dependencies, `regpack-model` and `regpack-ports`, and no third-party dependency (AP-5; `S3ModuleBoundaryTest`). `regpack-testkit`, `regpack-inmemory`, `regpack-tools` and `regpack-evidence` are test scope. `regpack-app` and `regpack-evidence` do not name the module (`S3ModuleBoundaryTest`), so the distribution does not reach the store; `regpack-postgres` has it as a test-scope dependency (the `PgWorm*IT` classes).
- The client is hand-written: `SigV4` (five vectors pinned in `SigV4Test`), `S3Client` (path-style requests; 2xx returned, anything else an `S3Exception`), `S3Transport` and `JdkTransport` (a fresh JDK `HttpClient` per request, HTTP/1.1, redirects not followed, one deadline for the whole exchange, a status outside 100 to 599 refused as a failed exchange, no retry of its own; the JDK `HttpClient` may retry an idempotent request once when the connection is closed before any byte of the answer, a recollection of the JDK behaviour that no test pins, as the Javadoc of `JdkTransport` says since FA1), `S3Xml` (a DOCTYPE is refused, `S3XmlTest#aDoctypeIsRefused`). `NoBypassTest` holds that the main sources neither name the governance-bypass header nor issue a DELETE request.
- `EvidenceStoreContract` has 31 methods (the 28 of P3b1 and the three added in T5) and `JournalContract` 11; `WormEvidenceStoreContractIT` ran 42 tests (31 + 11) at CP-2.

### 1.2 The mappings (D-W2 to D-W9)

| Concept | How P-WORM stores or reads it |
|---|---|
| Key | the S3 object `/{bucket}/{key}` (path-style); each byte of the key outside `A-Za-z0-9-._~` and `/` is written `%XX` once (`SigV4.encodePath`, `S3ClientTest#theCanonicalPathEncodesPlusEqualsAndComma`). Probe result P9: keys with `+ = , $` and a 512-character key were stored, read and listed back unchanged. |
| Bytes and content type | the object body; content type `application/octet-stream` (`WormEvidenceStoreTest#aNewObjectCarriesTheLockHeadersAndTheMetadataOfTheModel`). |
| Metadata (user metadata, lower-case names, prefix `x-amz-meta-`) | `regpack-sha256` (hex of the bytes), `regpack-written-at` (ISO instant of the data clock), `regpack-retain-until` (ISO instant, the exact value of the put), `regpack-class` and `regpack-media-type` (UTF-8, base64url without padding). Probe result P3: 1,676 bytes of user metadata in five names (the worst case of A10) were accepted and came back on HEAD and GET. The 2 KB limit that A10 computes against is recollection. |
| Which version is the object | invariant V: the oldest data version of the exact key. The version list of the key (`?versions&prefix=<key>`, entries of other keys ignored) is read to its end and the last data entry in list order is taken; Last-Modified is not consulted. Probe result P7: the list is newest first. |
| Lock | `x-amz-object-lock-mode` from the configuration (`GOVERNANCE`) and `x-amz-object-lock-retain-until-date`: the retain-until rounded up to whole seconds, at most `maxLockDate` (default `9999-12-31T23:59:59Z`). Probe result P2: the headers were accepted and HEAD returned the date text as sent. Probe result P12: whole seconds, six fractional digits and year 9999 were accepted and a past date was refused (400 `InvalidArgument`); this service kept the sub-second digits it was given, so the rounding up is harmless on it and is kept for a store that keeps whole seconds (recollection). |
| Retention extension | the lock first (`PutObjectRetention`, to a later date than the version has, and a shortening is not written: `WormRetentionTest#theLockIsNeverShortenedByAnExtend`), then the tag `regpack-retain-until` with the exact value, because metadata cannot change and tags can. Probe result P4: tags were written on a locked version and came back verbatim with a tagging count. Probe result P5: extending worked with and without Content-MD5; shortening a governance lock was refused (403 `AccessDenied`) without the bypass header and accepted with it. The main sources do not name the header (`NoBypassTest#noMainSourceNamesTheBypassHeader`). |
| Retention as reported | the exact value (tag, else metadata) when its rounded form equals the lock date; the lock date when the lock is longer (an extension that lost its tag); `EvidenceCorruptionException` when the lock is shorter than the exact value rounded up, absent, or the tag is no instant or lies below the metadata. |
| Legal hold | `PutObjectLegalHold` on the oldest data version, under the stripe lock; the header on GET is read as off when absent. Probe result P6: the hold was set and cleared, the header was absent before any hold and HEAD and GET carried it afterwards. A key that has not been put is `IllegalArgumentException("no such evidence key: ...")` after the outage check (M28, M33). |
| Delete marker | a marker as the newest entry over a data version makes `get`, `put` and the retention methods throw `EvidenceCorruptionException`; `list` still lists the key. Probe result P7: a DELETE without a version id added a marker (204) even under lock, GET and HEAD then answered 404 with the delete-marker header, and a DELETE of a locked version by id was refused (403). |
| Durability and grade | `durability()` reads the versioning status and the object-lock configuration when it is called (the code has no cache), throws `EvidenceUnavailableException` unless both are on, and returns the `Durability` that `WormConfig` declares. `grade()` makes the versioning request and returns `("P-WORM", "governance (unverified)")` for `UNVERIFIED_NON_AWS`. Probe result P1: a bucket created with the lock header showed versioning and object lock on. Probe result P15: the API showed no replication and no storage class, so the declaration is the operator's. The refusal paths are shown by fake-bound tests only (section 3, item 25). |
| Failures | a transport failure, a timeout, an interrupt (flag restored), any status the call does not expect (3xx included, not followed), a status outside 100 to 599 (status 0, code `ProtocolException`, since FA1), an unparsable answer, a missing version id, a listing that does not end or does not advance: `EvidenceUnavailableException` with operation, status and Code. The one absence is a version list of the exact key, read to its end, that holds no data version. Probe result P14: an error body is `<Error><Code>...</Code><Message>...`; the message is not copied. |
| Clocks | `open(config, dataClock, signingClock[, transport])`: the data clock gives `regpack-written-at` and the retain-until check; the signing clock gives `X-Amz-Date` and has to be real time (recollection: a service refuses a request that is far off its own clock). `regpack-written-at` is therefore the writer's clock and not the store's write time (section 5, P3c). |

`WormConfig` refuses before any request: an endpoint that is not `scheme://host[:port]` or has a port outside 1 to 65535 (since FA1); plain `http` for a host other than a literal 127.0.0.0/8 address, `[::1]` or `localhost` (read from the URI, no name lookup); `AWS_S3` with a host outside `amazonaws.com` and `amazonaws.com.cn`; `COMPLIANCE` with `UNVERIFIED_NON_AWS`; a declaration that is not synchronous or has no failure domain; more than one declared domain for `UNVERIFIED_NON_AWS`; a bucket name that breaks the S3 rules (`WormConfigTest`, 19 methods at `6b21151` and 20 since FA1).

### 1.3 The put algorithm and the race that remains (D-W3)

Inside the stripe lock of the key (64 locks held by the store object; a second store object on the same bucket models a second process):

1. Validate with no request: the retain-until has at most microsecond precision and a year from 0000 to 9999, the media type has at most 255 characters, the class name at most 100, an unpaired surrogate is `IllegalArgumentException`. List the versions of the key.
2. A delete marker as the newest entry over a data version: `EvidenceCorruptionException`.
3. An oldest data version exists: read it with GET, hash its bytes against the recorded `regpack-sha256` (a mismatch or missing metadata is `EvidenceCorruptionException`, no PUT), and then compare the recorded hash with the request's: equal is `ALREADY_PRESENT_IDENTICAL` with no PUT, different is `EvidenceIntegrityException` (`WormEvidenceStoreTest#aPutOfAnExistingKeyWithTheSameBytesSendsNoPut`, `#aPutOfAnExistingKeyWithOtherBytesIsAnIntegrityAlarmAndSendsNoPut`, `#aPutOfAnExistingKeyWhoseStoredBytesAreDamagedIsACorruptionAlarmAndSendsNoPut`).
4. Absent: refuse a retain-until not after the data clock, then PUT with `x-amz-content-sha256`, `Content-MD5`, the lock headers and the metadata; the answer must carry a version id. Then list the versions again: an own version missing from the second listing is `EvidenceUnavailableException` and not `CREATED` (`WormEvidenceStoreTest#anOwnVersionMissingFromTheSecondListingIsUnavailable`); the own version oldest is `CREATED`; another, older version decides as in step 3 and the own version stays as an extra version.

Probe result P10: a wrong `x-amz-content-sha256` was refused (400 `XAmzContentSHA256Mismatch`), a wrong `Content-MD5` was refused (400 `BadDigest`) and the run recorded `stored=0`, so the plan's fallback (read the own version back and hash it) was not built; section 3, item 7 states what rests on that. Probe result P17: `If-None-Match: *` on a PUT was accepted and ignored, a second PUT to the same key made a second version, so the algorithm does not rely on conditional writes. Probe result P13: eight concurrent PUTs of different bytes to one key answered 200 with eight version ids and eight versions; the newest version was not the last to finish and the oldest was the first to finish in that one run. The rank of a version is the server's.

The race that remains, two processes putting different bytes under one key at once, is stated in the words of the plan in section 3, statement (i). At `6b21151` `WormStoreVersionsTest#twoStoresRacingWithDifferentBytesAreCountedAndReadAsOne` was named as the test that states and counts the race, but the fake ranks versions by the order in which its single lock admits the PUTs, so that test could not produce two `CREATED` (final review, TESTS-1). Since FA2 the method is `WormStoreVersionsTest#twoStoresRacingWithDifferentBytesLeaveExactlyOneCreatedAndReadAsOne` (20 rounds, two store objects, two threads; exactly one writer is told `CREATED` in every round and both stores read the same bytes afterwards), which pins what the fake can show, and `WormStoreVersionsTest#twoStoresThatAreBothToldCreatedLeaveTheLaterFinishedUploadAsTheObject` shows the hole without a thread: the PUT of store B is held until store A has done its whole put, the fake's hook `rankNextPutBelowExisting` ranks B's upload below A's version (the rank is the server's, probe result P13, so the hook models it and the fake does not observe it), both writers are told `CREATED`, both stores read B's bytes, A's bytes stay as a second locked version, and `verify` over a ledger row with A's hash (made by hand in the test) reports `HASH_MISMATCH` with the detail `manifest-hash`. That test runs on the fake only and does not drive a seal over a real race. The methods of invariant V that need only the store and the raw client (`aNewerVersionAddedBehindTheBackNeverChangesWhatGetReturns`, `aDeleteMarkerOverAnObjectIsACorruptionAlarmForGetAndPutAndTheKeyStaysListed` and eight more, 10 in all) moved in FA2 to `AbstractWormVersionsTest`; `WormStoreVersionsTest` runs them on the fake and the new `WormVersionsIT` on the service, where they have not yet run. Threads of one store object share the stripe locks, and the shared contract method `concurrentPutsOfTheSameKeyWithDifferentBytesHaveExactlyOneWinner` shows one winner for them on the fake and, at CP-2, on the service. `aForeignOlderVersionAppearingDuringThePutWithOtherBytesIsAnIntegrityAlarmAndGetReturnsTheForeignBytes` and `aForeignOlderVersionAppearingDuringThePutWithTheSameBytesIsAlreadyPresentIdentical` cover the foreign-older-version case with the fake's `addOlderVersionOnNextPut`.

### 1.4 Get, list, paging

- `get`: the version list, GET of the oldest data version, bytes hashed against `regpack-sha256` (`EvidenceCorruptionException` on a difference, on missing or unreadable metadata, on a listed version that answers 404, and when the newest entry is a delete marker); one more request for the tags when GET carries a tagging count. `aNewerVersionAddedBehindTheBackNeverChangesWhatGetReturns` and `theOldestVersionIsFoundWhenTheVersionListSpansPages` pin invariant V.
- `list`: ListObjectVersions with the prefix and, for `after`, a key marker without a version-id marker; it returns the keys that have a data version in key order, skips keys that hold delete markers and no data version, and keys that are not valid `EvidenceKey`s, and follows the returned markers until `limit` distinct keys are collected or the listing ends. Probe result P8: with 1,100 keys and one marker the pages held 1,000 and 101 entries, keys came in ASCII order, a key marker without a version-id marker started strictly after that key, pages of 7 were distinct, a key hidden by a marker was listed, and the run saw no short page. The adapter does not rely on that. `listFollowsTheMarkersUntilThePageIsFull` (fake with pages of 2) is the test that pins the adapter's own behaviour: `list` with a limit of 10 answers exactly those 10 keys and takes exactly 5 version-listing requests. `WormSealScenariosTest#aMarkerBehindTheAdaptersPagingIsFound` shows that the caller finds the highest epoch marker, and the seal is cleared, when the service pages at 2 entries; `EpochMarker.current` reads to an empty page, so that test, as it was at `6b21151`, could not fail for an adapter that answered short non-empty pages (final review, RECORDS-3), and the version-listing count in it only shows that the fault switch took effect. Since FA2 it also asserts that `list("control/epoch/", empty, 10)` answers 10 keys under the fault, which is the property of the first test again, over the markers; the plan row WF5 and the earlier Javadoc called both tests end-to-end checks of the adapter's paging (section 7). A page that repeats its markers, a truncated page without both next markers and more than 10,000 pages are `EvidenceUnavailableException`; the fake's endless truncation shows the first case (`aListingThatNeverEndsIsUnavailable`).
- The paging hand-off of p3b-notes section 3 item 32: the `EvidenceStore.list` Javadoc promises full pages, the contract method `listReturnsFullPagesWhileKeysRemain` has the mutant `Flaw.SHORT_PAGES`, and `EpochMarker.current` and `JournalWriter.nextOrdinal` read to an empty page and fail instead of spinning on a listing that does not advance (`EpochMarkerTest#aStoreThatAnswersInShortPagesIsReadToTheEnd`, `JournalWriterTest#nextOrdinalReadsUntilAnEmptyPage`, and the two `aListingThatDoesNotAdvanceFailsInsteadOfSpinning` methods).

### 1.7 The fake and the behaviour contract

`FakeS3Server` (test code, JDK `HttpServer` on the loopback address) recomputes the SigV4 signature of each request from the raw request and answers 403 `SignatureDoesNotMatch` otherwise (`FakeS3ServerTest#aRequestSignedWithAnotherSecretIsRefusedWithSignatureDoesNotMatch`); it implements the behaviours of the probe results with the switches `SHORT_VERSION_PAGES`, `ENDLESS_TRUNCATION`, `LOSE_RESPONSE_AFTER_STORE`, `SERVER_ERROR`, `DROP_CONNECTION`, `CORRUPT_BYTES`, `NO_VERSION_ID` and `FAIL_TAGGING`. `S3BehaviourContract` (13 methods) states the behaviours the adapter relies on once and is bound to the fake (`S3BehaviourFakeTest`) and to the service (`WormServiceBehaviourIT`, 13 tests at CP-2): a fake that drifts from the service fails there. `S3BehaviourContract#theRetainUntilResolutionIsWholeSeconds` asserts the whole-second round trip of the adapter's own writes, not that the service truncates (probe result P12).

## 2. The gate commands and the label `REALWORM`

Local, from the repository root (Git Bash; `export JAVA_HOME=/c/dev/jdk/jdk-25.0.4.1+1; export PATH="$JAVA_HOME/bin:$PATH"` first):

## 3. Limits

Each limit says who owns it.

1. **Path-style addressing** (A1). The client sends `/{bucket}/{key}`; the first signed GET with the port in `Host` was accepted (probe result P16). A store that needs virtual-hosted-style addressing is not served (recollection about such stores). Owner: SP-O per store, and the wiring plan.
2. **Whole object in memory; response bodies read whole and not size-capped by the client.** `put` takes a `byte[]`, which is held in memory and hashed twice (SHA-256 and MD5), `JdkTransport` reads a response with `BodyHandlers.ofByteArray()`, and `get` returns the bytes. The size constants in the main code are the page size (1,000), the page cap (10,000) and the lengths of the media type and the class name; no limit on an object or on a response is set in `JdkTransport` or `WormEvidenceStore` (read at `6b21151`; no test pins it). The bound on an object is the journal bound where a journal object is stored (p3b-notes section 1.4: 1 MiB for most types and 64 MiB for two), and this module sets no bound on a sealed file. The peak heap per put or get is unmeasured. The plan's list of unrun cases names an object over 3 MiB and the 64 MiB journal bound through a real PUT. Owner: plan P8 and the wiring plan (a size cap in the transport is a later change that no task owns).
3. **A TLS handshake per request.** `JdkTransport` builds a fresh `HttpClient` for each request and closes it, so no connection is reused; a new key costs 3 requests (section 1.5). The CI service ran over plain `http` on loopback; a non-loopback TLS endpoint was not run. Besides the handshake cost, a new connection for every request can exhaust the ephemeral ports under load, and then every call fails with `EvidenceUnavailableException` until the sockets drain, so the seal path fails closed. The final reviewer measured this on Windows 11 against the loopback fake: 8,429 sequential `grade()` calls in 36.6 seconds ended with `status=0 code=ConnectException` and 15,270 sockets in TIME_WAIT (a measurement by the reviewer, not repeated in FB; the figures for Linux, about 28,000 ports and 60 seconds of TIME_WAIT, are recollection). One seal and its first-byte gate is 14 to 15 requests by the reviewer's count. Owner: the wiring plan (a shared connection pool is a condition of load, not only a performance hand-off).
4. **Failure domains are declared and not shown.** The S3 API shows no replication (probe result P15). The CI service declares one domain, so the production gate (`Requirement.production()` asks for two) stays closed for it; a test that declares three does so with `Verification.SP_O_VERIFIED` and says so (`AbstractWormSealTest#theProductionGateIsClosedForOneDeclaredDomainAndOpensForThreeDeclaredByTheTest`). A copy counts when it exists at the acknowledgement of the PUT; asynchronous replication counts zero (`WormConfigTest#aStoreMustDeclareSynchronousAcknowledgementAndOneFailureDomain`). Owner: the operator's declaration, attested in the G8 record (spec 5.4).
5. **Governance mode, graded unverified, one mode per store.** The grade is `P-WORM/governance (unverified)`. Compliance mode is accepted by `WormConfig` for `AWS_S3` or `SP_O_VERIFIED` and was not run through `WormEvidenceStore` on any store; the one observation of a COMPLIANCE lock is probe result P5, on the raw client in a throwaway bucket (a COMPLIANCE lock was not shortened, even with the bypass header). A per-class mode is not built (statement (ii) below). Owner: the wiring plan, SP-O and G8.
6. **A retain-until above `maxLockDate` is recorded and not store-enforced.** The lock date is clamped to `maxLockDate` and the exact value stays in the metadata and the tag (`WormRetentionTest#theLastSecondOfYear9999IsClampedAndStillRoundTrips`, `WormEvidenceStoreTest#aRetainUntilBeyondTheMaximumLockDateIsLockedUntilTheMaximumAndRecordedInFull`). Probe result P12 accepted year 9999, so at the default the clamp reaches a retain-until after `9999-12-31T23:59:59Z`; a lower configured `maxLockDate` widens it. Owner: the wiring plan (the value of `maxLockDate` for a store).
7. **In-transit integrity rests on the service verifying the payload hash.** The put sends `x-amz-content-sha256` and `Content-MD5`; the service refused a wrong value of either and the run recorded `stored=0` (probe result P10), and step 4 of the algorithm does not read the own version back. A service that did not verify could store altered bytes while the put answers `CREATED`; a later `get` then throws `EvidenceCorruptionException` and `verify` reports the key as `HASH_MISMATCH` `store-integrity`, because the recorded hash is that of the request (`getRefusesBytesThatDoNotMatchTheRecordedSha256`, `aDamagedObjectIsStoreIntegrityAndNotMissing`). Owner: SP-O per store.
8. **Adapter limits that are not port rules** (A10, Port change 4). A media type over 255 characters, a class name over 100, an unpaired surrogate in either, and a retain-until not after the data clock for a new key are refused before any request (`WormEvidenceStoreTest#aMediaTypeOver255CharactersAndAClassNameOver100AreRefusedBeforeAnyRequest`, `#aMediaTypeOrClassNameWithAnUnpairedSurrogateIsRefusedBeforeAnyRequest`, `#aRetainUntilNotAfterTheClockIsRefusedBeforeThePutOfANewKeyButNotForAnExistingOne`); the other adapters accept them, and the contract method `aMediaTypeOf255CharactersAndARetentionClassNameOf100CharactersRoundTrip` pins the boundary in the three bindings (`InMemoryEvidenceStoreContractTest`, `SealedEvidenceStoreContractTest`, `WormEvidenceStoreContractTest`). The reason is the user-metadata limit (recollection: about 2 KB) and a lock date that has to lie in the server's future (probe result P12: a past date was refused). Owner: the owner may ask for port rules.
9. **Extra versions after a lost race stay locked** (D-W3). A version that is not the oldest was put with its own lock headers and keeps that lock; a DELETE of a locked version by id was refused (probe result P7), and the port does not return such a version. Retention expiry (plan P4) has to deal with it. Owner: plan P4.
10. **Foreign keys and delete markers** (D-W4). A key that is not a valid `EvidenceKey` is skipped by `list`, if its characters can be carried by XML 1.0 (item 18) (`aForeignKeyWithInvalidCharactersIsSkippedByListAndStillFillsThePage`); a valid-looking foreign key without regpack metadata is listed and its `get` is `EvidenceCorruptionException` (`getRefusesAnObjectWithoutRegpackMetadata`); a delete marker added by another principal hides a key: it stays listed, `get` and `put` raise `EvidenceCorruptionException` and `verify` reports `HASH_MISMATCH` `store-integrity` (`AbstractWormVersionsTest#aDeleteMarkerOverAnObjectIsACorruptionAlarmForGetAndPutAndTheKeyStaysListed`, run on the fake by `WormStoreVersionsTest` and since FA2 by `WormVersionsIT` on the service, `AbstractWormVerifyTest#aHiddenObjectIsReportedAsStoreIntegrityHashMismatchAndTheRunContinues`). The main sources issue no DELETE request (`NoBypassTest`).
11. **Tags are not protected by the lock.** Probe result P4 shows tags written on a locked version. The lock date is therefore the floor of what `get` reports: a tag raised above the lock makes the rounded exact value later than the lock and `get` throws `EvidenceCorruptionException` (read from `retained()`; the test `WormRetentionTest#aLockShorterThanTheRecordedRetentionIsACorruptionAlarm` takes the same branch for a shortened lock). The adapter needs the permission to tag, so the identity cannot be denied it. Owner: deployment.
12. **No retry of its own, and one deadline per request.** The JDK `HttpClient` under `JdkTransport` may itself retry an idempotent request once when the connection is closed before any byte of the answer (recollection of the JDK behaviour; no test pins either reading; the Javadoc says so since FA1). A lost response is `EvidenceUnavailableException` and the retry finds the object (`aPutWhoseResponseIsLostIsUnavailableAndTheRetryFindsTheObject`, on the fake); the deadline of each request is `WormConfig.requestTimeout` (default 30 seconds) and the adapter bounds no call as a whole (a put is 3 requests). Owner: plan P8 (the watchdog of p3b-notes section 3 item 18 is the ledger side of the same question).
13. **Test data and clocks** (D-W13). The bindings run the data clock at `2040-03-01T00:00:00Z` so that retain-until dates in 2045 lie in the server's future; the signing clock is real time on the service and manual on the fake. One bucket per test (`rp-` plus 12 hex digits), not emptied afterwards; the tests that send the bypass header shorten a lock and do not delete a version; the service container is discarded with the job (recollection). Clock skew between the runner and a service was not run. The dates are fixed in the tests and hold while the real date is before them, because the fake checks "future" and "active lock" against `Instant.now()` and a service against its own clock: `AbstractWormVerifyTest` shortens a lock to `2041-01-01` in two methods, and `S3BehaviourContract` and `S3ServiceProbeIT` use `2044-03-01`, `2045-03-01` and `2046-03-01`. From `2041-01-01` a retain-until date of 2041 is a past date, which the fake refuses with 400 `InvalidArgument` on a put and on `PutObjectRetention` (`FakeS3Server.requireFuture`) and the service refused on a put (probe result P12; for `PutObjectRetention` on the service this is an inference), so the tests that use it would fail with no hint of the cause; from `2044-03-01` the `SHORTER` date of the contract is past too. Owner: the maintainer of the next slice that touches these tests (derive the dates from the real clock or move them forward).
14. **One probe run, one image digest.** The probe results above are one observation of CloudServer 9.5.0 at that digest on one CI runner. These notes make no statement about AWS S3, MinIO, SeaweedFS or another version, and SP-O has not been run.
15. **What runs where.** The `*Test` classes of the module, among them the contract bindings on the fake, `SigV4Test` and the teeth tests, run in `verify` locally and in the build jobs on Linux and Windows; at CP-2 those jobs were green, and that the tests executed is not observed there (the build jobs print no tally annotation), with two exceptions: the two fake-bound `INMEMORY` lines of `docs/traceability.md` (`WormSealScenariosTest#noByteReachesTheDestinationBeforeBothObjectsAndTheSendingCommitAreDurable` for I1 and `WormVerifyTest#theIdentityOfEverySentDeliveryIsReconstructableFromTheEvidenceTierAlone` for I10) are looked up in the reports by the traceability step of `check-gates.sh` in the build jobs (mode `skip` evaluates them, and a line with no passing report is a problem), so the green gate step is an observation that those two ran and passed; the local `./mvnw -B -ntp verify` of 2026-10-24 at `a7bc619` ended BUILD SUCCESS with 290 tests in `regpack-evidence-s3` (failed 0, errors 0, skipped 0) and 3,758 in the reactor (299 skipped, 288 of them integration tests of `regpack-postgres` that skip without a server). `Worm*IT` (88 tests at CP-2; `WormVersionsIT`, 10 tests, was added by FA2 and has not run on a service) and `PgWorm*IT` (28 tests) run in `evidence-worm` on `ubuntu-24.04`. The probe ran at CP-1 (job version 1); version 2 does not select it. Windows against the service and SP-W are not run.
16. **The PostgreSQL half.** On the PostgreSQL ledger with P-WORM the seeded faults are ORPHAN, MISSING, HASH_MISMATCH (`manifest-hash`) and INTENT_MISMATCH (`PgWormVerifyIT#aSeededFaultOnThePostgreSqlLedgerIsReportedWithItsOwnClass`); SEQUENCE_GAP needs the class (b) counter of P3d. `WormVerifyIT` (7 tests) runs `verify` on P-WORM with the in-memory ledger; it seeds 8 fault entries, a fresh tier for each (HASH_MISMATCH four times, one of them the delete marker over a locked object, MISSING, ORPHAN, SEQUENCE_GAP and INTENT_MISMATCH). Seven of them are P-WORM variants of faults seeded on P-SEALED in `EvidenceVerifierTest#eachSeededFaultIsReportedWithItsOwnClassAndNothingElse`, not identical seedings (for example 'object 3 of 5 deleted' gives MISSING and SEQUENCE_GAP on P-SEALED and only SEQUENCE_GAP here, because the object was never written: T9 report F4), and the other 13 of the 20 faults of that test are, by the Javadoc of the P-WORM test, verifier logic that does not depend on the store. The PostgreSQL test seeds its four faults cumulatively and asserts the exact list of findings after each seed (T11 R4), which is not the shape 'each fault alone' of the plan.
17. **The lock fields and tags are read from response headers, which AWS S3 may withhold (recollection).** `get` takes the legal-hold flag, the lock mode and date and the tagging count from the headers of the GET of a version (`readData`, `retained`, `taggingCount`). An absent legal-hold header is read as off (D-W6), an absent tagging count as no tags, and an absent mode or date header is an `EvidenceCorruptionException` ("an evidence object has no retention lock"). Recollection about AWS S3 (about 85 percent, not checked by any probe): these headers are returned only to an identity that holds the matching read permission (retention, legal hold, tag read). If so, an identity without the legal-hold read permission reads a held object as `legalHold=false` with no exception; one without the retention read permission gets an `EvidenceCorruptionException` for every object, which is an alarm of the tamper class raised for a permission fault; one without the tag read permission gets, for an extended version, the lock date in whole seconds in place of the exact retain-until. D-W6 and probe result P6 were observed on CloudServer with its one test identity. The adapter has no delete method, so a held version cannot be deleted through it whatever `get` reports, and the harm is a wrong flag for a consumer that trusts `StoredObject.legalHold`, such as the retention expiry of plan P4. Not changed in code; a remedy is a fallback read of the missing field (`GetObjectLegalHold`, `GetObjectTagging`) or a check of the permissions in the first call of a deployment. Owner: deployment (the identity and its permissions; section 5, Deployment) and the wiring plan; plan P4 before it trusts `legalHold`.
18. **A key that XML 1.0 cannot carry makes a version listing unusable.** `S3Client.listVersions` sends no `encoding-type=url`. Recollection about AWS S3 (about 85 percent): without it, S3 answers a key with a character that XML 1.0 cannot carry (a control character) as it is. `S3Xml` then cannot parse the page (the final reviewer reproduced this with a scripted listing), and the call is an `EvidenceUnavailableException` (`status=200 code=unparsable`) for every `list` and every version listing over a range that holds such a key; under `control/epoch/` every `EpochMarker.current()` fails and the first-byte gate fails closed. This narrows the rule "a listed key that is not a valid `EvidenceKey` is skipped, never thrown" (item 10, D-W4) to keys whose characters XML can carry; `WormEvidenceStoreTest#aForeignKeyWithInvalidCharactersIsSkippedByListAndStillFillsThePage` uses a space, an accented letter and a 101-character name, which XML carries. The cure of a stuck listing is to remove the object with credentials that may delete it. Owner: the wiring plan (to request `encoding-type=url` and decode, or to accept the fail-closed behaviour).
19. **`versionsOf` reads every page of the longer keys that start with the key.** The version list of a key is a prefix listing whose visitor never stops, so `get`, `put`, `extendRetention` and `setLegalHold` on a key that is a prefix of many keys cost one request per page of 1,000 entries beneath it and end in `EvidenceUnavailableException` (`TooManyPages`) after 10,000 pages. The contract allows a key to be the prefix of another (`aKeyMayBeAPrefixOfAnotherKey`); the final reviewer found the key layouts written so far to be of fixed shape, which makes this rare (not re-checked in FB). Owner: the wiring plan, or the maintainer of a later key layout.
20. **The callers depend on a key marker that starts strictly after the key.** Since T5 `EpochMarker.current` and `JournalWriter.nextOrdinal` issue a further `list` with `after` set whenever a page is not empty, and the adapter passes `after` as a key marker without a version-id marker and does not drop entries at or below it. A store whose key marker alone is inclusive would repeat the last key; the callers then throw (`IllegalStateException` or `EvidenceIntegrityException`: "evidence listing does not advance"), so the first-byte gate and the ordinals fail closed. Probe result P8 (`strictAfter=true`) observed the strict behaviour on CloudServer 9.5.0 only; AWS S3 and other stores are unobserved. Owner: SP-O per store and the wiring plan.
21. **A green `evidence-worm` job can hide a test that did not run.** `REGPACK_S3_REQUIRED` and `REGPACK_PG_REQUIRED` only stop the harness from skipping for want of a service. A test turned into a skipped one (an assumption, `@Disabled`), a class that lost its tag, or a removed test turns the job red only if a `REALWORM` line of `docs/traceability.md` cites it. `Annotations` prints a `skipped` warning and the `tally-classes` and `tally-total` notices, which a person reads at a checkpoint (CP-2 read skipped 0). `WormServiceBehaviourIT` (13 tests, the guard against drift of the fake) is cited by no `REALWORM` line, and neither is `WormVersionsIT`; `ServiceTestSelectionTest` checks the tag by `contains("@Tag(\"worm\")")` on the whole file, so a comment with that text passes it. The remedy is a CI change (fail the worm job on `skipped > 0`) that needs the owner's approval of the text (AP-3), and a stricter tag check in that test. Neither is done. Owner: the owner at the next CI change; the maintainer of the next slice for the test.
22. **A stray delete marker over an epoch-marker key.** If another principal puts a delete marker over a `control/epoch/` key, `EpochMarker.current()` reads the key with `get`, which throws `EvidenceCorruptionException` (`AbstractWormVersionsTest#aMarkerOverAnEpochMarkerKeyIsStillListedAndItsGetIsAnAlarm`), and `DurableSeal` answers `EPOCH_MARKER_UNREADABLE` to each send attempt while that read fails (it catches `RuntimeException`). The adapter has no delete, so the marker can be removed only with credentials that may delete a version: recollection about AWS S3 and about CloudServer; probe result P7 observed only the refusal of a DELETE of a locked version by id. Owner: plan P4 (the removal of delete markers and the operator procedure), deployment.
23. **`get` takes no key lock.** `get` reads the version list, the version and, when the count header says so, the tags in separate requests without the stripe lock of the key. A concurrent `extendRetention` of an already tagged version, between the GET and the tag read, can leave the pair inconsistent, and `get` then throws `EvidenceCorruptionException` for a healthy object (T8b report R2; a reading of the code, not reproduced in FB). The stripe lock covers the threads of one store object only, not a second process. Owner: the wiring plan.
24. **Duplicated test support and the way to re-run the probe.** `PgWormSupport` in `regpack-postgres` repeats part of `S3TestService` because a module cannot see the test classes of another (T11 report R2 gives about 100 lines; not counted in FB), so the two can drift; `PgWormSupportTest` covers the pure decision of the copy. The probe is not run by job version 2. To run it again, for example after a change of the image digest, use the form of the commands of section 2 with the probe tag and the same four `REGPACK_S3_*` variables (a command of that form, not run in FB: `bash scripts/it.sh regpack-evidence-s3 'S3ServiceProbeIT' -Dgroups=probe -DexcludedGroups=none`), against a service on a loopback address; the text of job version 1, which ran it, is in the history at `ab7dab2` (SHA-256 in `p3b2-decisions.md`). A digest bump needs the owner's approval of the job text again (AP-3, AP-6). Owner: SP-O and the maintainer of the job.
25. **The refusal paths of `durability()` are shown on the fake only.** The refusals of a bucket without object lock (`ObjectLockNotEnabled`) and without versioning (`VersioningNotEnabled`) are shown by the fake-bound methods `WormEvidenceStoreTest#durabilityIsRefusedWhenObjectLockIsOff` and `#durabilityIsRefusedWhenVersioningIsNotEnabled` (and the outage case); no test on the service creates a bucket without object lock, and the 404 `ObjectLockConfigurationNotFoundError` that `S3Client.objectLockEnabled` and the fake use for such a bucket is a recollection about AWS S3 that the fake does not mark as not probed. On the service only the positive path ran: a lock bucket (probe result P1, `S3BehaviourContract#aLockBucketIsVersionedAndLocked`) and `durability()` returning the declaration in `WormEvidenceStoreContractIT` (`gradeAndDurabilityAreDeclared`, `aStoreOfAnEvidenceProfileDeclaresItsDurabilityConsistently`). Because `objectLockEnabled` answers false only for that exact 404 code and every other failure is an `EvidenceUnavailableException`, an unexpected answer fails closed. Owner: the next checkpoint that adds a service-bound case, or SP-O per store.

Three statements, each copied from its source in the plan.

(i) The residual hole of the cross-process race (D-W3 of the plan):

> `get` returns the older-ranked version (invariant V), and if the server ranks by request start the answer of `get` can change once while the slower upload is in flight. The ledger keeps the hash of whichever writer reaches `recordObjects` first and fails the other seal closed, so when the writer whose bytes `get` does not return is first, its seal succeeds and gates an effect on bytes the port cannot return (they stay as a non-oldest locked version that the port does not return; reading it needs the raw S3 API with its version id [R]); `verify` reports the key afterwards (`HASH_MISMATCH`, `manifest-hash`). This is a stated residual hole of I10 for that attempt, not closed here: conditional writes (spec 5.2, 11.5 B.1; deferred) would close it, and no other closure was examined; `docs/exit/P3b2.md` says so in these words.

(ii) The per-class compliance mode (Departures (3) of the plan):

> Spec 16 P3 row: compliance mode is enabled per retention class in production. `WormConfig` carries one `LockMode` for the whole store; a per-class mode is not built in P3b2 and is a hand-off to the plan that wires the adapter and to G8. Nothing is wired. AP-1 approves it or asks for it.

The answer to AP-1, which named this departure, is recorded in [p3b2-decisions.md](p3b2-decisions.md).

(iii) The governance grade in production, from the Scope check of the plan:

> Nothing in the adapter or in `SendGate` refuses governance mode in production (`SendGate` reads durability only); refusing a governance grade in production is a hand-off to the wiring plan and to G8.

What this means in configuration, read from `WormConfig` and `SendGate.Requirement.production()` (`new Requirement(true, true, 2)`): a store with `WormConfig(GOVERNANCE, SP_O_VERIFIED, Durability(true, 3))` is accepted by `WormConfig` and opens the production requirement on the evidence side (`AbstractWormSealTest#theProductionGateIsClosedForOneDeclaredDomainAndOpensForThreeDeclaredByTheTest` does it with the governance mode of the test configuration and `SP_O_VERIFIED`), and the same holds for `AWS_S3` by the reading of `WormConfig`, whose only rule on the mode is that `COMPLIANCE` is refused with `UNVERIFIED_NON_AWS`. The exit record keeps this hand-off in the words of the plan.

### P3c

- Keys, the signer of manifests, the manifest function and the manifest conditions of the send gate; the signed-manifest findings of `verify` (on P-WORM the identity is reconstructed from `DeliveryIntent` objects, `AbstractWormVerifyTest#theIdentityOfEverySentDeliveryIsReconstructableFromTheEvidenceTierAlone`). Objects are stored as given: P-WORM holds plaintext until the envelope encryption of P3c, so the CI service and the fake receive no production data.
- SEAL-1: a content-addressed sealed object keeps the retention of its first put; the retention rows or the engine extend it to the maximum over the deliveries that name it, treating `EvidenceRetentionException` as satisfied. On P-WORM an earlier date than the exact retain-until throws it, an equal date writes nothing (`WormRetentionTest#extendingToTheCurrentRetainUntilChangesNothing`), and a later one costs 4 or 5 requests (section 1.5).

- The meaning of `StoredObject.writtenAt` on P-WORM. It is the writer's data clock, not the store's write time: `WormEvidenceStore.putNew` sets `regpack-written-at` from the injected data clock, `readData` reads it back, and `EvidenceStoreContract#putThenGetReturnsIdenticalBytesAndSha256` requires it to equal the injected clock. Spec 11.6 takes the time of a signature from independent evidence, the evidence store's write time of the manifest object (P-WORM) or the position in the second-location copy (P-SEALED). Before P3c uses a write time as that anchor, the adapter or the port has to carry the server-side creation time of the version (`LastModified` of the entry in the version listing, which `S3Xml.versionPage` and `VersionEntry` do not carry today), and the contract has to say which of the two meanings `writtenAt` has. This is a hand-off to P3c, not a defect of P3b2: there is no signer yet, a search of the main sources at `55ec3c4` for `writtenAt()` finds only the three stores (`WormEvidenceStore`, `SealedEvidenceStore` with `SealedFormat`, `InMemoryEvidenceStore`) and the testkit contracts, and section 1.2 states that the value is the data clock.

### Plan P4

- Retention expiry deletes versions: the adapter has no delete and no bypass, and plan P4 has to remove the data versions, the extra versions that a lost race left and the delete markers of a key (recollection about the delete permissions; a DELETE of a locked version by id was refused in probe result P7). Epoch markers (`control/epoch/`) stay exempt: `EpochMarker.current()` reads the highest marker and a deleted one reads as a lower epoch. A delete marker over a marker key is not a deletion of it: `get` of that key is an `EvidenceCorruptionException` and the first-byte gate answers `EPOCH_MARKER_UNREADABLE` until the marker is removed with credentials that may delete a version (section 3, item 22). Plan P4 also decides what the expiry trusts: `StoredObject.legalHold` is read from a response header that AWS S3 may withhold (section 3, item 17).
- `verify --deep` with `LedgerIntegrity`, the restore steps, `attempt_id` resume and the scheduled checks of p3b-notes section 5, plan P4.

### Deployment

- A bucket created with object lock and versioning on (probe result P1 shows that a bucket created with the lock header has both on). An identity for the adapter without the permissions to delete an object or a version, to bypass governance retention, to change versioning or the object-lock configuration, or to delete the bucket (the names of these permissions are recollection about AWS S3). The adapter makes these calls: PutObject, GetObject, ListObjectVersions, PutObjectRetention, PutObjectLegalHold, GetObjectTagging, PutObjectTagging, GetBucketVersioning and GetObjectLockConfiguration; that they map to permissions of those names is recollection. The identity also has to be allowed to read what the adapter reads from the response headers of a GET of a version: the lock mode and date, the legal-hold state and the tagging count. Recollection about AWS S3, not checked: those headers are returned only to an identity that holds the matching read permission, so the list needs, besides the names above, the permission to read the retention and the legal hold of an object and the version-qualified permissions to read a version, list versions and read and write the tags of a version (`s3:GetObjectVersion`, `s3:ListBucketVersions`, `s3:GetObjectRetention`, `s3:GetObjectLegalHold`, `s3:GetObjectVersionTagging`, `s3:PutObjectVersionTagging`, `s3:PutObjectRetention`, `s3:PutObjectLegalHold`, names by recollection). A missing one is a silent wrong value (legal hold read as off, tags read as none) or an `EvidenceCorruptionException` that looks like tampering (section 3, item 17); durability() does not check them. The G8 attestation is where they are to be listed (a hand-off). TLS to a non-loopback endpoint, credentials from the secrets port, and the declaration of failure domains attested in the G8 record.
