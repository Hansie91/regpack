## 1. The evidence tier as built

### 1.1 Modules and dependencies

- `regpack-evidence` (package `dev.regpack.evidence`; sub-packages `sealed` for P-SEALED, `seal` for `DurableSeal`, `SendGate` and `EpochMarker`, `verify` for `EvidenceVerifier`) has no third-party dependency (AP-5). It depends on `regpack-model` and `regpack-ports`; `regpack-testkit`, `regpack-inmemory` and `regpack-tools` are test scope. `regpack-app` does not depend on it and nothing is wired: no evidence adapter and no PostgreSQL adapter is reachable from the distribution. `ModuleBoundaryTest` parses the dependencies. `regpack-postgres` has `regpack-evidence` as a test-scope dependency (the real-store seal scenarios and the durability tests).
- The journal format, `JournalWriter`, `Sealing`, `ManifestLedger` and `LedgerDurability` live in `regpack-ports`, so that the shared suites of `regpack-testkit` can bind them (testkit cannot depend on a module whose tests depend on testkit). For the same reason the shared seal scenarios write the restore-epoch marker by hand.
- Real-store tests are `*IT` classes that skip when `REGPACK_PG_URL` is unset and fail instead of skipping when `REGPACK_PG_REQUIRED=true` (CI). The tests of the standby job are tagged `durability`; the module property `excludedGroups` is `mutant,capacity,durability`, so `verify` never runs them and the job `ledger-durability` selects them.

### 1.2 Port and model changes (additive except two)

- `EvidenceKey` tightens: each segment is at most 100 characters (the 512-character total stays). This is the first of two non-additive changes, and the only one that AP-1 listed. The key alphabet is `[A-Za-z0-9._=,+-]`; `.` and `..` are refused as segments.
- `EvidenceStore` gains Javadoc, shared contract methods and one rule that changes behaviour. `extendRetention` and `setLegalHold` of a key that was never put throw `IllegalArgumentException("no such evidence key: <path>")`, and during an outage `EvidenceUnavailableException` comes first (M28, M33). A `retainUntil` has at most microsecond precision and a year from 0000 to 9999, else `IllegalArgumentException` and nothing is stored (`put` and `extendRetention`). **That retain-until rule is the second non-additive change of the port** (final review SPEC-2): an adapter that took `Instant.MAX` or an instant with nanoseconds before now refuses it, and AP-1 listed only the `EvidenceKey` change. Nothing was released, so no caller is broken. The order "a bad instant versus an outage" is not specified at the port and differs between the adapters: the in-memory adapter checks the outage first (`failIfDown`, then the instant), P-SEALED checks the instant first (a pure check before any I/O) and no contract method combines the two. Both points go to the T22 sign-off list for an explicit owner answer (accept the second change; specify one order at the port or leave it open). `EvidenceCorruptionException` (a damaged stored copy) is a new subclass of `EvidenceIntegrityException`. `RetentionPolicy` is passed in; there is no production default (`RetentionPolicy.fixedDays` is for tests and tools).
- `regpack-ports.ledger`: `ManifestLedger` (object entries, rows, `recordObjects`, `manifestRow`, `manifestRows`), `LedgerDurability`, `ManifestConflictException`, `DeliveryLedger.AttemptIntent` with a trailing list of at most 8 object entries (`MAX_INTENT_OBJECTS`; the two-argument constructor stays), and `LedgerStore` extending both new sub-ports. `ObjectClass` codes: SEALED_FILE 1, JOURNAL_A 2, JOURNAL_B 3, LANDING_BATCH 4, ENRICHMENT_RESPONSE 5, SIGNED_MANIFEST 6, OTHER 7; `Provenance` codes: WRITTEN 1, ADOPTED_AT_RESTORE 2 (pinned by `CodesTest`; the database has no CHECK on the set). The in-memory ledger answers `LedgerDurability` with `(false, 0, "in-memory ledger")` unless a test sets it.
- Public additions and one signature change beyond the plan signatures, accepted: `JournalObject.MAX_BYTES`, `JournalObject.MAX_SMALL_BYTES` (FK), `JournalType.maxBytes()` (FK), `JournalWriter.MEDIA_TYPE`, `JournalWriter.RETENTION_CLASS`; `JournalObject.fromBytes(byte[])` of the plan is `fromBytes(JournalKey, byte[])` since FK (the key names the type whose bound applies). `PgManifest.record` (package-private) returns a boolean since FH.

### 1.3 The key space: exact renderings

| Object | Key | Notes |
|---|---|---|
| Sealed file | `sealed/{first two hex digits}/{64 hex digits}` of the SHA-256 of the bytes | content-addressed: the same bytes are one object whatever the number of attempts; for empty input `sealed/e3/e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`; retention class `sealed` |
| Restore-epoch marker | `control/epoch/e{epoch:012d}`, for example `control/epoch/e000000000003` | bytes are the canonical JSON `{"epoch":3}` and nothing else; media type `application/vnd.regpack.epoch+json`; retention class `epoch`; epoch 0 to 999,999,999,999 |
| Journal object, class (a) | `journal/{scope}/e{epoch:012d}/a/{wire name}/{shard}/{subject}/{ordinal:012d}` | see below |
| Journal object, class (b) | `journal/{scope}/e{epoch:012d}/b/{seq / 10000 :08d}/{seq:016d}` | endpoint scope only; sequence number 1 to 999,999,999,999 |

- **Scope.** The word `control` (pack and batch objects that belong to no endpoint) or the four parts `{environment},{route},{lei},{authority}` of an endpoint, each part 1 to 24 characters of `[A-Za-z0-9._-]` (assumption A9: decodable, injective, one key segment, at most 99 characters). An endpoint with a part outside that alphabet can be leased and queued but is refused by `seal` (section 3, item 14). The control scope is allowed only for `BatchAdmitted` (where it is required) and `OperatorAction`.
- **Class (a) subject and shard.** The subject has the raw alphabet `[A-Za-z0-9._:-]{1,100}`, not `.` or `..`; `=` is not allowed raw and `:` renders as `=`. A subject of digits only (an attempt id) must be 1 to 12 digits with no leading zero (so `0` and `042` are refused) and is zero-padded to 12 digits in the path. The shard of a numeric subject is `n` plus the first 8 digits of the padded form (10,000 consecutive ids per directory). The shard of any other subject is `x` plus the two lower-case hex digits of the first byte of the SHA-256 of the subject text as written (with `:`, not `=`), UTF-8: 256 shards (a `BatchAdmitted` subject is `<64 hex>:<slice>`, never numeric, and about 10,000 are admitted a day). The ordinal is 1 to 999,999,999,999 and is supplied by the caller (D-E7); `JournalWriter.nextOrdinal` reads the tier (the highest stored ordinal plus one) and reserves nothing.
- **Pinned examples.** `journal/PRODUCTION,ARM-ONE,5493001KJTIIGC8Y1R12,FCA/e000000000003/a/DeliveryIntent/n00000000/000000000042/000000000001` (attempt 42, ordinal 1, epoch 3); `journal/control/e000000000003/a/BatchAdmitted/x63/<"ab" repeated 32 times>=7/000000000001` (batch id `<64 hex "ab">:7`); other shard vectors: subject `a:7` gives `x36`, `b:1` `x34`, `p:1` `xab`, `a` `xca`, `a:a:a:a` `x4f`, 100 times `x` gives `x09`; class (b) `journal/PRODUCTION,ARM-ONE,5493001KJTIIGC8Y1R12,FCA/e000000000003/b/00000001/0000000000010001` (seq 10,001). The longest class (a) key is 258 characters; every segment has at most 100 characters.
- `JournalKey.parse` is the exact inverse of `evidenceKey()`: it re-renders what it parsed and refuses any other padding, shard or bucket (`JournalKeyTest`, 2,000 seeded random keys). Two different tuples never share an `EvidenceKey`.

### 1.4 The journal object and the payload schemas (version 1)

- **Bytes.** The canonical JSON `{"envelope": ..., "payload": ...}` in UTF-8 (sorted keys, no white space, instants with microseconds). The envelope has `endpoint` (the scope text), `restore_epoch`, `type` (the wire name), `schema_version`, `clock_instant`, `payload_sha256` (SHA-256 of the canonical payload text) and, for class (a), `subject_id` and `ordinal`, for class (b) `seq`. `clock_instant` is the ledger event time, so a re-ship of the same object is byte-identical. Golden pins (`JournalObjectBytesTest`): the class (a) fixture, a `DeliveryIntent` for attempt 42, has `payload_sha256` `78facdebbceaf2a512fa1c77235dbbc6608bc4054383f3e3a305612d357b6bb9`; the class (b) fixture, a `TransportResult` with seq 10001, has `c16a69090065d1af87884de1e62d723f12b73549ae8396b535457f4e8af534bb` (the values first recorded for the payloads `{"attempt_id":42,"note":"x"}` and `{"attempt_id":42,"observed_at":"x"}` belong to payloads that the schemas made unconstructable; no test holds them); the seven per-type object digests are pinned in `JournalSchemasTest#goldenObjectOfEachTypeHasThePinnedSha256` (`DeliveryIntent` `e8b202cf...`, `BatchAdmitted` `49f9437b...`, `TransportResult` `bd6603bf...`, `FeedbackReceived` `47aab80e...`, `RecoveryDecision` `f64cb143...`, `OperatorAction` `4508aad9...`, `VersionAssigned` `16284fee...`; the full values are in decisions.md).
- **Strict reading.** `JournalObject.fromBytes(JournalKey storedUnder, byte[] bytes)` accepts only canonical text (it re-renders and compares byte for byte), exactly the envelope keys of one class, and a `payload_sha256` that is the hash of the payload; a malformed text is an `IllegalArgumentException` that never echoes the input and has no cause. **The size bound is per type** (`JournalType.maxBytes()`): 64 MiB (`JournalObject.MAX_BYTES` 67,108,864) for `VersionAssigned` and `BatchAdmitted`, whose payload lists grow with a batch (a `VersionAssigned` of a 10,000-record batch is about 1 MB), and 1 MiB (`MAX_SMALL_BYTES` 1,048,576) for every other type. The bound is taken from the type that a class (a) key names and is checked before anything is parsed; `toBytes` refuses an object over the bound of its type. **A class (b) key does not name its type**, so a read under a class (b) key keeps the 64 MiB bound and a longer object of a small type is refused only after it is read, by the canonical comparison. **The bound is on bytes, not on parse work:** the parser builds a tree of every JSON node before any schema check, and a dense text (for example `{},` repeated) needs many times its length in heap (an `OutOfMemoryError` was reproduced at `-Xmx1g` with the single 64 MiB bound); the 1 MiB ceiling bounds that for a read under a key of one of the five small class (a) types (`EvidenceVerifier` parses only `DeliveryIntent` keys and so is protected), but the dense-input cost of a 64 MiB input under a class (b) key or a `BatchAdmitted` key is accepted until the parser has a node budget (hand-off, section 5). Text is at most 4,096 UTF-16 characters for `detail` and `reason`, 1,024 for every other text and list element; no unpaired surrogate; instants have at most microsecond precision and a year from 0000 to 9999. **A constructed object is serialisable except for its size:** the constructor refuses what `toBytes` could never write (an unpaired surrogate, an instant of more than microsecond precision or outside the years 0000 to 9999), but the lists of the schemas have no count bound, so a list of very many elements builds an object whose canonical bytes are over the bound of its type and `toBytes()` then throws `IllegalArgumentException`; a producer that must know before it takes an effect calls `toBytes()` first (`DurableSeal` does, in its validation). A consequence: a `DeliveryIntent` over 1 MiB (about 15,600 context ids) can no longer be sealed; it is refused before an attempt id is taken.
- **Media type and retention.** `application/vnd.regpack.journal+json`; retention class `journal`, asked from the `RetentionPolicy` with the object's `clock_instant`. The class names `journal`, `sealed` and `epoch` and the period 1,826 days are the OI-6 defaults, for tests and tools only; Legal's values are a deployment hand-off.
- **Payload version 1** (required keys exactly, no unknown key; counts are non-negative `Long`, hashes 64 lower-case hex):

| Type (wire name) | Class | Required payload keys |
|---|---|---|
| `DeliveryIntent` | a only | `attempt_id`, `delivery_id`, `business_key`, `trn`, `version_seq`, `action`, `logical_hash`, `artifact_sha256`, `file_name`, `context_ids` (list of hashes) |
| `BatchAdmitted` | a only, control scope | `batch_id`, `pack_digest`, `context_digests` (list of hashes) |
| `TransportResult` | b only | `attempt_id`, `status`, `detail`, `observed_at` (instant) |
| `FeedbackReceived` | b only | `feedback_sha256`, `received_at` (instant), `file_ids` (list of text) |
| `RecoveryDecision` | a or b | `delivery_id`, `attempt_id`, `intent_restore_epoch`, `artifact_sha256`, `decision`, `authorises_effect`, `reason`; `authorises_effect` must be true exactly when the object is class (a) |
| `OperatorAction` | by kind | `kind`, `operator`, `subject`, `detail` |
| `VersionAssigned` | b only | `batch_id`, `assignments` (list of objects with exactly `subject`, `trn`, `version_seq`) |

- **`OperatorAction` kinds** fix the class and the scope: `APPROVAL` class (b) with either scope in the schema; `WRITE_OFF`, `FORCED_RESEND`, `ROUTE_CHANGE` class (a) with an endpoint scope; `PACK_ACTIVATION`, `PACK_ROLLBACK`, `PACK_EXPIRY` class (a) with the control scope. `WRITE_OFF` is class (a) because spec 11.2 gates the effect of a forced resend and a write-off. The kinds are closed at seven and `JournalKey.ClassB` refuses the control scope, so an `APPROVAL` in the control scope cannot be built through `JournalObject` (open item, section 4).
- **Producers' duty.** Version 1 does not cross-check the payload's `attempt_id` or `delivery_id` against the key subject. `DurableSeal` takes the attempt id once and uses it in both places; `EvidenceVerifier` reports a difference as INTENT_MISMATCH. The intent's `business_key` and `version_seq` are checked against the ledger row of the delivery by `seal` (an `IllegalArgumentException` before any effect) and by `verify` (INTENT_MISMATCH); `trn`, `action` and `logical_hash` are not in that row and stay the sender's duty (P8).
- **`JournalWriter.write`.** Retention from the policy, `put`. `CREATED` or, for an existing key with the same `payload_sha256` (whatever the envelope's instant), `ALREADY_PRESENT_SAME_PAYLOAD`, which is returned only after the stored object (its bytes, media type and retention) has been put again through the store and that put has returned; any exception of that put propagates. On a two-volume store that second put publishes a missing second copy; on any other store it is an idempotent no-op. Another payload hash under the key is an `EvidenceIntegrityException`; `EvidenceCorruptionException` is never absorbed. The writer returns neither the stored hash nor the stored size (section 5, P3d).

### 1.5 P-SEALED (`SealedEvidenceStore`)

**Grade and claim.** Grade `("P-SEALED", "")`. Tamper-evident, not immutable: someone with storage access can delete or rewrite files. It claims the durability of spec 5.4 (an acknowledged write survives the loss of one volume) and counts failure domains only as far as `VolumeProbe` can show (section 3, item 2). It is test-grade until SP-W has reported (section 3, item 1). Nothing wires it.

**Layout of one volume.** `{root}/.sealed-volume` holds the volume id (a dot file, plain text, at most 256 bytes, read with trailing white space removed); an object `a/b/c` is the file `{root}/o/d-a/d-b/o-c` and its retention record `{root}/o/d-a/d-b/m-c`. The volume ids are 1 to 32 characters of `[a-z0-9-]` and differ. A segment is encoded injectively and independently of case: every capital letter becomes `^` and the lower-case letter, a final `.` becomes `^0`, every other character of the alphabet is unchanged, the prefixes `d-`, `o-`, `m-` keep every name from being a bare Windows device name. Vectors: `enc('Landing')` is `^landing`, directory `A.b` is `d-^a.b`, object `abc.` is `o-abc^0`, object `con` is `o-con`, meta `K1` is `m-^k1`; 100 capitals give 202 characters. A temporary file is `{name}~tmp~{pid}~{counter}` (`~` is outside the alphabet, so a temporary name never decodes and is never listed or served).

**File formats (version 2, the whole file sealed).**

- Object file: the magic `RPSEAL02`, a big-endian int32 header length, the canonical JSON header (fields `key`, `media_type`, `sha256`, `length`, `written_at`, `retention_class`, `retain_until`; at most 65,536 bytes), the payload, and a 32-byte SHA-256 trailer over all the bytes before it. Golden: 297 bytes, SHA-256 `6ba2ff133d8c5097ef0bdf16cc772a6a98669e098bbd68d0002a0dc78720308a` (key `landing/k1`, payload `hello`, media type `text/plain`).
- Meta file: `RPMETA02`, the canonical JSON of the four fields `rev`, `retention_class`, `retain_until` and `legal_hold`, the same trailer. Golden: 139 bytes, SHA-256 `03b06654451ec4dd82b7f234894df1f096ae2175f8999d59811b0c2aa4e4a0a3`.
- Decoding checks, in this order: the magic, the minimum size (44 bytes for an object, 40 for a meta), the trailer, then header length, the canonical header text, the key the file was read under, the length and the payload hash. Reasons: `BAD_MAGIC`, `HEADER_TOO_LARGE`, `BAD_HEADER`, `KEY_MISMATCH`, `LENGTH_MISMATCH`, `HASH_MISMATCH`, `TRUNCATED`. A flipped bit anywhere and every cut of the golden files is a `CorruptException`. A deliberate edit that recomputes the trailer is not found before the signed manifests of P3c (section 3, item 5).

**Put (under a 64-way striped lock of the key).** Both volumes are read first. A damaged copy on either volume, and two whole copies that differ in any byte (a different payload, or the same payload under another header: write time, media type, retention class or retain-until), are an `EvidenceCorruptionException`; a copy with other bytes than the request is an `EvidenceIntegrityException`; nothing is written in any of these cases. If exactly one volume holds the key, its verified file is published to the other, so the two stay byte-identical and the first header (media type, write time, retention class) is kept. If neither holds it, the object file is built and published to volume a, then to volume b, and the call returns after both. The result is `CREATED` only when neither volume held the key. A failure on the second volume is an `EvidenceUnavailableException`; the object stays on the first volume, is served from it, and a retry with the same bytes completes the second. `put` holds the whole object in memory.

**Publish (one volume).** The file is written under a temporary name in the final directory (`CREATE_NEW`, then `FileChannel.force(true)` of data and metadata), given its name by a hard link (a link never replaces, so of any number of writers exactly one gets the name and the file at the name is always one writer's bytes in full), the temporary name is deleted, and then the directory is forced on POSIX systems together with the parent of every directory this JVM created and has not yet been able to sync. When the link is refused because the name exists, the holder and every ancestor up to and including the root are synced before `false` is returned (the in-memory bookkeeping of unsynced directories is empty after a restart). **On Windows no directory is forced** (the JDK cannot open one); `durability()` still reports synchronous acknowledgement there (section 3, item 11). A volume that cannot make a hard link, or whose root sync fails where supported, refuses to open (assumption A10).

**Reads.** `get` serves the payload of the first copy that passes its own seal (volume a, then b); it reads both copies when it can, and the retention class and retain-until it returns are those of the header with the longest retain-until, maximised with both metas (described next); no valid copy and an unreachable volume is `EvidenceUnavailableException`, no valid copy and a damaged one is `EvidenceCorruptionException`. `list` is the union of the keys of both volumes in UTF-16 code-unit order; it walks and sorts a subtree (section 3, item 3).

**Retention and legal hold.** The header holds the first retention. Each key may have a meta file with a revision on each volume. The effective retain-until is the maximum over **both headers** and both metas (two copies can differ in the header only, which `put` and the retention methods refuse as divergent; `get` still serves the longest); the legal hold is that of the meta of the higher revision (two metas of one revision merge: later retention, hold of either). `extendRetention` only extends (`EvidenceRetentionException` for a shorter instant) and `setLegalHold` writes a new revision (top plus 1) to volume a, then b, in three tries ("another writer keeps changing it" is an `EvidenceUnavailableException`). Both return in the "requested state already holds" branch only after the meta directory of every volume that holds a meta has been synced again. A meta write replaces only a lower revision (temporary file, force, atomic replace, directory sync). `repair` never shortens retention: if the lower-revision meta holds a later retain-until, it writes a new revision with that retain-until and the higher revision's hold to both volumes.

**Health, open, repair, scrub.**

- `open` first decides, before it creates anything, that the two roots are different directories with neither inside the other (on the absolute normalised paths and on the real path of the nearest existing ancestor, so a link above a root that does not exist yet is caught; a refused open leaves the file system as it was), then creates both roots (syncing the parent of every directory it creates), checks the real paths again as a safety net, runs the hard-link self-test on both volumes, and reads both markers. Two missing markers on two empty roots are a new store (both markers are written, a then b). One missing marker is a replaced disk: the store is `degraded()`, declares no synchronous acknowledgement, refuses every write and is brought back by `repair()`; the exception is a first open that stopped between its two markers, which is recognised (neither volume holds an object or a meta) and completed. A marker that names another volume refuses the open; so do two unmarked roots of which either holds any entry ("both volumes are unmarked and their roots are not empty (<volume a holds N entries, volume b holds M entries>; the root of a new store must be a new empty directory below the mount point)": the text names the volume id and the number of entries, no file name). It also sweeps stale temporary files, those of a dead pid and those of a live pid that were last written more than 2 seconds before this JVM's start instant, **except a complete one**: a temporary that decodes as a whole object (its header key is the key that its directory and name give) or a whole meta, and whose final name does not hold the same bytes (for a meta: holds no higher revision), may be the only surviving name of an acknowledged write after a power loss on Windows, where no directory is forced. It is kept where it is, never listed or served, and `scrub()` reports it. Half-written files, files at the wrong key, files whose final name holds identical bytes, superseded metas and the self-test file are deleted; a temporary that cannot be read makes `open` throw `EvidenceUnavailableException` (nothing uninspected is deleted).
- `repair()` copies every object and meta that one volume holds and the other does not (a damaged source is skipped, an existing copy is never overwritten) and writes missing markers last, so a repair that fails midway leaves the store degraded. Idempotent.
- `scrub()` reads each key under the key's lock and writes nothing. One line per defect, sorted by key (or path) and volume id: `<volumeId> <key> CORRUPT`, `<volumeId> <key> MISSING_COPY`, `<volumeId> <key> CORRUPT_META`, `<key> DIVERGENT` (both copies are whole but differ in **any** byte, also in the header alone), and `<volumeId> <path> COMPLETE_TEMPORARY`, where `<path>` is the path of the kept temporary file below the volume root with '/', for example `o/d-landing/o-k1~tmp~4711~3` (a bare temporary name is ambiguous across directories). Empty on a clean store. It is the only detector of a masked single-copy corruption, of divergent copies and of a kept temporary; run it after every repair and expect it empty. The manual cure of a `COMPLETE_TEMPORARY`: the operator adopts the file by renaming it to its final name **only when that final name is absent**; when the final name exists (for example after a retry of an unacknowledged put wrote the key with a new write time) the operator compares the two and removes the temporary, otherwise the line stays for ever (a permanent false alarm that is known: a clean store is then not `scrub`-empty). One unreadable temporary file makes the whole `scrub()` throw `EvidenceUnavailableException`, which hides every other finding.
- **Interrupt.** A thread interrupted during a forced write gets an `EvidenceUnavailableException` ending in "interrupted", the temporary file is removed and the interrupt flag is set again; a caller that retries in the same thread must clear the flag first.
- **`durability()`** is `(true, domains)` while both volumes are healthy (marked and readable) and `(false, 1)` otherwise, **except** that it throws `EvidenceUnavailableException` ("no evidence volume can be reached") when neither volume can be reached; the send gate reads that exception as "the evidence store durability cannot be read" (closed). `domains` is 2 when the probe puts the two roots in different domains. `VolumeProbe.fileStores()` uses the device number and file-store type where the platform has the `unix` attribute view, and the file-store name, type and description (the drive) elsewhere. Two directories of one file system are one domain; two file systems on one physical disk count as two.

### 1.6 The table `object_manifest` and the semantics of `recordObjects` and `beginSending` with objects

Migration `V002__evidence_manifest.sql` (SHA-256 `7dd09d404be962f44a463ddbaec961b41abf5192fa109cba9951412bf8cf562a`; applied scripts are never edited) from the approved document (AP-7, SHA-256 `a48d083f15e849fa9f8e0d40eac383107810cde97238ec4fb3afe7dd9c101662`): one table, one index, one trigger.

| Part | Definition |
|---|---|
| `object_manifest` | `object_key text COLLATE "C" NOT NULL`, `entity_id smallint NOT NULL DEFAULT 1`, `object_class smallint NOT NULL`, `sha256 bytea NOT NULL`, `size_bytes bigint NOT NULL`, `provenance smallint NOT NULL`, `attempt_id bigint`, `written_at timestamptz NOT NULL` |
| constraints | `object_manifest_pk` primary key on `object_key` alone (D1: unpartitioned, so one key can never carry two hashes on two days), `object_manifest_hash_check` (`octet_length(sha256) = 32`), `object_manifest_size_check` (`size_bytes >= 0`); no foreign key from `attempt_id` (D3: after a restore the evidence tier is ahead of the database); no CHECK on the code sets |
| index | `object_manifest_attempt_idx` on `attempt_id` where it is not null |
| trigger | `object_manifest_immutable` rejects UPDATE and DELETE through `reject_modification()` of V001 (D2); no purge in release 1 (D5) |

- **`recordObjects(entries, provenance, attempt)`** is all or nothing in one unit. A key that exists with the same hash is left unchanged (the first row wins, with its provenance, attempt and time); with another hash it throws `ManifestConflictException` and nothing of the call is stored; the message names the key path only. Two entries of one call with one key are an `IllegalArgumentException`. A call that inserted no row (an empty list excepted, which returns early; every key already stored with the same hash) has written nothing: it ends with the replay barrier of section 1.8 (`Unit.durabilityBarrier`), so that the success of a retry of a call whose commit was "not confirmed" is as durable as the first call's. `PgManifest.record` returns whether it inserted a row; a driver count of 0 or `SUCCESS_NO_INFO` counts as "inserted nothing", which at worst adds one lock. `writtenAt` of a new row is the ledger clock. An entry's `sha256` and `sizeBytes` are those of the object bytes as handed to the store: for a sealed file the bytes themselves, for a journal object the whole canonical JSON, never the `payload_sha256`. The rows are insert-only; a row may name an attempt that has no attempt row.
- **`beginSending(delivery, attemptId, token, intent)`** is one unit. Order: the delivery must exist (else `IllegalArgumentException`); the attempt id must have been allocated (else `IllegalArgumentException`) and not be stored on an attempt (else `DuplicateKeyException`); the fence on the lease (no match: `STALE_LEASE`, nothing written); the compare-and-set `QUEUED` to `SENDING` (no row: `STATE_MISMATCH`; the in-flight index: `IN_FLIGHT_CONFLICT`); the attempt row; then the manifest rows of `intent.objects()` with provenance `WRITTEN` and this attempt id. A conflicting key throws `ManifestConflictException` and the unit rolls the state change back (the delivery stays `QUEUED`, no attempt row, no manifest row, the attempt id stays unused). A status other than `APPLIED` records nothing. The attempt row and the manifest rows share one ledger time.
- **`manifestRows(prefix, after, limit)`** is a range on the primary key in byte order of the key (the order of `EvidenceStore.list`), at most `min(limit, 1,000)`; the prefix need not end at a segment boundary and may be empty; a negative limit is an `IllegalArgumentException`; a prefix that no key can have lists nothing. `PgManifest` statements are pinned by `PgManifestTest`: `INSERT ... ON CONFLICT ON CONSTRAINT object_manifest_pk DO NOTHING`, `SELECT object_key, sha256 FROM object_manifest WHERE object_key = ANY (?)`, and `WHERE object_key >= ? AND object_key < ? AND object_key > ? ORDER BY object_key LIMIT ?`. **Observed** at CP-1 (run 39599214942, 539 tests, skipped 0): the arbiter with the row trigger, the `COLLATE "C"` range, `text[]` binding, the CHECK and unique violations with their constraint names, the index use of the three reads and the wait-then-skip path under READ COMMITTED all behave as designed.
- **Conditions on any caller of `PgManifest.record`** (the Javadoc is the source): it must be the last statement of a short unit (every inserted key is locked until the unit ends; a concurrent unit that records the same key waits for `lock_timeout`, 5 s by default, and then fails with `55P03`; in the lock order the manifest keys come after the delivery rows); the unit must run under READ COMMITTED (`Unit.begin` sets it). A connection opened without it, on REPEATABLE READ or stricter, fails earlier than the read-back: the `INSERT ... ON CONFLICT DO NOTHING` against a row that its snapshot cannot see raises `40001` ("could not serialize access due to concurrent update") itself, which is a `LedgerException` carrying that SQLSTATE and still fails closed; the branch that fails with "has no manifest row after its insert" is a safety net that no isolation level is known to reach (final review POSTGRES-3: the earlier text said the read-back fails). The call sorts the keys itself, so a caller must not split one set of keys over several calls of one unit.
- **`PgDeliveries.beginSending(Connection, ...)` does not undo itself.** It is package-private; the conflict is found in Java after the state change and the attempt row were written, no SQL error aborts the transaction, so a caller that caught the exception and committed would keep SENDING. Its only caller outside the tests is `Unit.inUnit`, which rolls back on any exception. A later unit that composes it with other writes must roll back or take a savepoint.
- **Size (an estimate from the design document, not measured).** About 464,000 rows a day at the SP-L volume model (50 million records a day), about 165 to 170 MB a day, 60 to 62 GB a year and 300 to 311 GB after 5 years of 1,826 days without purging (about 0.18 percent of the ledger estimate of 166 TB). A purge or archive design is due before the first production quarter.

### 1.7 `DurableSeal`, the send gate and the restore-epoch marker

`DurableSeal implements Sealing` (spec 11.2 steps 2 to 4; D-E4) over a `LedgerStore`, an `EvidenceStore`, a `Clock`, a `RetentionPolicy` and a `SendGate`. It never calls a transport. `seal(request)` runs in this order and nothing reorders it:

1. **Validation, no effect.** The SHA-256 of the bytes equals `intent.artifactSha256`; the intent names the request's delivery and file name; the media type is 1 to 255 characters (UTF-16), not blank, with no ISO control character and no unpaired surrogate; the endpoint has a journal scope (assumption A9); the delivery exists and belongs to the request's endpoint; the intent's `business_key` and `version_seq` equal those of the delivery row (`trn`, `action` and `logical_hash` are not in the row and stay the sender's duty); the intent object and the `AttemptIntent` are built once as a dry run, and the dry run calls `toBytes()` with the widest attempt id (999,999,999,999) and the last instant, so a text the journal or the ledger cannot hold, and an intent object over the 1 MiB bound of its type (about 15,600 context ids), are found here, before an attempt id is taken. Any of these is an `IllegalArgumentException` before the gate, an attempt id and any put (the messages name the field, never the value). A consequence for a P8 sender: it must pass the identity of the ledger row.
2. **State check.** A delivery that is not `QUEUED` is `STATE_MISMATCH`, nothing written (advisory; `beginSending` stays the judge).
3. **The send gate.** A closed gate is `GATE_CLOSED` with the reasons joined by "; ", nothing written, no attempt id taken.
4. **An attempt id** from the ledger sequence (`allocateAttemptId`; the sequence is never rewound, an id of a seal that does not end `SEALED` is a gap).
5. **PUT of the sealed bytes** at `sealed/{hex2}/{hex64}` (retention class `sealed`), then **PUT of the `DeliveryIntent` journal object** (class (a), key subject the attempt id, ordinal 1, restore epoch of the lease token, `clock_instant` the clock reading of this step; media type `application/vnd.regpack.journal+json`). An already stored intent object with the same payload but other bytes fails the seal closed with an `EvidenceIntegrityException` (the manifest row would otherwise name a hash that is not the stored one).
6. **One ledger unit** `beginSending` with the manifest entries planned before the first put, exactly two and in this order: SEALED_FILE (hash and size of the sealed bytes) then JOURNAL_A (hash and size of the canonical intent bytes). Because the sealed key is content-addressed, two deliveries with identical bytes share one sealed object and one manifest row (the first row wins, with the first attempt).

Statuses (`SealStatus`): `SEALED` (both objects acknowledged and the delivery is `SENDING`; the attempt is present only then), `GATE_CLOSED`, `EVIDENCE_UNAVAILABLE` (an `EvidenceUnavailableException` on either put; the ledger is untouched; an object already acknowledged stays as an orphan; the detail never repeats the exception text), `STALE_LEASE`, `STATE_MISMATCH` and `IN_FLIGHT_CONFLICT` (the ledger refused the unit after the puts; the objects stay as orphans by design, spec 7.2). **Not caught, so the seal fails closed by exception:** an `EvidenceIntegrityException` or `EvidenceCorruptionException` of the store, a `ManifestConflictException`, and any `LedgerException`, including "commit not confirmed by the synchronous standby" (section 1.8): the caller must read a `LedgerException` out of `seal` as outcome unknown and send nothing.

`beforeFirstByte(endpoint, attempt, token)` is the commit gate that the sender passes to `Transport.send` (it is `CLEAR` only then). In this order: the send gate (`GATE_CLOSED`); the current lease of the endpoint holds `token` (`STALE_LEASE`); the attempt has a row and its `commit_issued` is false (`MARKER_REFUSED`: the ledger's marker statement is idempotent, so a second pass for one attempt is refused here); the token of the attempt row equals the given token (`STALE_LEASE`: a token is not bound to an endpoint, the first token of every endpoint is the same, so the lease check alone cannot tell); the delivery of the attempt exists, belongs to the given endpoint and is `SENDING`, and the manifest holds both rows of the SENDING unit, the sealed file with the attempt's artifact hash and the intent object naming this attempt (`MARKER_REFUSED`; an attempt begun through the bare ledger without `Sealing` does not pass); the highest restore-epoch marker of the evidence tier is readable (`EPOCH_MARKER_UNREADABLE` for an outage, a damaged marker or a foreign key under the prefix) and equals the restore epoch of the token (`EPOCH_MARKER_DIFFERS`); then the fenced `markCommitIssued` (`CLEAR`, or `MARKER_REFUSED`). The residual race of two concurrent callers for one attempt is not decided by the database (the check that the marker is not yet set is a read, and the marker statement is idempotent, so two concurrent callers can both see `CLEAR`): it rests on the sender's in-flight guard (one attempt, one thread, a duty of P8) and on the destination's refusal of a duplicate file (SEAL-4).

`SendGate` (D-E11) is a library check of both sides: `Requirement(ledgerSynchronous, evidenceSynchronous, minFailureDomains)`; `Requirement.production()` is `(true, true, 2)`; `Requirement.none()` asks and reads nothing and is for tests and tools. A side is read only when the requirement asks something of it. The reasons are fixed texts, in this order and joined by "; ": "the ledger commit is not acknowledged by a synchronous standby" (a status that is not synchronous, or is synchronous with fewer than one standby); "the ledger durability cannot be read"; "the evidence store does not acknowledge a write only when it is durable"; "the evidence store has fewer than N independent failure domains"; "the evidence store durability cannot be read". A `RuntimeException` while asking closes the gate and its text is never repeated. There is no manifest condition (section 3, item 15).

`EpochMarker`: `declare(epoch)` writes the marker (the same epoch again is an idempotent success; other bytes under the key are an `EvidenceIntegrityException`) and is the restore procedure's, not the sender's; `current()` lists `control/epoch/` in pages of 1,000 and returns the highest epoch (0 when none), strictly: a key under the prefix that is not `e` plus exactly twelve digits, or a highest marker whose bytes are not exactly the canonical text of the epoch of its key, is an `IllegalStateException`; an outage is never read as "no marker". The zero-padded key makes epochs 9 and 10 sort numerically.

### 1.8 The standby gate and the commit-warning rule

**`PgLedgerDurability`** answers `LedgerDurability` from the server (assumption A11). A commit is **synchronous** exactly when all three hold: the `synchronous_commit` a unit of the adapter commits with is `on` or `remote_apply`; `synchronous_standby_names` is not blank; and the number of standbys that are `streaming` with `sync_state` `sync` or `quorum` is at least `n`, where `n` is the number of `ANY n (...)`, `FIRST n (...)` or `n (...)` (case-insensitive) and 1 for a plain list or `*`. The read is one unit with `SET TRANSACTION READ ONLY` (so its commit has no transaction id and never waits for a standby): `SELECT setting FROM pg_settings WHERE name = 'synchronous_standby_names'`, `SELECT count(*) FROM pg_stat_replication WHERE state = 'streaming' AND sync_state IN ('sync', 'quorum')` and, only when `Config.forceSynchronousCommit` is false, `SELECT reset_val FROM pg_settings WHERE name = 'synchronous_commit'` (the prologue overrides the setting inside the transaction, so `current_setting` would always say `on` there; when forced the effective value is `on`). The detail is a fixed text with the failing conditions and the counts, for example "0 of 1 required synchronous standbys are streaming". The status is a reading at one moment; it does not make a commit synchronous.

**The commit-warning rule (`Unit.inUnit`, EF15).** The warnings of the connection are cleared when the unit begins and again immediately before `commit()`. After `commit()` the unit is marked committed (the connection is released as committed) and the warning chain is walked: any `SQLWarning` whose SQLState is null or does not start with `00` (a NOTICE is `00000`) fails the unit with `LedgerException("commit not confirmed by the synchronous standby (sqlstate=<five characters or none>)")` and the warning as its cause; a failure to read the warnings fails the unit too. No list of SQLStates and no message text is matched (the text depends on `lc_messages`). The transaction has committed locally and may not be on the standby: **the caller must read the exception as unknown, send nothing, and leave the `SENDING` row without a marker to recovery** (spec 11.5 A.3 a). This holds for the `beginSending` unit and for the `markCommitIssued` unit.

**What the rule covers, and the replay barrier (final review POSTGRES-1 and SEAL-3, fixed by FH).** The rule covers the unit's own commit. The server makes a commit wait for the standby only when the transaction has written WAL, so a unit that wrote nothing has no transaction id, never waits and can never warn, whatever the state of the standby. That is right for a read, but not for the replay of an idempotent write whose success a caller takes to mean "it is stored": after a first call whose commit was reported "not confirmed", a retry that only found the rows would have returned at once, and a pipeline would have acknowledged the source (I1, acknowledgement limb) for rows that exist on the primary only. So the replay branches end with a barrier that makes their commit wait like the first call's: the ingest redelivery reads the stored batch row with `FOR SHARE OF b` (`PgIngest.BATCH_SELECT_SHARE_SQL`) as the last statement of its unit; a `recordObjects` that inserted no row, a `commitDecisions` of only `NOOP_REDELIVERY` decisions with no outbox completion, and a `commitReportable` redelivery that created no version run `Unit.durabilityBarrier`, which is `SELECT 1 FROM restore_epoch WHERE singleton FOR SHARE`. **A transaction id alone is not a barrier:** `RecordTransactionCommit` computes `wrote_xlog` before it writes its own commit record, and assigning an id writes no WAL, so a unit that only calls `pg_current_xact_id()` commits asynchronously. A row lock is WAL-logged (`XLOG_HEAP_LOCK`), and because its commit record is later in the log than the first attempt's, a standby that confirms it has the first attempt as well; when the wait is cancelled the retry ends in the same `LedgerException`. The lock on the `restore_epoch` singleton is held until the commit returns, including a stuck standby wait, and conflicts only with `declareRestoreEpoch`, which then waits up to `lock_timeout` (`55P03`, section 3, item 26); the ingest uses the batch row, which conflicts with nothing. No barrier is needed by lookups, the durability read, `LedgerIntegrity` and refusals (`STATE_MISMATCH`, `STALE_LEASE`, `Held`), and none is added to the dictionaries and the partition creation (nothing is acknowledged on them), to `Migrator` (it commits without the warning rule) and to `PgLeases.release` on a retry (it writes nothing; the lease then stays held until its TTL). The new server test `PgDurabilityDownIT#aRedeliveryAfterAnUnconfirmedIngestCommitIsNotAcknowledgedEither` was **observed** at CP-3 (run 39854837072): the redelivery of the batch, with the standby still down, waited in the wait for synchronous replication until the harness cancelled it and ended in "commit not confirmed by the synchronous standby (sqlstate=01000)", like the first delivery (the notice lines `cancelled-ingest-wait` and `cancelled-redelivery-wait`); so a row lock does make the commit wait and warn on cancel, and the ledger role (`postgres`, a superuser, in CI) can take it. That the non-superuser ledger role of a deployment holds `UPDATE` on `ingest_batch` and `restore_epoch` is the code's own use of both tables and is not observed with such a role. Rules for callers: `STATE_MISMATCH` and a `false` marker result must never be read as "already done" (the retry after an unconfirmed `beginSending` gets `STATE_MISMATCH`; the retry after an unconfirmed marker commit gets a normal `true`, because the UPDATE writes); `declareRestoreEpoch` for an epoch already on the primary throws `IllegalArgumentException`, which an operator must read as "maybe already declared, verify on the standby". An unknown commit outcome is the message prefix "commit not confirmed by the synchronous standby" on a plain `LedgerException`, not a subclass; a typed exception would help the retry logic of P3d and P8.

**Observed on the real runners** (job `ledger-durability`, run [39714442722](https://github.com/Hansie91/regpack/actions/runs/39714442722) on `45f1277`, all nine jobs green; the primary has `synchronous_standby_names = 'ANY 1 (standby1)'` and a streaming hot standby of the pinned PostgreSQL 18.6 image, pgjdbc 42.7.14):

1. A COMMIT whose wait for synchronous replication is ended by `pg_cancel_backend` returns with a **WARNING with SQLSTATE `01000`** in `getWarnings()`; both the `beginSending` unit and the marker unit then fail with "commit not confirmed by the synchronous standby (sqlstate=01000)". The plan's recollection (a cancelled wait is reported as `01000`, the driver surfaces it) is confirmed.
2. **`statement_timeout` does not end a COMMIT's wait.** A store with a 2-second statement timeout was still blocked after 6 seconds in both cancel tests (the harness cancels only a call that is still blocked after at least 6 seconds), and the harness had to end the wait with `pg_cancel_backend` (`ended-by=pg_cancel_backend`). That is observed; the reason (the server cancels the statement timeout before the commit) is the T17 reading of the server source, which the run confirms. `lock_timeout` does not bound a commit wait either (from the same reading; no test isolates it). The sender therefore needs a client-side bound on a commit, and the bound is a **watchdog that cancels the backend from a second connection** and reads the resulting `01000` warning as "unknown": a socket timeout alone ends nothing on the server, where the backend keeps waiting and keeps its row locks (section 5, P3d and P8). The tests keep the plan's name `aCommitWaitCancelledByTheStatementTimeoutIsNotReportedAsDurable` because the evidence lines cite it.
3. With replay **paused** on the standby (`pg_wal_replay_pause()`), a `beginSending` under `remote_apply` stays blocked with the wait event `SyncRep` (the backend's statement is `COMMIT`, the pause state is `paused`), while a control commit under `on` returns at once with its row invisible on the standby; after the resume the call returns and its rows are visible at once.
4. **The SENDING row and the attempt row are visible on the hot standby the moment `beginSending` returns** (under `remote_apply`, no polling; the store of that test is built unforced, `forceSynchronousCommit` false, with a `remote_apply` connection option). **Exit clause (3) must carry this qualifier** (final review SPEC-4 and POSTGRES-4): visibility on the standby when the call returns is shown for `remote_apply` on an unforced store. The default configuration (`Config.forSchema`, which forces `synchronous_commit = on` in the prologue of every unit) commits with `on`, which returns when the standby has **flushed** the commit, not when it has replayed it; that guarantee ("flushed on the standby before the call returns") is shown by the Down phase (a commit with no standby waits) and by the control commit of the visibility test (an `on` commit returns while its row is still invisible on the standby, replay being paused), not "visible at once". No test runs the forced `on` production configuration with replay paused and a standby up. At the end of the run the primary, standby flush and standby replay positions are equal and `sync_state` is `quorum`.
5. `pg_stat_activity` shows `SyncRep`; `reset_val` reflects a connection option; the READ ONLY durability read is accepted after earlier queries; `PgLedgerDurability` reports a synchronous quorum standby with the standby up and "0 of 1" with it stopped.
6. The commit-warning rule on **every** unit caused no false alarm: `ledger (real PostgreSQL 18)` ran 48 classes and 574 tests with failed 0 and skipped 0 (runs 39674216938 and 39714442722), so pgjdbc does not report a non-`00` warning after an ordinary commit.
7. The scripts `scripts/ci/pg-quorum-up.sh` and `pg-init-replication.sh` and the pinned image worked as written, including `pg_basebackup` over `trust` with `-c fast`. The first run (39674216938) failed at its install step because failsafe 3.6.0 ignores `-DskipTests` (the corrected step passes `-DskipITs`).

**Not observed (documented server behaviour only):** that a ledger role without `pg_monitor` or `pg_read_all_stats` sees no streaming standby (every test connects as the superuser `postgres`; the rule is the documented visibility of `pg_stat_replication` and the Javadoc states it: such a role reads zero standbys and the gate stays closed; a CP step with a non-superuser ledger role would observe it); the `pg_terminate_backend` path (a terminated session is expected to end the connection, so that `commit()` itself throws; the observed path is the cancel, which warns with `01000`); a failover or promotion; a standby under replay lag in normal operation; the 55P03 of a second seal behind a stuck commit; more than one standby; the hot path at 50 million records a day.

### 1.9 `verify` over the evidence tier

`new EvidenceVerifier(store, ledger).verify(prefix)` (a library; the application is not wired) lists the evidence store and the ledger's manifest in key order in pages of 500, walks the two lists side by side, reads every listed object through `EvidenceStore.get` and returns a `Report(findings, objectsChecked, manifestRowsChecked)`, sorted by key, kind and detail. A clean tier has no finding. The classes (assumption A13):

| Class | Meaning |
|---|---|
| `ORPHAN` | an object in the listing with no manifest row; a crash orphan (spec 7.2, D-E8), not an error of the writer. Detail `sha256=<hex>` of the stored bytes, `sha256 unknown` when the object is damaged, and for a `DeliveryIntent` object with neither a manifest row nor an attempt row the detail `in-doubt input (11.5 B.5)` |
| `MISSING` | a manifest row whose object is not in the listing, or is gone when read; and a sealed file that a parseable `DeliveryIntent` object names (`artifact_sha256`) and the tier does not hold, with the detail "named by an intent, absent", also when the ledger has no row for it (a database restored from a backup older than the seal); a file missing for both reasons is one finding, the manifest row's. The existence check is one `list` call with limit 1 per distinct sealed file and run |
| `HASH_MISMATCH` | detail `store-integrity`: the store reports the object damaged (an `EvidenceIntegrityException`, `EvidenceCorruptionException` included) or answers with a hash that is not the hash of its bytes; detail `manifest-hash`: the object is whole but its SHA-256 or length is not what the manifest recorded |
| `SEQUENCE_GAP` | the class (b) objects of one scope and epoch must have the seq numbers 1 to their maximum; the first hole of each group is reported with the key of the absent seq; a group the prefix cuts is not judged |
| `INTENT_MISMATCH` | a `DeliveryIntent` object that is not what its key and the ledger say: not a journal object, an envelope naming another key, a payload `attempt_id` that is not the key subject and, where the attempt has a row, another `artifact_sha256`, `file_name` or `delivery_id`, a key scope that is not the endpoint of the attempt's delivery or a key restore epoch that is not the token epoch of the attempt, and, where the delivery has a row, another `business_key` or `version_seq`. Details (fixed texts): "the object is not a journal object" (also for an object over 1 MiB under a `DeliveryIntent` key, refused unparsed), "the envelope names another key", "attempt_id differs from the key subject", "artifact_sha256 differs from the attempt row", "file_name differs from the attempt row", "delivery_id differs from the attempt row", "business_key differs from the delivery row", "version_seq differs from the delivery row", "the key scope is not the endpoint of the attempt", "the key restore epoch is not the token epoch of the attempt". `trn`, `action` and `logical_hash` are not in the ledger and are not compared |

An outage of the store or the ledger aborts the run (an object that cannot be served is not a missing object); a damaged object is never reported as `MISSING`. A missing attempt row or manifest row is an `ORPHAN` or `MISSING`, never an `INTENT_MISMATCH` (after a restore the evidence tier is ahead of the database). The keys under `control/epoch/` are neither orphans nor missing, and an unrecorded marker is not read: the epoch-marker coverage is P4. **What `verify` does not see:** a damaged copy that the other volume masks (that is `scrub`); an edit that recomputes the seal of a P-SEALED file; `UNEXPLAINED` and chain breaks (they need the signed manifests of P3c); it is meant for a tier nobody writes to (an overlapping write may show as `ORPHAN` or `MISSING`, and a second run decides). Storage half of I10: from the evidence tier alone the identity of every attempt that gated an effect is reconstructable (the `DeliveryIntent` object carries business key, TRN, version, action, logical hash, artifact hash, file name and context ids).

### 1.10 Crash points and what is left behind

The column "Recovery decides" quotes spec 11.5 A.2, A.3, A.4 and B.5 and nothing else; remarks about what the code does are in the evidence column. P3b1 builds none of the recovery (it is P3d and P4).

## 3. Limits

Each limit says who owns it. `SealedEvidenceStore.limits()` has 19 items (17 until FJ; items 18 and 19 are new, items 1, 3, 10 and 15 changed); the items the plan names are repeated here in their current wording and the weaker earlier wording is not.

1. **P-SEALED is test-grade until SP-W has reported** (limits items 1 and 2). Not exercised: power loss, drives that acknowledge a flush early, SMB and other network file systems, ReFS, Windows Server volume pairs, and the directory durability of Windows. Directory entries are forced on POSIX systems only; on Windows a new file name may not survive a power failure although its data was forced. The build job on `ubuntu-24.04` was green at CP-1a, but whether each POSIX-only test ran and was not skipped is not observed in CI (item 23), and no test shows a directory entry surviving a power failure. After a power loss on Windows the final name of an acknowledged object may be missing while its complete temporary file survives: the sweep keeps such a file and `scrub()` reports it as `COMPLETE_TEMPORARY` (section 1.5). Owner: the SP-W run (entry target `P-SEALED-outside-tests`, MISSING); nothing wires the store before it.
2. **The failure-domain count is inferred, not shown** (limits item 4). It rests on file-store identity (device number and type, or the drive description); two file systems on one physical disk count as two. That the two volumes are independent is attested in the G8 record. Owner: deployment, gate G8.
3. **Scale** (limits items 3, 9 and 19). `list` walks the directory tree of both volumes and sorts it, so `EvidenceVerifier.verify` and any caller that pages `list` cost N/500 + 1 full walks of both volumes (quadratic in the number of objects) and are not usable beyond test sizes (the list optimisation is not implemented; SP-W and P3b2 scale work); `open()` lists every directory of both volumes to sweep temporary files; `repair()` and `scrub()` hold the key set of both volumes in memory; a replaced volume blocks every write until `repair()` has finished; `put` holds a whole object in memory (the port's `byte[]`): about 8 times the object size at its peak when both volumes already hold the key, 3 times for a new key, with up to 64 puts of different keys in flight (limits item 19); a put of a key that both volumes already hold (every journal re-ship and `DurableSeal` retry) writes and forces a full-size temporary file on both volumes, has its link refused and deletes it, only to trigger the directory-sync chain. Unmeasured. Owner: SP-W and the SP-M memory bound; a streaming `repair` and `scrub`, a staging directory for temporaries and a method that only syncs the directories of an existing key are later class changes.
4. **Plaintext until P3c** (limits item 5 and 6). Objects are stored exactly as given until the envelope encryption of P3c, so P-SEALED must not receive production data before P3c and gate G8. On Windows the files carry the access control list they inherit from their directory; only on POSIX systems are they owner-only. Likewise `report_version.body` in the ledger is plain until P3c (P3a notes).
5. **Tamper-evident only after P3c** (limits items 7, 8 and 14). Every file ends in a SHA-256 trailer, so a flipped bit anywhere is found; a deliberate edit that recomputes the trailer, and a shortened or deleted meta, are not detected until the retention rows and the signed manifests of P3c; the header fields are sealed, not authenticated. Retention and legal hold on P-SEALED live in the header and the meta files.
6. **One process owns a volume pair** (limits items 10 and 11). The read-compare-replace of a meta file is atomic only through locks shared inside one JVM, and `open` takes no file lock. A second process over the same two directories (an overlapping rolling restart, a sender not stopped after a failover, an operator tool) silently loses legal-hold and retention-extension updates, and two stores in different containers or hosts over one directory are not told apart by the temporary-file sweep. Advisory file locks are unreliable on network file systems. Owner: P3c (the immutable per-revision meta file is the durable cure; a single-owner enforcement is not built).
7. **Restart gap and lock coupling** (limits item 12). After a restart the bookkeeping of unsynced directories is empty, so a publish whose link succeeds in directories that a crashed earlier attempt created syncs only the directory that holds the link (the refused-link path syncs the whole chain). The directory lock and the 64 meta locks are static and shared by every volume and store in the JVM, so a stalled volume can hold up another; the lock order is the key stripe of the store first, then the meta lock of the volume. Owner: SP-W follow-up; no task owns a change.
8. **The root of a volume, unmounted volumes and the marker** (limits items 13 and 15). The root of a new store must be a new empty directory below the mount point: `lost+found`, `System Volume Information` and `$RECYCLE.BIN` count as content, and two unmarked roots of which either holds any entry are refused (the strict rule is kept; an allow-list is the owner's decision). Two volumes that are not mounted (empty mount-point directories on the system disk) are indistinguishable from two new volumes and open as a new store on the system disk; the production send gate refuses fewer than two failure domains. The marker is a dot file: a restore by copying `vol/*` drops it and the next open refuses; a single dropped marker looks like a replaced disk. Owner: P4 or the deployment design (a `Config` flag for a new store and an operator call to adopt a restored pair).
9. **Manual cures and unrecovered states** (limits item 15). A corrupt copy next to a valid one, of an object or of a meta, is reported by `scrub` and never replaced by `repair`; `put` (for an object) and the retention methods (for a meta) fail closed on it. The cure is manual: move the damaged file aside (outside both volume roots; it stays as evidence), then run `repair()`, which finds the name absent and copies the valid file; then run `scrub()` and expect it empty. Two **divergent** copies (whole, but different in any byte, also in the header alone) are reported by `scrub` as `DIVERGENT`; `put`, `extendRetention` and `setLegalHold` refuse them with `EvidenceCorruptionException`, `repair` picks no side, and `get` serves the payload of the first valid copy with the longest retain-until over both headers and both metas. The cure is manual: keep the copy whose payload hash equals the `object_manifest` row (when the payloads differ; for a header-only difference the payload hashes are equal and the operator keeps the copy with the longer retain-until, the one that `get` serves, because retention is never shortened), move the other aside, then `repair()` and `scrub()`. A `COMPLETE_TEMPORARY` is adopted by renaming only when its final name is absent and otherwise removed after a comparison; a kept temporary whose key was later put again stays reported for ever until an operator removes it, and one unreadable temporary makes the whole `scrub()` throw, which hides every other finding (known, minor). A damaged meta file can never be replaced by the store (`writeMeta` refuses, `repair` skips it, `snapshot()` throws `EvidenceCorruptionException` even when the other volume's meta is valid), so `extendRetention` and `setLegalHold` on that key fail until an operator removes the file (open item F9). Owner: P4 or an operator procedure; no task owns the cure.
10. **A hold release that reached one volume is effective before it is acknowledged** (limits item 16). The hold of two metas of different revisions is the hold of the higher revision, so a partial release is already the hold of every reader, and a `repair` copies it to the other volume. An OR rule across revisions is a design change, not made. Owner: P3c and P4 design.
11. **Windows `durability()`** (limits item 17). `durability()` reports `synchronousAcknowledgement` true although no directory is forced there, so a send-gate decision on Windows rests on the G8 attestation and on SP-W. Whether `durability()` should report false without a directory sync is an open question for the owner.
12. **Temporary-file sweep** (limits item 10): a temporary of a live pid is swept when it was last written more than 2 seconds before this JVM's start instant, so a container JVM that is PID 1 still sweeps its predecessor's debris; where the platform does not report the start of the JVM only pid liveness applies. **Except a complete temporary of an object or a meta whose final name does not hold it**, which is kept and reported by `scrub` as `COMPLETE_TEMPORARY` (items 1 and 9).
13. **Retention and legal hold are not enforced by anything but the store's refusal to shorten.** Nothing deletes an object, so there is no retention enforcement in P3b1 (P4); a deleted file is a `MISSING` for `verify` only if the manifest has the row.
14. **The endpoint-part alphabet (A9).** An endpoint with a part outside `[A-Za-z0-9._-]{1,24}` (the ledger's `EndpointKey` allows up to 128 characters per part) can be leased and queued but is never sealed: `seal` refuses it with an `IllegalArgumentException` naming the field, before any effect, until the owner widens the encoding. Owner: the owner, with the first real endpoint configuration.
15. **No manifest function and no manifest condition in `SendGate.Requirement`.** Keys, the signer, the manifest function, signed manifests, the second manifest location and `manifestMaxAge` are P3c. I1 on P-SEALED is therefore complete for the ledger and evidence-durability conditions only; spec 5.4 and 11.3 require an unreachable or unverifiable manifest to close the gate, and nothing here does. P-SEALED stays test-only, so no production send can pass without it. Owner: P3c (the owner may move the cadence into P3b2).
16. **What `seal` and `verify` check of the intent, and what stays the sender's duty.** Since FI `seal` refuses an intent whose `business_key` or `version_seq` differs from the ledger row of the delivery (an `IllegalArgumentException` before the gate and any effect; a P8 sender must pass the row's identity), and `verify` reports both as `INTENT_MISMATCH` besides the artifact hash, file name, delivery id, key scope and key epoch. `trn`, `action` and `logical_hash` are not in the ledger row and stay the sender's duty (P8).
17. **No crash point may be placed on a fail-closed read.** `beforeFirstByte` and `SendGate` catch every `RuntimeException` while reading the epoch marker, `EvidenceStore.list`, `get` and `durability`, and `LedgerDurability.durability`: an injected crash there would be read as "unreadable" and swallowed. `CrashPoints.onAFailClosedRead` registers the calls and a test pins that no point is one of them.
18. **The commit wait is not bounded by the server** (section 1.8, observed for `statement_timeout`). A unit whose standby is gone after the gate was read blocks until the backend is cancelled or the standby returns, because neither `statement_timeout` nor `lock_timeout` bounds a commit. **The bound is a watchdog that cancels the backend from a second connection** (`pg_cancel_backend` or the driver's cancel request) and reads the resulting `01000` warning as "unknown", which `Unit` does; **a socket timeout alone is not a bound**: the client gives up but the backend goes on waiting in `SyncRepWaitForLSN`, which looks at the cancel and die flags and the postmaster and not at the client connection, and it keeps the row locks of its transaction. Those locks matter: the unit holds the `FOR SHARE` lock of the lease row (the fence) and the delivery row, so a takeover (`acquire`) or a restore declaration (`declareRestoreEpoch`) waits behind a stuck commit until `lock_timeout` (`55P03`); a second seal of the same sealed key behind such a commit waits for the unique key and is cut off by `lock_timeout` (`55P03`) after 5 seconds (not exercised). Owner: P3d and P8 (the watchdog).
19. **The standby gate rests on one standby on one VM.** The job tests one named standby on the same runner as the primary; failover, promotion and a standby under replay lag were not run. With `ANY n (list)` naming more standbys than n, only the standby with the highest received LSN may be promoted (compare `pg_last_wal_receive_lsn` on all of them first); otherwise an acknowledged commit can be lost and I1 fails across the failover. Owner: deployment and the standby-takeover runbook (P9b). The synchronous-implies-standby invariant is not in the `Status` constructor (`SendGateTest` builds `Status(true, 0, ...)` on purpose); the gate itself treats such a status as closed.
20. **`pg_stat_replication` visibility.** Documented, not observed: a role that is not a superuser and not a member of `pg_monitor` or `pg_read_all_stats` sees no streaming standby, so the gate reads zero and stays closed. Owner: deployment (grant it to the ledger role).
21. **Error text of a failed manifest batch.** The `BatchUpdateException` that is the cause of a failed manifest insert carries the SQL with the bound values (key paths and hashes; the `LedgerException` message stays clean). A caller logs `getMessage()` and never the exception with its causes (as the P3a notes say for the ledger).
22. **`Json.writeInstant` in `regpack-model`** still reads `atOffset(UTC).getYear()` and would throw `DateTimeException` for `Instant.MIN`; no caller reaches it any more (the port refuses such instants). Fix when another caller can pass an unchecked instant.
23. **Real-store evidence is CI-only** and the unobserved list is long: PostgreSQL on Windows, a standby under replay lag, the hot path at 50 million records a day, a store of several hundred thousand objects a day, power loss. No PostgreSQL ran on the development machine; the per-test skip counts of the build jobs are not readable without a GitHub sign-in, so that the POSIX-only tests ran (and were not skipped) is **not observed in CI**: the six tests that the `REALFILES` lines cite are platform-neutral and run unguarded on Windows too, and cite no POSIX-only test. The guard against a silent skip of every POSIX twin through a misreported platform is the unguarded `SealedPortabilityTest#directorySyncIsCalledWhereThePlatformCanAndTheLimitsSayWhereNot`; owner-only permissions, `unix:nlink` and the directory forced through a channel are not observed in CI (final review SPEC-3, PSEALED-5).
24. **The step `-DskipITs` is missing in the jobs `ledger-pg` and `ledger-capacity`** (failsafe ignores `-DskipTests`): their integration tests simply run twice because a service container is up; in `ledger-capacity` the install step therefore runs the whole integration suite, so its duration is to be checked at the next dispatch. Deferred by decision; harmless while green.
25. **A test-only process spawn.** The test helper `createLink` runs `cmd /c mklink /J` on Windows when a symbolic link cannot be created (paths inside the temporary directory, no environment read, nothing left behind). Accepted by the controller; the owner may veto it (the alternative is `assumeTrue` on the symbolic link).
26. **The replay barrier holds a lock until the commit returns** (section 1.8). A replay of a manifest call, a decision batch or a report commit holds a share lock on the `restore_epoch` singleton until its commit returns, a stuck standby wait included; it conflicts only with `declareRestoreEpoch`, which waits behind it for up to `lock_timeout` (`55P03`). The ingest redelivery locks the stored batch row instead, which conflicts with nothing. Owner: deployment and P8 (a stuck replay blocks a restore declaration until the backend is cancelled).
27. **A shared content-addressed sealed object keeps the retention of its first put** (SEAL-1). Two deliveries with identical bytes share one sealed object and one manifest row, which names only the first attempt, and a later put of the same bytes keeps the retention of the first. Nothing deletes before P4, so nothing is lost now. Owner: the retention rows or the engine of P3c and P4 must extend the object to the maximum over all deliveries that name it, treating `EvidenceRetentionException` as satisfied.
28. **Epoch markers share the 1,826-day OI-6 retention** (class `epoch`). Nothing deletes before P4, but `EpochMarker.current()` reads the highest marker and answers 0 when there is none, so a marker deleted at expiry would make every sender of a restored epoch fail closed (`EPOCH_MARKER_DIFFERS`) and would erase the record that a restore happened. P4 retention enforcement must therefore exempt `control/epoch/`.
29. **The source-file limb of I1 is covered by nothing before P7a** (SPEC-1). Only the source-acknowledgement limb is covered, by `ToyCrashIT` and `PackToyCrashIT#acknowledgementFollowsIngestCommit` on in-memory ports (and, at the ledger commit, by `PgDurabilityDownIT#aRedeliveryAfterAnUnconfirmedIngestCommitIsNotAcknowledgedEither`, observed at CP-3). No code moves or deletes a source file before the file connectors of P7a; that limb is first proven there on the real stores. An explicit open item (section 4).
30. **Dense hostile input of a large type.** The parser builds a tree of every JSON node before any schema check, so a 64 MiB input under a class (b) key or a `BatchAdmitted` key can still need more than a gigabyte of heap; the per-type 1 MiB ceiling protects the five small types under class (a) keys only (section 1.4). Owner: P3d, when the class (b) shipper reads, and P7a (`BatchAdmitted`): a parser node budget or a class (b) key that names its type.
31. **Pooled session settings and `Migrator`.** `Migrator` commits without the commit-warning rule (not an acknowledgement path). `reset_val` of `synchronous_commit`, which `PgLedgerDurability` reads when the setting is not forced, reflects the settings of the pool's connections (only the non-production capacity variant); a pooled `DataSource` that a deployment passes to `PgLedgerStore` must pass `getWarnings` and `clearWarnings` through to the real connection, or the commit-warning rule reads nothing. Owner: deployment.

## 5. Hand-offs

### P3b2 (P-WORM, the S3 client)

- Bind the shared suites to the P-WORM adapter: `EvidenceStoreContract`, `JournalContract` and `SealScenarioContract`, and run `verify` on it (the same two exit clauses for both evidence profiles). A put of an existing key is decided without conditional writes (read, compare, a version-order check after the PUT) and the race that remains is stated.
- `SendGate.Requirement`: the durability-configuration check for S3 makes `EvidenceStore.durability()` report what the store configuration shows; `Requirement.production()` stays `(true, true, 2)`.
- Entry target `P-WORM-non-aws` (needs SP-O; MISSING today): no non-AWS store is called P-WORM or compliance mode in production before it.
- The S3 pointer of the plan: defaults Zenko CloudServer as the CI service, a hand-written SigV4 client in a JDK-only module, no copyleft image; the facts about the candidates are recollection until the first probe of P3b2; OI-3 and OI-5 are asked when P3b2 is scheduled.

### P3c

- The manifest function: a digest over the ledger's write-time hashes and the listing, objects of class `SIGNED_MANIFEST`, the cadence, `manifestMaxAge` as a condition of `SendGate.Requirement`, the signed manifest and the second manifest location (spec 5.4, 11.3, 11.6). Manifest orphan lines carry `ledger_ref` NONE, the object hash, the size and the first-seen time, which needs a clock and a store of first sightings; a changed orphan changes the digest.
- `PgClock`, the `retention` rows, keys and envelope encryption (P-SEALED takes production data only after it), the tamper evidence of the header fields of P-SEALED files and of meta files, the immutable per-revision meta file and the enforcement of a single owner of a volume pair.
- **SEAL-1:** a content-addressed sealed object is shared by deliveries with identical bytes and keeps the retention of its first put (the manifest row names only the first attempt); the retention rows or the engine must extend the object to the maximum over all deliveries that name it, treating `EvidenceRetentionException` as satisfied (section 3, item 27). Epoch markers (`control/epoch/`) must be exempt from retention enforcement (item 28).

### P3d

- `journal_seq` with its table and counter, the class (b) shipper with `PayloadSource` and the continuity check (spec 11.5 A.1), the `delivery_event` unit and step 5 on PostgreSQL, the state machine, WITHDRAWN.
- `RecoveryDecision` ordinals: class (a) ordinals are supplied by the caller (D-E7), the counter belongs to the subject's row; a `RecoveryDecision` has its own key (subject the delivery), carries `attempt_id`, `artifact_sha256` and `intent_restore_epoch`, and the intent key is derived from (`attempt_id`, `intent_restore_epoch`, endpoint scope).
- A manifest entry's `sha256` is the hash of the object bytes as stored, so `JournalWriter` must return the stored hash and size for `ALREADY_PRESENT_SAME_PAYLOAD` (today it returns neither, and `payload_sha256` is not the manifest hash).
- The open `APPROVAL` control-scope question and the `OperatorAction` kinds (section 4).
- A client-side bound on a commit (section 3, item 18): a **watchdog that cancels the backend from a second connection** and reads the `01000` warning as "unknown"; a socket timeout alone is not a bound. The 55P03 expectation for a second seal, a takeover or a restore declaration behind a stuck commit.
- **The replay-barrier rules** (section 1.8): the success of a redelivery (ingest, manifest, decisions, reports) is as durable as the first call's only through the barrier, so the pipeline must not swallow the exception of an unconfirmed commit (`MicroBatchPipeline.process` propagates it today); a decide path that skips `commitDecisions` entirely would not wait (its read-only decisions are readings of the primary and no confirmation); callers of `transition`, `markCommitIssued` and `beginSending` must not read `STATE_MISMATCH` or a `false` result as "already done"; an operator who gets the `IllegalArgumentException` of `declareRestoreEpoch` for an epoch already on the primary must treat it as "maybe already declared, verify on the standby". A typed exception for an unknown commit outcome (a subclass of `LedgerException`) would help the retry logic; today it is a message prefix.
- The dense-input node budget for class (b) keys (section 3, item 30).
- Any unit that composes `PgDeliveries.beginSending(Connection, ...)` or `PgManifest.record` with other writes: the conditions of section 1.6 (last statement of a short unit, READ COMMITTED, keys sorted inside; roll back or take a savepoint).

### P4

- `attempt_id` resume above the maximum found in the evidence tier (`maxIntentAttemptId`; spec 11.2): the sequence has gaps and is not rewound, and after a restore it may be behind the tier; an intent object stored under an id with other bytes fails the seal closed. `decision_id_seq` resumes above the maximum of the stored ids.
