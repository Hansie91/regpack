What the S3-compatible CI service really does, read from the first CI run that executed the probe. Written by the controller; every statement about the service below is an observation of that one run (a probe result), not a claim about AWS S3 or about any other version of the image.

- The text below is the `probe-results` warning annotation of that job, read without sign-in from the check-run annotations. The probe reduces every observed value to the characters `A-Za-z0-9 ._:=,;/+-` (anything else is printed `?`) and cuts it at 120 characters (`ProbeReport.reduce`). No item was cut: counted from the table below, the longest observed text is that of P8 with 114 characters and the next is P15 with 111, and P7 has 108. The reduction shows in P8: its page sizes are a list, and the two `?` of `?1000, 101?` stand for the brackets of `[1000, 101]` (the comma and the space are in the kept set). `mkFirst` at the end of P7 is a flag, not a cut value: the probe appends it only when the first entry of the key's version list, read after the DELETE, was the delete marker and was the latest entry of the key (`S3ServiceProbeIT.p7`).

## What this does not show

- Whether any of this holds for AWS S3 or another store, or for another version of the image (SP-O is not run).
- Any behaviour outside the one run: the probe ran once, with one writer set per item, in one CI job.
- What a bucket without object lock or without versioning answers to the two configuration reads of `durability()`. P1 probed a bucket created with the lock header only. The refusal of such a bucket is shown by the fake-bound methods of `WormEvidenceStoreTest` (`durabilityIsRefusedWhenObjectLockIsOff`, `durabilityIsRefusedWhenVersioningIsNotEnabled`) and by no test on the service; the 404 `ObjectLockConfigurationNotFoundError` that `S3Client.objectLockEnabled` and the fake use for a plain bucket is a recollection about AWS S3 (the fake carries no `not probed` mark on it).
- That the lock mode and date come back on GET. P2 probed HEAD; the adapter reads them from the GET of a version (`WormEvidenceStore.retained`). See the CP-2 observation below.

## Later observation (CP-2)

The behaviour contract `S3BehaviourContract`, bound to the service as `WormServiceBehaviourIT`, ran 13 tests at CP-2 ([run 40141048211](https://github.com/Hansie91/regpack/actions/runs/40141048211), head `6b21151`) with failed 0, errors 0, skipped 0. It includes a case that the probe text did not record: two versions of one key straddling a page of 7 in a version listing (added in T7 because P7 and P8 do not say whether a page can end inside a key); that case was observed passing against the service at CP-2 for the first time (contract method `listVersionsFollowsTheMarkersAndKeyMarker`, whose pages were asserted to be exactly 7, 7, 7 and 5 entries).

Three more assertions of the contract go beyond the text of the probe items (the T7 report lists them), and they too first met the service at CP-2 and passed there, as part of the 13 passing tests: a second `PutObjectTagging` on a locked version leaves the second value under the same tag name (`tagsOfALockedVersionCanBeChangedAndKeepTheirValue`; both writes use one tag name, so it does not tell a replacement from a merge); `HEAD` after a `PutObjectRetention` returns a lock date that `Instant.parse` reads as the date sent (`retentionCanBeExtendedButNotShortenedWithoutBypass`; P2 printed the date only after a PUT with lock headers, and P5 printed statuses and no date, so the format after `PutObjectRetention` was not in the printed text); and `HEAD` of a version by its id carries `x-amz-version-id` (`theRetainUntilResolutionIsWholeSeconds`; P2 sent `HEAD` without a version id). The adapter's reading of the lock mode and date from the `GET` of a version (not `HEAD`, the only form P2 probed) is not asserted by a contract method; the CP-2 pass of `WormEvidenceStoreContractIT` is its indirect evidence, because `get` throws `EvidenceCorruptionException` when the lock headers are absent. The comment in `FakeS3Server` that labels this behaviour `probe: P2` is test code and was not changed in this correction.

After the final review, the commit `55ec3c4` (FA2) added to both marker methods (`aDeleteWithoutAVersionAddsAMarkerEvenUnderLock`, `aKeyHiddenByAMarkerStaysInTheVersionListing`) the assertion that the marker is the first and the latest entry of the key's list, the property that `mkFirst` of P7 records. That assertion ran on the fake and, at CP-3 (run 40157767799, head `49a55fa`, green), on the service in `WormServiceBehaviourIT` (run=13, failed 0, errors 0, skipped 0).

## Deviations from the plan that the read-out causes

None so far. P12 is a difference between this service and the AWS behaviour the plan recollected, not a contradiction of a decision.
