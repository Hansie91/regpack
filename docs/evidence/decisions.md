**Correction of a statement of the controller's brief for FH.** The brief said that a transaction that only assigns an xid (`SELECT pg_current_xact_id()`) waits for the standby. It does **not**: `RecordTransactionCommit` computes `wrote_xlog` (the transaction has written WAL) before it writes its own commit record, and `SyncRepWaitForLSN` runs only if `wrote_xlog` and the commit is marked; assigning an xid writes no WAL, so a unit that only assigns one commits asynchronously and a retry would still be acknowledged at once. The barrier is therefore a **row lock**, which is WAL-logged (`XLOG_HEAP_LOCK`) and assigns the xid: `FOR SHARE OF b` on the stored `ingest_batch` row for the ingest redelivery, and `SELECT 1 FROM restore_epoch WHERE singleton FOR SHARE` (`Unit.durabilityBarrier`) for the manifest, decision and report replays. Because the commit record of the retry comes later in the log than the commit of the first attempt, a standby that confirms it has the first attempt too, and when the wait is cancelled the retry warns and ends in the same exception as the first call. The lock on the `restore_epoch` singleton is held until the commit returns, including a stuck standby wait, and conflicts only with `declareRestoreEpoch`, which then waits up to `lock_timeout` (`55P03`); it is placed only in units that hold no lease or delivery row (the singleton is first in the lock order of `PgLeases`); the ingest uses the batch row, which conflicts with nothing. Server assumptions and the implementer's confidence (FH report): a row lock writes WAL, assigns an xid and so waits in `SyncRep` and warns on cancel, 90 to 95 percent (the converse claim, that `pg_current_xact_id` alone would not wait, 80 to 85 percent from the source, not verified on a server); `FOR SHARE OF b` on a join is valid syntax, 99; the ledger role holds `UPDATE` on `ingest_batch` and `restore_epoch`, about 97; the harness sees the redelivery backend in `SyncRep` and cancels it after at least 6 s, about 90; the locally committed batch row is visible and lockable by the retry, 97; pgjdbc returns per-statement counts 1 and 0 for `ON CONFLICT DO NOTHING`, about 90 (if it returned `SUCCESS_NO_INFO` the barrier is simply always added, which is safe). **If a row lock does not make the commit wait, the new test fails at CP-3 and nothing else would show it.**
