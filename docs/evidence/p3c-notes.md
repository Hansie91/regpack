### 1.2 The envelope (D-K1)

Version 1 (`EnvelopeTest`, V3 and V4), lengths big-endian: the bytes `RPEN`, the version byte, the kind (`01` object, `02` body), the KEK id length (1 to 100), the KEK id (`[A-Za-z0-9._-]`), the wrapped-key length (2 bytes, 1 to 1,024), the wrapped data key, a 12-byte nonce, the ciphertext and a 16-byte tag. The cipher is AES-256-GCM through the JDK (`AesGcm` is the one class of `regpack-ports` that uses a JCA cipher); a third-party library is not used: the diff of the POM files from `38f8a18` to this head is the one test-scope dependency of `regpack-postgres` on `regpack-inmemory` (AP-5; `git diff 38f8a18 HEAD --stat -- '*pom.xml'`), and `ThirdPartyBoundaryTest` and the enforcer ran in the full build of T14. The authenticated data is the bytes before the nonce, then a 4-byte length and the context, so a swapped KEK id or wrapped key, or an envelope moved to another context, fails the tag. The header is readable without a key (`Envelope.header`); `Envelope.isEnvelope` is true exactly when `header` would succeed (`EnvelopeTest#isEnvelopeAgreesWithHeaderOnEveryMutationAndTruncation`) and does not authenticate (a well-formed header over random bytes passes). The fixed overhead of an envelope is the header, 12 bytes of nonce and 16 bytes of tag; the golden object envelope (V3) has a 77-byte header for an 8-character KEK id and a 60-byte wrapped key, and 110 bytes in all for a 5-byte plaintext. The vectors V1 to V9 of the plan are pinned by `AesGcmTest`, `EnvelopeTest`, `CounterEntropyTest`, `ObjectCipherTest`, `SubjectHasherTest` and `InMemoryKmsContractTest`. `EnvelopeTest#everySingleByteChangeOfTheGoldenEnvelopeIsRefused` changes each byte of the golden envelope in turn and expects a refusal for each, and `EncryptingEvidenceStoreTest#everySingleByteChangeOfAStoredEnvelopeIsACorruptionAlarmAndNeverPlaintext` does the same through the decorator.

### 1.3 Keys, draws and wraps (D-K2, D-K5)

- **Hierarchy (A3, Departure 2).** One KEK per UTC year of the write instant, named `kek-<year>` (`KekSelector.perUtcYear`; `KekSelector.single` exists for the one-KEK alternative that the owner did not choose); one random 256-bit data key per evidence object (`ObjectCipher`); one per UTC day and KEK for report bodies (`BodyCipher`), rotated also after `MAX_SEALS_PER_KEY` = 2^30 seals (the NIST limit of 2^32 random 96-bit nonces under one key is [R: SP 800-38D 8.3]). The wrapped key travels inside the envelope, so the tier is readable with the KEKs alone and the schema has no key table (V003 holds exactly the six statements of the approved document: `SchemaDocMatchesMigrationsTest#v003HoldsExactlyTheStatementsOfTheProposedTextOfItsDocument`).
- **Order of draws.** `ObjectCipher.seal` reads the clock once, selects the KEK, draws the 32-byte data key and then the 12-byte nonce from `Entropy` (pinned by V6), wraps the key, seals and zeroes the data key array in a `finally`.
- **Wrap AAD.** `regpack/dek/v1|<OBJECT or BODY>|<kek id>|<key path, or body>` (V9). The context of an object is its key path; the context of a body is `regpack/body/v1|<regime>|<event identity>|<leg>|<logical hash hex>` (`BodyContext`, V4).
- **Failure mapping (KF5).** The KMS port reports an unknown KEK and a tampered wrapped key alike (`IllegalArgumentException`), so `open` reports both as `Envelope.AuthenticationException`, and `EncryptingEvidenceStore` as `EvidenceCorruptionException`. A KEK id in the header that was changed to name a key which the key service holds but this identity may not use as a KEK is answered with access denied and read as an outage (`EvidenceUnavailableException`), not as a corruption alarm, as a real denial would be (D-K2); a changed id that names no key is a corruption alarm (`EncryptingEvidenceStoreTest#aHeaderThatNamesAKeyThisIdentityCannotUseReadsAsAnOutageAndOneThatNamesNoKeyAsCorruption`). On seal, any `RuntimeException` of `KekSelector.kekAt` or `Kms.wrap` becomes `KeyUnavailableException` (a fixed text, no cause), which the decorator turns into `EvidenceUnavailableException`; this includes the next year's KEK not yet created, which stops sealing fail-closed (`ObjectCipherTest`, `BodyCipherTest`, `EncryptingEvidenceStoreTest#aKmsFailureOnPutOrGetIsAnEvidenceOutageAndStoresNothing`). `KmsKeyDestroyedException` on `unwrap` becomes `DataShreddedException`; on seal a destroyed KEK is a `KeyUnavailableException`. A `RuntimeException` of `Entropy` or `Clock` passes through unchanged. No message holds a key, a KEK id or a path (`EncryptingEvidenceStoreTest#noMessageHoldsAKeyAKekIdOrAPath`, `EnvelopeTest`, `KmsValuesTest`).
- **Subject hash (D-K5).** `SubjectHasher` is HMAC-SHA-256 under an `INDEX_HMAC` key through `Kms.hmac` over `regpack/subject/v1`, a NUL byte, the kind, a NUL byte and the NFC form of the value in UTF-8 (V8); it refuses a key of another purpose (`SubjectHasherTest#aTrnHmacKeyIsRefused`) and an unpaired surrogate. The caller canonicalises the identifier (trim, upper case with `Locale.ROOT`, strip separators) before it hashes; the slice does not do so, because `SubjectHasher` has no caller in main code.

### 1.4 The decorator (D-K3)

`EncryptingEvidenceStore` sits above the store port and below `DurableSeal`: the manifest rows and the intent hash stay hashes of the plaintext handed in, and the stored bytes are the envelope. The default policy encrypts the namespaces `sealed`, `landing` and `enrichment`; `journal` and `control` pass through (A5, owner answer OI-5; no check shows that the journal objects hold no personal data, and P3d and P9b keep personal data out of them). A put of a present key opens the stored envelope and, for equal plaintext, puts the stored envelope bytes again (which completes a missing second P-SEALED copy) and answers `ALREADY_PRESENT_IDENTICAL`; other plaintext is `EvidenceIntegrityException`. `get` opens and returns the plaintext with its SHA-256; bytes under an encrypted key that are not an envelope of that key are an `EvidenceCorruptionException`, without a fallback to the stored bytes (`EncryptingEvidenceStoreTest`; the counts are in section 6.1). One wrap per created object and one unwrap per repeated put and per read (`#theKeyServiceIsCalledOncePerOperation`); a `journal/` or `control/` object does not touch the key service (`#thePlainClassesNeedNoKeyServiceAtAll`). The binding really encrypts what the shared suites store (`EncryptedInMemoryContractTest#theBindingReallyEncryptsWhatTheSuitesStore`, `EncryptedSealedContractTest`, the twins of section 6.1); without that test a policy that encrypts nothing would leave the shared suites green. That test stores one key, so the five bindings of T13 (`EncryptedWormContractTest`, `WormEncryptedContractIT`, `WormEncryptedSealScenariosTest`, `WormEncryptedSealScenariosIT` and `PgEncryptedSealScenarioIT`) also check after every method, in an `@AfterEach`, that all stored objects are envelopes (the two own methods of `AbstractWormSealTest`, which build their sealer over the raw store on purpose, are left out); scratch mutants of the policy (skipping a namespace, `control/` or `journal/`, landing only, no key over 200 characters, the default policy) turn these checks red. The four earlier bindings over the in-memory store and P-SEALED (`EncryptedInMemoryContractTest`, `EncryptedSealedContractTest`, `SealScenariosEncryptedInMemoryTest`, `SealScenariosEncryptedOnSealedTest`) have the same `@AfterEach` since the final review (T15-1), so each of the nine encrypted bindings now has an `@AfterEach` that checks that every object the method stored is an envelope; the four read the inner store, or the two volumes, and `EncryptedSealedContractTest` skips a key whose raw read is the corruption alarm of P-SEALED (no method damages both copies today, so the skip is a guard). The same scratch mutants of `EncryptedFixtures.everyKey()` turn the four classes red (failures: skipping the namespace `a` 8, `control` 8, `journal` 72, `journal` and `control` 72, the default policy 94, `landing` only 94, no key over 200 characters 2); on the tests of `8258f24` six of the seven leave the 141 tests green. The shared suites and the seal scenarios run through a decorator that encrypts every key (`EncryptedFixtures.everyKey`), `journal/` and `control/` included; the production policy that leaves them plain is shown by `EncryptingEvidenceStoreTest#aKeyOutsideThePolicyPassesThroughUnencrypted` and `#thePlainClassesNeedNoKeyServiceAtAll` at unit level and by the verify twin `aTierWithTheProductionPolicyKeepsTheJournalPlainAndStaysCleanAfterTheKekIsDestroyed` on P-WORM (`WormEncryptedVerifyTest` on the fake, `WormEncryptedVerifyIT` on the service).

### 1.5 Retention rows, the engine, the seal hook and the verifier (D-K4, A8)

- **Rows.** One row per (artifact, regime, anchor event); `retain_until` is extend-only (`GREATEST` in `PgRetention`, the trigger `retention_extend_only` in V003, the later date in `InMemoryLedgerStore`) and may be NULL for an anchor not yet known; one `legal_hold` flag per artifact, which a new row of a held artifact inherits. Keys under `control/` (epoch markers) get no row from the engine and are left out of the expiry list (`RetentionLedgerContract#expiredRetentionNeverListsControlKeys`, `RetentionEngineTest`). The class names are `journal`, `sealed`, `epoch`, `landing` and `enrichment`; the 1,826-day period is a placeholder for tests: it appears in the contracts of `regpack-testkit` and in tests, and a grep of `regpack-*/src/main` for `1826` finds it nowhere else. It can be one day short of five calendar years, and the policy of gate G8 must replace it before any retention is enforced.
- **Engine and hook.** `RetentionEngine` records the claim and then extends the stored object to the latest date of the rows of the artifact, taking `EvidenceRetentionException` as satisfied. `DurableSeal` (six-argument constructor) calls the `RetentionRegistrar` after the sealed put and before the intent put, passing the `Retention` the put used, so a shared sealed object (identical bytes) is extended by each later seal (SEAL-1: `SealScenarioContract#theSameBytesSealedLaterExtendTheSharedObjectAndKeepOneRow`, with the mutant `ForgetsSharedRetentionScenarioTest`). A registrar failure before the SENDING commit fails the seal closed and leaves the delivery queued; a row written for a seal that does not commit over-retains.
- **Verifier.** `RetentionVerifier` compares each row with the store and reports `RETAIN_UNTIL_SHORTER`, `HOLD_MISSING` and `HOLD_NOT_RECORDED`, at most once per artifact and kind. It skips an absent object and a shredded one, and an outage or an alarm of the store aborts the run. `EvidenceVerifier` does not call it (section 3).
- **PostgreSQL (V003).** Two tables (`retention`, `subject_index`), two indexes, the guard function and the trigger: six statements. The text columns that the reads order or compare carry the collation `"C"`, and the two keyset comparisons name it on the bound text as well (`PgRetentionTest#theStatementsHaveThePinnedShapes`, `PgSubjectIndexTest#theBoundOfTheRowComparisonNamesTheCollationOfTheColumn`). A call that records claims or sets a hold takes one transaction-level advisory lock per distinct artifact, in key order, before it writes. The advisory lock purposes in use are 1 (`Migrator`), 2 (partition creation in `PgDecisions`), 3 (ingest source in `PgIngest`) and 4 (retention artifact in `PgRetention`); the lock text of purpose 4 is the schema name, a colon and the artifact path. Convention 12 of the P3a plan (unedited) lists purposes 1 to 3. Another writer of retention rows takes the purpose-4 lock first (hand-off P4-4).

### 1.6 The data-subject index (A9, A10, A12)

`SubjectIndexLedger` stores `(subject hash, reference kind, reference)` rows: keyed hashes and references, deleted with the artifact by `removeSubjectRefs`. The table has five columns, a 32-byte hash among them (`PgSubjectIndexTest#theTextsNameTheObjectsThatV003Creates` names them), so a plaintext identifier has no column, and the index is not encrypted at rest (D4 of the schema document). Reference kinds are REPORT_VERSION (code 1) and EVIDENCE_OBJECT (code 2); references are ordered by kind and then by Unicode code point, which is the byte order of UTF-8 and the order of `COLLATE "C"` in a UTF8 database (`SubjectIndexLedgerContract#refsBeyondTheKeyAlphabetAreOrderedByCodePointNotByUtf16Unit`). A call that inserts or deletes nothing ends with the durability barrier (KF22); `PgSubjectIndexIT` shows that with a lock probe on the `restore_epoch` row, and `PgRetention` takes no barrier because a claim already in the table is written again [R] (the statement order is shown by `PgRetentionTest#recordingAnExistingClaimStillWrites`; that the update to an unchanged value writes a row version is not observed). `indexSubjects` appears in main code in the port, the two adapters and the contract, and no writer calls it: the writers (P5, P7a, P3d) and the access-request path do not exist.

### 1.9 The in-memory KMS and destruction

`InMemoryKms.destroy(KeyRef)` replaces a KEK by a tombstone: `wrap`, `unwrap`, `sign`, `verify` and `hmac` of that id report `KmsKeyDestroyedException`, `createKek` refuses the id, destroying again is a no-op, and destroying what is not a KEK is `IllegalArgumentException` (`"unknown KEK"` for an unknown id or an id that names a key that is not a KEK, `"only an ENVELOPE_KEK can be destroyed"` for a `KeyRef` with another purpose; the tests pin the type, and that the message does not hold the id, not the full text: `InMemoryKmsContractTest#destroyIsIdempotentAndRefusesWhatIsNotAKek`, `KmsContract`). It is an administrative method of the fake and not a port method (A7); it does not model a real pending window, cancellation or replicas.

## 2. Shredding and the granularity of a cohort

What is shown is an effect on the in-memory KMS: after `InMemoryKms.destroy` of a KEK, an object whose envelope names that KEK cannot be decrypted through `EncryptingEvidenceStore` (`DataShreddedException`; `EncryptingEvidenceStoreTest#aShreddedObjectIsDataShreddedOnGetAndPutAndStaysListed`), objects under another KEK stay readable (`#aShreddedKekDoesNotTouchTheObjectsOfAnotherKek`), and `EvidenceVerifier` counts the object in `objectsShredded` and does not judge its hash, so the run stays clean (`EvidenceVerifierTest#aShreddedObjectIsCountedAndVerifyStaysClean`; cited in `docs/traceability.md` for I10 with the store label `INMEMORY`). The same on P-WORM is written for the real service in `WormEncryptedVerifyIT#verifyStaysCleanAfterTheKekOfAnObjectIsDestroyed` and is NOT RUN LOCALLY (section 6.2). The statements of this section are about the fake: the one `Kms` implementation in main code is `InMemoryKms` (a grep for `implements Kms` in `regpack-*/src/main` finds its inner class and no other), and the pending window, replicas, backups and escrowed shares of a real KMS are not modelled (P9b).

**Cohort granularity (Departure 2, owner answer OI-3).** The unit of destruction is the KEK of a UTC year, not an object, because there are no key tables (D1). An object stays readable until its KEK is destroyed, and the rule handed to P4 is to destroy the KEK of a year when the last retention of its cohort has ended and not before: an EMIR, SFTR or CFTC object with an open anchor, a SEAL-1 extension of a shared object or a legal hold keeps the whole year readable, and an enrichment snapshot does not leave readability at the end of the retention of the report that cites it unless that ends the cohort. Re-wrapping a stored object into a later cohort is not possible: the stores are write-once without delete, and the KEK id and the wrapped key are part of the authenticated data, so a different wrap is a different object. Rotating key material is a KMS act under the same KEK id (P9b). The expiry job that decides which cohort is destroyable and destroys it is P4 (owner answer OI-10).

**Two more consequences, both pinned by a test.** (1) A byte-identical re-seal after the KEK of the object's cohort was destroyed throws `DataShreddedException` out of `DurableSeal.seal` and not a `SealStatus` (`EncryptingEvidenceStoreTest#aResealOfByteIdenticalBytesAfterTheirCohortWasDestroyedIsADataShreddedExceptionAndNotAStatus`; the owner answered OQ-2 "Accept and hand off"; hand-off P4-2). (2) On P-WORM a lost cross-process race keeps the loser's upload as an extra locked version; with the decorator that version is another envelope of the same plaintext wrapped under the KEK of the loser's clock. After the winner's KEK is destroyed on the in-memory KMS the extra version still opens with the other KEK (`WormEncryptedVersionsTest#aLostCrossProcessRaceLeavesTheLosersEnvelopeAsAnExtraVersion`, on the fake only). That both writers of such a race are told `CREATED` is shown on the fake only and rests on the rank of concurrent PUTs, which the service decides (P13 of the probe: one observation); the extra locked version itself rests on the behaviour of the raw store shown on the service by `WormVersionsIT` (P7 and P17 of the probe), and `WormEncryptedVersionsTest` has no IT twin. P4's cohort rule must count extra versions (P4-2).

## 3. What `verify` can and cannot tell

`verify` (`EvidenceVerifier`) reports a shredded object as counted and clean; it cannot tell destruction at the end of a retention from destruction before it, and it cannot tell a destroyed KEK from a header rewritten to name a destroyed KEK (the object reads as shredded in both cases); a header rewritten to name another key can read as shredded, as an outage or as corruption, depending on the id chosen (`EncryptingEvidenceStoreTest#aHeaderThatNamesAKeyThisIdentityCannotUseReadsAsAnOutageAndOneThatNamesNoKeyAsCorruption`); the tamper evidence of P-SEALED headers is P3c2. A wrong manifest row of a shredded object is not found, because its hash is not judged (`EvidenceVerifierTest#aWrongRowOfAShreddedObjectIsNotFoundAndAnOutageOfTheKeyServiceStillAbortsTheRun`); a plain object under an encrypted key is HASH_MISMATCH (store integrity) and is not counted as shredded (`#aPlainObjectUnderAnEncryptedKeyIsStoreIntegrityAndNeverShredded`). `RetentionVerifier` is not called by `verify` (a grep of `regpack-*/src/main` finds it in its own file and in three Javadoc lines of `RetentionEngine` only), sees the objects that have a row (`RetentionVerifierTest`), skips a shredded object and stops at a damaged object instead of reporting it; a KEK destroyed before the end of a row's retention is therefore invisible to the retention check (hand-off P3c2-1, owner question OQ-4). Rows and the index are ledger-only state: regime and anchor are not recoverable from the tier, so the restore gap replay has to re-create them from the `DeliveryIntent` and the store's retention (P4); until it does, an object without a row is not detected.

## 4. The signer and the plaintext hashes (A13, for P3c2)

For the encrypted classes the store holds the envelope while `object_manifest` holds the hash and size of the plaintext (D-K3). The signer of P3c2 has no KEK, so it cannot compare those rows with the bytes it lists. P3c2 chooses between (i) recording the hash and size of the stored bytes as well (nullable columns in V004; the seal takes them from the inner put), which also keeps a shredded object hash-checkable, and (ii) a signer that checks presence and class, so that the integrity of encrypted objects rests on the AEAD tag checked by `verify` with the KEKs. The default is (i). This is not built.

## 5. Limits

Each limit says who owns it.

1. **Whole objects in memory.** `ObjectCipher`, `BodyCipher` and `AesGcm` take and return `byte[]`; a put holds the plaintext and the envelope, a get holds both. The heap use of the largest envelope was not measured. Owner: the wiring plan (sizes of the evidence classes).
2. **A KMS call per object read and per body read.** `open` asks the KMS to unwrap on each call (there is no read cache; `EncryptingEvidenceStoreTest#theKeyServiceIsCalledOncePerOperation`), a repeated put of a present key reads and so unwraps, and `RetentionVerifier` reads each object whole. The plan's volume model (100,000 sealed files, 10,000 landing objects and 30,000 enrichment responses a day, `docs/ledger/schema-design-p3c.md`) gives 140,000 encrypted objects a day and so 140,000 wraps; the model's figures are the document's and no call rate was measured. Owner: P9b (real KMS call rates), the wiring plan.
3. **Residency of the key of the sealing instance.** A `BodyCipher` holds the current generation key in memory until its UTC day, KEK or seal limit ends and zeroes it at the next seal after that (D8 in [p3c-decisions.md](p3c-decisions.md)); a writer that stops sealing keeps the last key until the process ends, and a process that sealed today can still seal with today's key if the KEK is destroyed in the middle of the day. There is no `close()`. Owner: the writers (P3d, P5, P7a).
4. **No rotation and no re-wrap.** The stores are write-once and the wrap is in the authenticated data (section 2). Owner: P9b for key material under one KEK id.
5. **Zeroing is best effort.** The classes zero the arrays they hold (the drawn data key, the unwrapped key); the copies inside the JCA, `SecretKeySpec`, the `Normalizer` strings and the heap are out of reach, and the opened plaintext and the hash buffers are not zeroed. The records do not rely on it (D-K2).
6. **KMS-side destruction is not shown.** The effect of a destroyed KEK is shown on the fake only (section 2). A real adapter must answer a destroyed or pending-deletion KEK with `KmsKeyDestroyedException` and not as unknown, otherwise `verify` reports a shredded object as corrupt (KF5); a real KMS usually answers "not found" [R]. A restore into a KMS without the escrowed KEKs reads as corruption. The next year's KEK must exist before 1 January UTC or sealing stops fail-closed. Owner: P9b.
7. **The 1,826-day placeholder** (section 1.5; owner answer OI-6; Legal replaces it at G8). The expiry job must not destroy on it. Open anchors are stored through the contract (a NULL date, `RetentionLedgerContract#anOpenAnchorTakesAValueAndNeverBecomesOpenAgain`), and a grep of `regpack-*/src/main` for `TERMINATION` finds the enum and a Javadoc line (`RetentionLedger`), the codes (`Codes`), a comment of `V003__retention_and_subject_index.sql`, a Javadoc line of `RetentionEngine` and the test support `RetentionLedgerContract` in `regpack-testkit` (17 lines); no production code writes such a claim; until a maintenance job writes the row, G8 must not enable compliance mode for a class with an open anchor. Owner: P4 and P8.
8. **The construction of `SecureEntropy`** (section 1.8): one process-wide `SecureRandom`, the platform default algorithm and provider, no seeding. On Windows 11 with JDK 25.0.4.1 the default is DRBG of the provider SUN (printed by a scratch program that builds a `SecureRandom` and prints `getAlgorithm()` and `getProvider()`, not committed). The default is chosen in `sun.security.provider.SunEntries` (read in the `src.zip` of this JDK): NativePRNG when that class is available and the seed source (the system property `java.security.egd`, else the security property `securerandom.source`) is `file:/dev/random` or `file:/dev/urandom`, otherwise DRBG; that NativePRNG is available on Linux is [R], because the NativePRNG source in this Windows `src.zip` is the stub that answers false, and nothing was run on Linux. The statistical quality is not tested.
9. **A byte-identical re-seal after shredding is an exception** (section 2). Owner: P4 and P8.
10. **A lost cross-process race on P-WORM leaves an extra locked version**, and with per-year KEKs a race across 1 January UTC leaves a version under the other year's KEK, so the destruction of the winner's KEK does not remove it from reach; within one process the stripe lock prevents the race. That both writers are told `CREATED` is shown on the fake only and rests on P13 (the rank of concurrent PUTs is the service's); the extra locked version rests on the behaviour of the raw store shown by `WormVersionsIT` (P7, P17), and `WormEncryptedVersionsTest` is fake-only. P4's cohort rule must count extra versions (P4-2).
11. **The media type, the retention class and the retention that `get` returns are unauthenticated inner-store metadata.** The envelope authenticates the plaintext, the key path and the wrapped key; it does not cover those three values, which the decorator takes from the inner object (a note in the class Javadoc of `EncryptingEvidenceStore`).
12. **A concurrent `extendRetention` of one key from two processes can fail the later one** with `EvidenceUnavailableException`: the service refuses a shortening that a stale read allowed [R; modelled on the fake, not observed on the service]. The retry succeeds and no date is lost. The seal path on P-WORM also pays one extra `extendRetention` per seal (the owner accepted this as OQ-1 option 1; the measurement could not be taken at CP-2 as the job stands, section 6.2). Owner question OQ-3 (decide after CP-2).
13. **The decorator is not enforced.** The raw store stays a public object behind it; an object written there is a corruption alarm on read and HASH_MISMATCH in `verify` (`EvidenceVerifierTest#aPlainObjectUnderAnEncryptedKeyIsStoreIntegrityAndNeverShredded`). The wiring has to give each reader and writer of the encrypted namespaces a store built with `EncryptingEvidenceStore.withDefaultPolicy`, and an evidence key under an encrypted namespace must not hold a natural-person identifier (P5 and P7a key small or low-entropy landing and enrichment objects by a surrogate id). Accepted residue after shredding: key paths, the plaintext SHA-256 in keys, ledger and manifest rows, `logical_hash`, TRNs, retention rows and envelope headers; a plaintext hash lets a holder of a candidate plaintext confirm it, which is acceptable only for objects too large or too varied to guess (the DPO's view was asked as OI-5 and not given). Owner: the wiring plan, P5, P7a.
14. **The advisory lock table.** The artifact lock holds one entry of the server's shared lock table per distinct artifact until the commit. The nominal capacity is 64 times 100 entries by default [R]; measured on the local PostgreSQL 18.6 with the defaults, a call of 14,250 distinct artifacts succeeded and one of 14,600 failed with SQLSTATE 53200 (recorded in the Javadoc of `PgRetention`, D33 (3) of the decisions record), so the nominal figure is a lower bound and the edge moves with the locks of other sessions. A call that meets the limit is rolled back; while it holds its locks, a bystander unit that needs an advisory lock (ingest, partition creation, the migrator) can fail with 53200 too, and plain reads did not fail in the measurement. Bulk callers chunk their claims (P4-3). The commit of a call waits for the synchronous standby before it releases its locks, so a slow standby makes the next call for the artifact fail with 55P03 [R]; `ledger-pg` has no standby and cannot show it.
15. **The stored head of a head conflict (D35).** A `DecisionHeadConflictException` names the head that is stored, not a head that includes an earlier decision of the same unit, in both ledgers (`DecisionLedgerContract#aStaleHeadInAUnitOfTwoDecisionsOfOneChainReportsTheStoredHead`, `ReportLedgerContract#aRedeliveryBehindANewDecisionOfTheSameUnitReportsTheStoredHead`; the in-memory ledger changed at two sites). When a unit has several defects, which refusal is raised is unspecified, and the unit is rolled back (the Javadoc of `ReportLedger.commitReportable`).
16. **A statement pinned identically by a unit test passes the local unit tests**, and a server shows the mistake; the server ITs of the `ledger-pg` job and the mutation run against the local PostgreSQL close that for the statements of V003 (D32), not for the planner choice of the partial index (performance only).
17. **Overhead against store limits (KF26).** The envelope adds the header, 12 bytes of nonce and 16 bytes of tag to an object, the same for an empty and for a 100,000-byte plaintext (`EncryptingEvidenceStoreTest#theEnvelopeAddsAFixedOverheadWhateverThePlaintextSize` asserts that the two overheads are equal and lie between 60 and 255 bytes). For the shape of the golden vector V3 and of the fixtures (an 8-character KEK id, the 60-byte wrapped key of the in-memory KMS) the overhead is 105 bytes (77 of header, 12, 16; in general 97 plus the length of the KEK id), which agrees with the 110 bytes of V3 for a 5-byte plaintext (`EnvelopeTest`); the size limits of the stores were not re-measured with envelopes.

### 6.4 The differential fuzz

`PgInMemoryDifferentialIT` drives the in-memory ledger and `PgLedgerStore` with the same generated operations over retention rows, the subject index and envelope bodies and compares the answers (the generator `DifferentialGenerator` draws from a `SplittableRandom` and reads no wall clock; `DifferentialOps` formats its text with `Locale.ROOT`; this is by reading and a grep of the fuzz classes for clock, random and locale calls, and no scan covers test classes). It is skipped without `REGPACK_PG_URL` and fails with `REGPACK_PG_REQUIRED=true` and an unreachable server. Its system properties: `regpack.differential.seeds` (default 1), `regpack.differential.sequences` (600), `regpack.differential.operations` (60), `regpack.differential.exactUnits` (false), `regpack.differential.all` and `regpack.differential.verbose`; a failure prints, in its first line, the seed, the sequence number, the `-D` options that run it again and both answers cut to 60 characters, so that the head of a head conflict survives: the first line is what the check-run annotation shows (it keeps the first line, cut at 300 characters). The second line says `shrunk from L operations to K`, or `NOT SHRUNK, the second run did not differ` when the sequence is run once more before it is shrunk and the difference does not recur (before, such a difference was shrunk and the report ended in a `NoSuchElementException` without a seed); then follow the numbered operation list, the first difference with both answers in full and the line with the `-D` options. A scratch pool that throws one `SQLException` makes the check fail in seconds with that first line and the `NOT SHRUNK` line, and the earlier mutant of the in-memory `DecisionStage.stage` (D35: the head that includes the earlier decision of the unit) gives, at seed 1 and sequence 38, a first line of 269 characters that holds both answers and both heads. Reproducibility holds for the same JDK (bounded `SplittableRandom` draws are not specified across JDKs). The default run takes 77 to 130 seconds on an idle development machine (112 seconds in the final run of T13b, D35) and longer under load from other processes, so only the job time at CP-2 tells the CI figure; CI runs the IT classes twice (the install step of `ledger-pg` has no `-DskipITs`, D27 item 7), so the fuzz runs twice there. `DifferentialOps.agree` is lenient for one kind of difference, which refusal wins in a unit with several defects (D33 (2)), and strict for the stored head of a head conflict on the same event identity (D35; two head conflicts on different event identities agree without a comparison of heads); `exactUnits=true` compares units in full. The generator never produces a TRN conflict, a change of the executing LEI or a replaced TRN (the TRN and the executing LEI of a subject are functions of its regime, event and leg), so the fuzz says nothing about them; the contract methods `aSecondSubjectWithTheSameTrnAndLeiIsRejectedAtomically`, `aStoredTrnCannotBeReplacedByAProposal` and `aStoredExecutingLeiCannotBeChangedByALaterVersion` do. The run asks that the two kinds of refusal of a unit (a head conflict and a refusal in the course of the unit) and the refusal of `removeSubjectRefs` were seen, from 200 sequences on (the default run of seed 1 saw 98, 70 and 16).
