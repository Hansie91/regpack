# 04 - Data-quality validation and identifier standards

Research brief for the regulatory/financial reporting platform design spec. Research date: 2026-10-08. Every source below was retrieved on 2026-10-08/09 unless a document date is given. "Confidence" is mine: **H** = read in a primary document or reproduced by computation; **M** = primary-adjacent or consistent secondary sources; **L** = single secondary source or unverified. Items amended/introduced in 2025-2026 or scheduled are tagged **[2025]**, **[2026]**, **[SCHEDULED]**.

## 1. Summary

1. Regulators do **not** publish conditional ("mandatory-if") rules as XSD or Schematron. ESMA publishes (a) an XSD 1.0 ISO 20022 schema and (b) an Excel rulebook in which each rule is tagged "XML schema" (whole file rejected) or "Application" (only the offending record rejected). MiFIR rulebook v1.7 (2022-05-31) has ~220 rules: ~120 syntax rules in the XSD and ~95 content rules, with 96 distinct `CON-NNN` error codes. The code format is `CON-<field no><seq>`; there is no `CONC-xxx` scheme (CONCAT is the natural-person ID construct). EMIR Refit uses `EMIR-VR-<table><field>-<seq>`.
2. The hard part of validation is **time**, not checksums. Nearly every reference rule is "valid at the trade date" (LEI status, MIC, ISIN-on-venue, ISO 4217, ISO 3166), and some need a second as-of date (submission date). GLEIF publishes only current state, so we must keep our own bitemporal reference history. ESMA says the same for NCAs.
3. Identifier algorithms are cheap and stateless: LEI = ISO 7064 MOD 97-10; ISIN = Luhn over letter-expanded digits; FIGI = a different "double-add-double" variant; UPI = ISO 7064 hybrid MOD 31,30 (third-party claim). I verified LEI, ISIN and FIGI against published examples.
4. ESMA's own rulebook already encodes a layered pipeline and a severity model: file vs record scope, `ACPT/PART/RCVD/RJCT/RMDR/WARN/INCF/CRPT` file statuses, `ACPT/PDNG/RCVD/RJCT` record statuses, and a 7-day "pending instrument validation" state (CON-411/CON-412). Our blocker/warning/info model should map onto these and add an explicit HOLD (pending) disposition.
5. XSD engines: ESMA's schema uses only XSD 1.0 features (no `xs:assert`/`xs:alternative`), so any mainstream validator works. libxml2 (the default C choice, behind most Rust/Go bindings) was declared "more or less unmaintained" by its maintainer on 2025-09-15, which is a lifecycle risk. Pure-Rust/Go validators exist but are very young. XSD 1.1 buys nothing for ESMA schemas.
6. Two regime moves matter for rule-set versioning: the UK moves to a 52-field regime on **2028-04-03** (FCA PS26/15, draft MDP schema published 2026-10-02), while the EU RTS 22/RTS 24 review was parked in June 2025 in favour of an ESMA "report once" proposal (final report 2026-07-02, target years only from secondary commentary).
7. Licensing flag: the ESMA MiFIR XSD files carry a SWIFT MyStandards licence header restricting redistribution/resale by software providers. Do not bundle them without legal review.

### 3.3 Timestamp, price, quantity, ISO 8601

- MiFIR field 28 format `YYYY-MM-DDThh:mm:ss.ssssssZ`, minimum precision seconds; OTC trades "at least to the nearest second"; trading-venue trades follow RTS 25 granularity. The XSD only enforces `xs:dateTime` plus pattern `.*Z`, so **granularity and UTC discipline are not syntactically enforced**. Content rules: trading time must not be after reception (CON-280) and not older than 5 years or before the regime start (CON-281). EMIR uses `YYYY-MM-DDThh:mm:ssZ` with rules relative to receipt and execution time.
- RTS 25 divergence/granularity tiers are in fact 13. UTC traceability (BIPM timing centres or a satellite source with offsets removed) is Art. 1. Clock evidence is a firm-side control; our platform can only check *plausibility* (future-dated, sub-granularity zero-fill, e.g. all `.000000` for an HFT venue) as WARNINGs.
- Price/quantity: see fact 14. Debt instruments quoted per unit cannot use percentage price (CON-330/331). "Major currency unit" rule means pence-quoted prices need conversion before the ISO 4217 check.
- XSD `xs:dateTime`/ISO 8601 edge cases (leap second `:60`, `24:00:00`, missing zone) were not verified in this session; treat as test-vector candidates [unverified].

### 3.7 Severity model and data-quality score

- **Severity**: BLOCKER (would be rejected, or legally wrong: never transmit), WARNING (accepted by regulator but risky/inconsistent: LEI lapsed on counterparty, nearing renewal, sub-second zero-fill, mismatch with counterparty or order data), INFO (derived/ignored/enriched, no action). Add a **disposition**: PASS, HOLD (outcome pending, with deadline, e.g. ISIN not yet in FIRDS: ESMA allows 7 days), QUARANTINE (blocked, awaiting fix).
- **Mapping to ESMA statuses** (`auth.031`): record ACPT/PDNG/RJCT/RCVD; file ACPT/PART/WARN/RJCT/RCVD/RMDR/INCF/CRPT.
- **Score (our proposal, not a standard)**: gate on blockers; for transmitted records compute per-dimension scores (completeness, validity, consistency, timeliness, uniqueness) as weighted pass rates, e.g. `score = 1 - sum(w_sev * failed) / sum(w_sev * applicable)` with w = 1 for WARNING, 0.1 for INFO. Report by regime, rule and source system. ESMA's own indicators (secondary, L-M): file and field rejection rates, pairing/matching rates, stale valuations, a 5% materiality threshold.

## 4. Design implications for our platform

1. **Rules as versioned data, not code.** Store each rule with: regulator rule ID (`CON-nnn`, `EMIR-VR-...`), regime, layer, severity, scope, as-of semantics (trade date / submission date / report time), reference datasets, effective-from/to, rule-set version and a legal-basis link (feeds R9 and R10). Import ESMA/FCA workbooks as seed data and generate test cases from them.
2. **Bitemporal reference store from day one.** Adopt ESMA's `ValidFrom/ValidTo/LatestRecordFlag` pattern for FIRDS, MIC, CFI, currency, country and *LEI*. Because GLEIF gives no status history, ingest every Golden Copy/delta and derive status intervals ourselves; keep the snapshot ID used by each validation so reports are reproducible (R4, R13).
3. **Every lookup takes explicit as-of dates** (trade date and submission date). Provide a "re-validate as of date X with snapshot Y" operation to reproduce past decisions.
4. **Stateless identifier library with golden vectors** (LEI, ISIN, FIGI, UPI, CONCAT, BIC). Include the verified vectors above and known weak spots (Luhn transpositions).
5. **Per-record XSD fragment validation before file assembly**, then whole-file XSD as the final gate (layer 6). ESMA rejects a whole file for any syntax error, so one bad record must never reach the file. Put the validator behind a port so it can be Xerces-J/.NET/libxml2/Rust without touching rules. Do not use `xs:assert`. Prefer a maintained engine; weigh libxml2's maintainer exit against its ubiquity.
6. **Do not redistribute regulator XSDs** until licensing is cleared (SWIFT MyStandards header); fetch from ESMA/FCA at deploy time with checksum pinning and keep the exact schema version in each evidence record.
7. **Severity plus HOLD**: model ESMA's PDNG/7-day semantics as first-class (HOLD with deadline, auto-escalation to BLOCKER). Persist all outcomes (rule, version, inputs, snapshot) in the immutable history for R4/R6.
8. **Cross-reference graph** with bitemporal edges (3.8) powers LEI-status-vs-counterparty checks, trade/order/allocation linkage, UTI chains and R12 duplicate detection (TRN uniqueness, action-type state machine).
9. **Regime plurality**: EU RTS 22 (65 fields, XSD 1.1.0) and the UK 52-field regime (from 2028-04-03) will coexist; rule sets and schemas must be selectable by jurisdiction and report date.
10. **Operational watchers** for: GLEIF dictionary/CDF versions, MIC monthly list, SIX ISO 4217/CFI changes, ESMA/FCA workbook and XSD versions, ANNA DSB CFI/UPI changes.
11. **PII**: natural-person fields (DOB, names, national IDs) require field-level protection and retention rules (not researched; flagged).

### Corrections that would change a design decision

1. **Rulebook typing has three values, and rule-to-code is one-to-many.** Model "Not implemented in the XML schema" (8 name-field charset rules, no error code) as a first-class rule type: nothing in ESMA's artefacts enforces it, so the platform must choose its own severity. Rules 220 and 148 each emit two error codes (CON-411/412, CON-471/472), so the rule table needs a rule-to-error-code relation, not a single code column. The max rule ID is 284.
2. **The FIRDS instrument lookup is venue-class dependent.** Do not implement it as a flat (ISIN, MIC, trade date) lookup. EEA venue: valid on that venue. XOFF, SI or non-EEA platform: valid on any EEA venue or SI, and only when fields 47/48 are empty. XXXX: the ISIN must be absent from reference data (CON-361).
3. **Basis-point precision conflict.** The XSD enforces 18/17 for BsisPts; the rulebook prose says 18/5. Make the XSD facet the hard gate (it decides whole-file rejection) and record the 18/5 text as a rule that needs confirmation with the receiving NCA before it is raised above WARNING.
4. **LEI status semantics are per regime and per role, not one rule.** MiFIR buyer/seller and non-MiFID executing entity: LAPSED allowed, as-of trade date. MiFIR MiFID-firm executing entity: LAPSED only if the submission-date re-check passes. MiFIR submitting entity: as-of submission date, LAPSED allowed. EMIR Counterparty 1: LAPSED not allowed, as-of reporting timestamp, skipped for old events. Parameterise the LEI check by (regime, role, as-of anchor, allowed statuses).
5. **Pin regulator workbooks by content hash and retrieval date, not by the date on ESMA's web page.** The EMIR workbook page says 2023-09-06 while the file at the same URL contains an October 2025 change and was last saved 2025-10-08.
6. **Licence scope is wider than "no resale".** The SWIFT header also limits external end users to internal use unless SWIFT agrees in writing, so even shipping the XSDs to customers needs legal sign-off, not only resale.
7. **Track two FCA artefacts separately.** Draft schemas and validation rules (MDP page, 2026-10-02) are outside CP26/34 (closes 2026-11-06); a watcher on only one will miss the other.

### Incidental findings (outside the 12 selected claims; not counted above)

- **FIGI check digit (3.1, confidence M): the description is ambiguous and the ISIN-style reading is wrong.** Recomputed on seven FIGIs recalled from memory (BBG000BLNQ16, BBG000B9XRY4, BBG000BPH459, BBG000BVPV84, BBG009S39JX6, BBG001S5N8V8, BBG000C6K6G9; these examples are not from a primary source) the working rule is: map characters to values 0-35, multiply the values at the 2nd, 4th, 6th, 8th and 10th positions from the LEFT of the 11-character payload by 2 (so the character next to the check digit is NOT doubled, the opposite of the ISIN/Luhn convention), sum the decimal digits of every resulting value, check = (10 - sum mod 10) mod 10. The ISIN-style parity fails on all seven, and BBG000BLNQ17 fails as a negative control. The OpenFIGI page confirms 12 characters, character 3 = G, 8 non-vowel characters, and the name "Modulus 10 Double Add Double", but the linked check-digit PDF was not read. Golden test vectors for the FIGI validator must include these.
