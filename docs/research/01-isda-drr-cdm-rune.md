# Research brief 01: ISDA DRR, FINOS CDM and the Rune DSL

As-of date of this brief: 2026-10-08. All web sources were retrieved on that date. Items first published or changed in 2025-2026, or scheduled for the future, are marked **[2025-26]** or **[FUTURE]**.

## 1. Summary

- **ISDA Digital Regulatory Reporting (DRR)** is an industry-governed, machine-executable interpretation of derivatives reporting rules. It is written in the **Rune DSL** on top of the **FINOS Common Domain Model (CDM)**. A generator turns the model into Java libraries. Firms feed CDM-shaped trade data in and get regime-specific report objects out, plus ISO 20022 XML, DTCC Harmonized XML or CSV projections.
- **Coverage today (June 2026 ISDA statement):** nine rule sets (CFTC, SEC, CSA Canada, EU EMIR, UK EMIR, ASIC, MAS, HKMA, JFSA). **MiFIR/MiFID, SFTR and Swiss FinfraG are commitments, not delivered.** I found no public evidence that any MiFIR rule is released yet. A 2026 working-group roadmap plans an RTS 22 build for Q2 and RTS 1/2 for Q3 2026. DRR is derivatives-first by design.
- **It is not OSI open source.** DRR code is governed by the *ISDA DRR License* (effective 2023-09-19), distributed through an ISDA-hosted Maven repository and a non-public GitHub repository. The CDM is FINOS-hosted (spec under Community Specification License 1.0). The Rune DSL and its Java generator are Apache-2.0.
- **The Java generator is the only complete one.** Python (CDM on PyPI) works for the data model and many functions. Nothing I found shows `report`/`reporting rule` support outside Java. Rune maintainers opened a batch of "make Rune easier to target from any language" issues on **2026-09-25**, including a request for a language-neutral conformance suite that does not yet exist.
- **DRR stops at generated, pre-validated reports.** Per ISDA's own adopter study, firms still build submission, acknowledgement handling, eligibility/jurisdiction scoping and resend logic themselves. That is exactly our requirements R4, R6, R9 and R12.
- **Recommendation:** treat DRR as (i) an optional, isolated "regime pack" for derivatives regimes and (ii) a *design template and golden-test source*. Build our own model-driven rule layer that borrows Rune's concepts (regulatory hierarchy, eligibility vs field rules, report definitions, projections, citation of provisions, test packs) but adds structured reason codes, runtime lineage persistence and effective-dated rule versions.

## 3. Detailed findings

### 3.1 What DRR is, and what sits underneath

- **FINOS CDM**: machine-readable model of products, trades and lifecycle events, covering OTC derivatives, cash securities, securities financing and commodities. Maintainers include ISDA, ICMA, ISLA, REGnosys (release management), TradeHeader and JPMorgan. Governance: Steering WG plus topic working groups. Per the draft 2026 schedule: CDM 5 end of life, 6 maintenance, 7 production, 8 and 9 in development.
- **Rune DSL** (formerly Rosetta DSL): REGnosys contributed it to FINOS (2024). Eight modelling components per the docs: data, metadata, expressions, data validation, functions, schema (serialisation), namespace, reporting.
- **Rosetta**: REGnosys's proprietary workspace, test and execution platform. DRR docs use it as the reference execution engine and offer an HTTP API (ingestion, custom function and regulation-report services, API-key header). Rune is explicitly usable without Rosetta, but all DRR tutorials lean on it.
- **DRR**: the regulatory layer. Namespaces: Base, Enrichment, Ingest, Standards (CPMI-IOSCO critical data elements), Regulation (`drr.regulation.<body>.<regulation>` with a `common` shared layer), Projection. Dependency chain: projections build on regulations, regulations on common rules, common rules on CDEs, CDEs on base.

### 3.3 MiFIR: verified position

1. DRR does **not** currently list MiFIR in its supported-regime pages (docs 7.0.0 and "next" omit it).
2. ISDA committed on 2025-05-07 to EU/UK MiFID/MiFIR, then reaffirmed it in the Nov 2025 paper and the June 2026 letter.
3. The 2026 roadmap targets RTS 22 transaction reporting (Q2) and RTS 1/2 transparency (Q3). I could not confirm either was delivered by 2026-10-08.
4. The DRR source is not publicly browsable, so partial MiFIR work-in-progress inside it cannot be excluded or confirmed. A June 2022 DRR overview table (older Rosetta docs, seen via search only) listed MiFIR as a UK pilot proof-of-concept; treat as historical.
5. Regulatory dates moved: ISDA's May 2025 text expected revised EU/UK transaction reporting in 2027. A secondary source (ACA Group, 2026-10-08) says UK rules take effect **2028-04-03** (FCA PS26/15; CP26/34 closes 2026-11-06). Verify on FCA/ESMA sites (owned by the regulatory-regime briefs). [2025-26][FUTURE]
6. Non-derivative MiFIR coverage (equities, bonds) is a model-fit question: CDM includes cash securities and securities financing, but the DRR pipeline is organised around trade lifecycle events (`WorkflowStep`, `TradeState`), not orders and executions.

### 3.4 Licensing, distribution, governance

- **Licence trap.** The 2023 ISDA licence permits redistribution only "without modifications" and "as part of a Larger Work", defines "ISDA DRR" as the methodology and documentation of any version at a portal URL (code coverage is implicit), imposes an indemnity on the licensee, and bars using "ISDA DRR" as a trademark. Yet ISDA's own docs tell firms to extend the model by regenerating Java or editing it, in a separate namespace. A vendor FAQ (TradeHeader, Feb 2026) states DRR is free to use but not open source; ISDA materials say "open-access" and sometimes describe the code as open source. Legal review is required before embedding or forking.
- **Distribution.** Java jars from the ISDA Maven repository; model `.rosetta` files inside the distribution; downloads and examples via the documentation portal; source repo access-controlled; starter kit on request.
- **Release cadence.** Docs show DRR 7.0.0 (current), 6.0.0, next. Minor releases are targeted about every four weeks (never more often than fortnightly); patch on demand; major scheduled by the Steering WG. A third-party repo claims DRR 7.13.0 on CDM 6.28.1 (low confidence: personal account, no provenance).
- **Governance.** Steering Committee (scope and priorities), Peer Review WG (interpretation sign-off), Technical Execution WG. Anyone may contribute via issue then PR, but must comply with the licence. ISDA says updates are incorporated well ahead of compliance dates.

### 3.5 Model structure and authoring

Real syntax, abbreviated, from the DRR documentation (https://drr-docs.isda.org) and Rune documentation (https://rune.finos.org):

```
// 1. Reporting rule with legal citation (DRR design principles)
reporting rule Cleared from TransactionReportInstructionBase: <"Cleared">
    [regulatoryReference CPMI_IOSCO cdeV3.CDE section "2" field "14"
        provision "Indicator of whether the transaction has been cleared..."]

// 2. Report definition: timing, eligibility and output type (DRR scope-and-structure)
report CFTC Part43 in T+1
  from TransactionReportInstruction
  when IsReportableEvent
    with type CFTCPart43TransactionReport

// 3. Validation as a cited condition (DRR "next" docs, abbreviated)
condition ReportingTimestampCondition:
  [regulatoryReference CFTC Part43 appendix "1" dataElement "97" validationRule "Transaction"
    provision "M, the value shall be equal to or later than [Execution timestamp]"]
    reportingTimestamp = executionTimestamp or reportingTimestamp > executionTimestamp
```

Other constructs seen in sources: `type ... extends ...` with cardinalities `(0..1)`, `(1..*)` and `[metadata reference]`; `choice`, `one-of`, `optional choice` conditions; `enum`; `func` with `inputs`, `output`, `alias`, `set`/`add`, `condition`, `post-condition`; filters (`filter ... then only-element`); `eligibility rule` (returns Boolean) and `reporting rule` (returns a value); report type attributes with `[ruleReference X]` and `[label ...]`; `[ruleReference empty]` to switch off an inherited field; `func X extends Y` scoped overriding with `super(...)`. FpML ingestion is functional in the DRR 7.0.0 docs (`Ingest_FpmlConfirmationToWorkflowStep`, `Ingest_FpmlRecordKeepingToReportableEvent`), while legacy `synonym` mappings still ship in CDM 6.x and DRR 6.x/7.x (CDM issue #5080) and were removed from the CDM 7 line.

Eligibility: the report's `when` clause gives **product/event-level** eligibility (`IsReportableEvent`, `ReportableProduct`). Entity classification and jurisdiction scoping are fed in through FpML `partyTradeInformation.reportingRegime` data and `ReportableJurisdictionInformation`, i.e. the firm must supply regime applicability. The Rune eligibility rule returns only a Boolean, not a reason.

### 3.6 Execution and code generation

- Each Rune type becomes an immutable Java interface with builders (`prune()`, visitor `process(path, processor)`); each report/rule becomes a `ReportFunction<IN,OUT>` (annotated `@RosettaReport(namespace, body, corpusList)`) injected through **Guice**; JSON through Jackson; XML projection through a Jackson XML mapper configured with a JSON file that matches the regulator XSD (`xml-config/auth108-esma-rosetta-xml-config.json`).
- Runtime libraries: `rune-common`, `rune-testing` (Apache-2.0, FINOS, both still snapshot-style versions on their READMEs). Rune 10.x builds on Java 21; `rune-common` README says Java 11.
- Other targets: CDM Python on PyPI (`finos-cdm`, Python 3.11+, Pydantic v2, `rune.runtime` 2.x; Java-native functions appear as stubs raising `NotImplementedError` unless registered); TypeScript and JSON Schema distributions (data model only for TypeScript); community generators for Scala, Kotlin, Go, C#, DAML; a C#/.NET CDM implementation proposed 2026-09-14 (Rune `number` to `decimal` loses precision versus Java BigDecimal). The DRR release checklist mentions code-generation checks for Java, C#, Scala and Kotlin.
- **No evidence** that the Python or any other generator handles `report`, `reporting rule`, `eligibility rule` or projections. Treat as unsupported until proven.

### 3.7 Field-level lineage

Three layers exist today:
1. *Design-time linkage*: each rule cites body/corpus/segment/provision text; each report attribute names its `ruleReference`. Machine-readable in the `.rosetta` source.
2. *Tool-time lineage*: Rosetta's Data Lineage view draws the execution graph of function calls with input/output payloads per step and the linked provisions.
3. *Industry decision lineage*: the Gentek AI traceability tool (mined working-group minutes mapped to rules) is under development (selected 2026-03-30; no delivery date).

Gap for us: no documented, persisted, per-submission runtime trace in the Java API (the open-source ORR project records lineage only per report row). That evidence (rule id, rule-set version, input hash, output) must be captured by our own layer.

### 3.8 Test strategy

Synthetic FpML or CDM JSON samples per asset class feed pipeline configs; each sample has input and output paths and assertions; expected outputs are committed and regenerated by a build profile; modifier classes patch samples; the Rosetta UI highlights mismatches with expectations. Docs suggest three adoption modes: *Build* (own engine plus DRR test packs), *Benchmark* (compare against the reference model) and *Buy*. ISDA describes running DRR in parallel to validate legacy output as an established use. Actual pack content and size are not public without repo access.

### 3.9 How a firm integrates it

Input: CDM `ReportableEvent` (or `TradeState`/`WorkflowStep`), obtained by FpML mapping (Translate 2.0, Rosetta service, commercial ETL or custom code) or built natively. Enrichment is an interface the firm implements (GLEIF LEI and ISO MIC lookups available via Rosetta). Output: regime report object, ISO 20022 XML (docs show ESMA auth.030 trade and auth.108 margin projections), DTCC Harmonized XML (Canada), or CSV (ISDA's adopter study says DRR can generate both CSV and ISO 20022). Firms choose one of three integration points (native upstream CDM, data-lake conversion, conversion at the reporting layer). Typical cost and effort quoted by adopters: POC about 3 months, full rollout 12-21 months, cost savings "up to 50%" (self-reported).

### 3.10 Known limitations

- Derivatives-centric; MiFIR, SFTR, FINMA not delivered.
- Java-only complete runtime; JVM, Guice, Jackson and Rune version coupling; CDM 8 and partitioning bring breaking changes.
- No submission, acknowledgement, resend or de-duplication layer; eligibility only partly modelled.
- Licence ambiguity and access control on the source repository.
- Upstream FpML-to-CDM mapping is not included in DRR itself.
- Traceability of *why* a rule was coded as it was is still being built.
- Rune semantic reference is the Java generator; no conformance suite yet.

### 3.11 What it would take

**(a) Embed DRR directly in a non-JVM runtime.**
- Port or regenerate: the Java generator is the only complete one. Python is the most advanced alternative but is unproven for DRR constructs (reports, projections, enrichment interfaces); even for CDM, Java-native functions are stubs that must be re-implemented and registered by the consumer.
- Must replicate Rune semantics exactly (BigDecimal precision, empty-value propagation, equality). No shared test suite yet; we would write our own differential tests against the Java output using DRR test packs.
- Licence: "without modifications" wording makes regenerating or transpiling DRR a legal question.
- GraalVM native image or Wasm are possible in principle; no evidence of anyone doing it for Rune/CDM; reflection-heavy Guice/Jackson code is a risk.
- Verdict: high cost, high risk. Not recommended as a first move.

**(b) Consume DRR-generated artefacts.** Lowest-risk route:
- Run the Java distribution as an isolated worker/sidecar with a narrow contract (CDM JSON in, report JSON or ISO 20022 XML out).
- Or use only the *outputs*: DRR test packs (CDM JSON in, expected report out) as golden fixtures; ISO 20022 XSD-conformant XML; `.rosetta` regulatory references as a rule/provision catalogue.
- Needs: JVM runtime and pinned jars, access to the ISDA Maven repo/starter kit, licence sign-off, a firm-side FpML/internal-to-CDM mapper and enrichment implementation.

**(c) Own DRR-like layer covering MiFIR-style regimes.** Reuse the *concepts*, not the code:
- Regulatory hierarchy (authority, document, segment, provision) with effective dates.
- Three rule kinds per report: timing, eligibility, field; functional, side-effect-free, composable.
- Report types with per-field rule references; projections to CSV/XML/ISO 20022 as separate, tested stages.
- Conditions citing the source validation rule (TR specifications, XSD, ESMA validation tables).
- Enrichment as an explicit interface (LEI, ISIN/CFI/FIRDS, MIC).
- Test packs: input, expected output, regenerate-and-review workflow.
- Additions Rune lacks: structured eligibility outcome with reason code and provision (R9), runtime lineage persistence (R4), submission state, ACK/NACK and resend queue (R6), idempotency keys (R12), hot-swappable rule versions (R8).
- Canonical model must suit order/execution-centric MiFIR (not just lifecycle events); a CDM mapper can be offered for derivatives.

## 4. Design implications for our platform

1. **Decouple DRR behind an adapter.** Define an internal "regime pack" interface: `evaluate(event, context) -> {eligibility decision, report fields with lineage, projection payload}`. Implementations: native rule pack (MiFIR first) and optional DRR-backed pack (JVM worker). Core platform never imports Rune/CDM types.
2. **Model eligibility as data with reasons.** Output `{eligible, reasonCode, provisionRef, ruleId, ruleSetVersion}` per record (R9). DRR's Boolean `when` clause is insufficient and entity/jurisdiction scoping is outside DRR anyway.
3. **Persist runtime lineage as evidence (R4).** For every reported field store rule id, rule-set version, input snapshot hash, output value and provision reference; keep the exact submitted payload. DRR's lineage is a design-time/UI feature.
4. **Own the submission state machine (R5, R6, R12).** DRR ends at pre-validated messages. Build send, ACK/NACK parsing, resend queue, UTI/transaction-key dedup and replay in our layer (recoverability, R13).
5. **Rule configuration (R8).** Store rules as declarative, versioned, effective-dated artefacts loaded without redeploy; keep expression language small (path navigation, cardinality, conditionals, filters, enums) like Rune's controlled expression set. Define exact numeric and empty-value semantics up front (Rune's own issue tracker shows this is where ports diverge).
6. **Prefer pinned versions.** DRR/CDM/Rune move fast (CDM 8 breaking changes, partitioning vote Nov 2026, Rune 10.x refactors). Pin everything; run DRR golden packs as regression.
7. **Use the test-pack pattern as the TDD unit (R14).** Each rule gets input JSON and expected output JSON; expectations regenerated and reviewed; suits subagent-driven TDD.
8. **Treat DRR as a benchmark and accelerator for derivatives regimes.** Parallel-run our EMIR/UK EMIR output against DRR output, as ISDA recommends.
9. **MiFIR cannot wait for DRR.** Plan the native MiFIR rule pack now; re-evaluate when DRR publishes RTS 22 and a licence-cleared distribution.
10. **Validation (R10).** Borrow the "condition cites source rule" pattern for XSD, TR-specific and standard checks (LEI, ISIN); generate error messages that cite the rule.
11. **Performance (R2).** No published DRR benchmarks; if a JVM worker is used, define memory/CPU budgets and benchmark early. A Rune-style immutable object graph with BigDecimal arithmetic is allocation-heavy by design (inference).
12. **Legal gate before any use.** Get counsel to review the ISDA DRR License (modification clause, indemnity, trademark), CDM Community Specification License and FINOS CLA terms.

## 5. Risks and unknowns

- **Licence interpretation** of "without modifications" and indemnity (counsel needed). Whether jars in the Maven repo are individually licensed is unverified.

- **MiFIR delivery**: no confirmation of RTS 22/RTS 1/2 coverage; scope (derivatives-only?) unknown; UK date conflict (2027 vs 2028-04-03).
- **SEC** status inconsistent across ISDA documents.
- **DRR to CDM to Rune version mapping** not documented on the pages read; only a third-party hint.
- **Non-Java support** for reporting constructs: unverified; Python function generation described as incomplete in one README and as supported in the CDM 7 post.
- **Performance and memory** of generated Java: no data.

### Corrections that would change a design decision

1. **Artefact access is not the blocker; the licence is.** The ISDA Maven repository (including the DRR jar checksum) is anonymously readable, so a spike can start without waiting for the starter kit. What gates adoption is the ISDA DRR License: "without modifications and solely as part of a Larger Work", the broad s4(b) indemnity for the licensee's Larger Work, and the s5 naming limits. Keep the legal gate (design implication 12), and note that arbitration is conditional on a US party.
2. **Pin a CDM 6 and Rune 9 stack, not CDM 7 and Rune 10.** DRR 7.14.0 and 8.0.0-dev.28 are built on CDM 6.29.0 and Rune DSL 9.95.x with JDK 21 at build time and Java 11 bytecode. Do not plan around CDM 7 features (functional FpML mappings, the new JSON format) or Rune 10 in a DRR-backed pack; a JVM worker needs both a 9.x-era Rune runtime and CDM 6 JSON. Design implication 6 (pin everything) gets a concrete target.
3. **Do not wait for DRR MiFIR.** Even on the CDM roadmap, MiFID II testing is Q4 2026 and the RTS 1/2 build is Q3 2026; ISDA's own page on 2026-10-08 still says the work is in progress. The UK go-live is now firm at 2028-04-03 (FCA PS26/15), which gives a native MiFIR pack time, but also means the "2027" planning assumption is wrong for the UK. The EU date still needs an ESMA or EUR-Lex check.
4. **"14 regimes" is a commitment count, not delivered coverage.** Plan on nine delivered rule sets (derivatives, mostly EMIR-type and CFTC-type reports), and treat MiFIR, SFTR and FinfraG as not available.
