# 06 - Data-source and destination connectivity

Research brief for the regulatory/financial reporting platform design spec. Evidence as-of **2026-10-08** unless a row says otherwise. Items marked **[2025-26]** were introduced or changed in 2025-2026; **[FUTURE]** are scheduled. Confidence is high/medium/low; "unverified" means I could not read a primary source.

## 1. Summary

1. **Do not adopt any single integration tool as the product's connector layer.** Each candidate fails at least one hard constraint: Camel and NiFi are JVM-heavy and carry their own lifecycle (LTS every ~6 months, 1-year support for Camel); Redpanda Connect gates its CDC inputs behind a commercial licence and has no IBM MQ/JMS/Solace/FIX/Db2 inputs in its catalogue index; Airbyte's connectors are Elastic License 2.0 per its own docs; Vector is an observability pipeline with no SQL/SFTP/MQ/FIX source; Kafka Connect needs a Kafka cluster.
2. **Own a narrow connector contract and an ingestion ledger; reuse everything else behind it.** The contract copies the shape that Airbyte, Singer and Redpanda's dynamic plugins converged on: `spec / check / discover / read(state) -> records + checkpoints`, out-of-process, opaque state, destination (our platform) commits before the checkpoint is acknowledged.
3. **Effectively-once = at-least-once delivery + idempotent landing.** Every tool researched (Debezium, Redpanda Connect, Airbyte, Event Hubs) is at-least-once by default. Kafka Connect source-EOS exists but needs distributed Connect and Kafka transactions, and Debezium's own docs warn it may not be fully reliable. Our ledger, not the source tool, carries the guarantee, and the raw landing zone doubles as the replay store (R4, R12, R13).
4. **Three-tier pathway:** (A) a small first-party native set; (B) contract-compatible out-of-process connectors (JVM host for JDBC/JMS/FIX/Debezium; Python host for dlt/Singer/Airbyte-protocol); (C) a "landing-zone" pattern (customer tools drop files, Kafka topics or staging tables that tier A consumes). CDC arrives via tier C in v1.
5. **Outbound is a different problem from inbound.** Destinations (FCA MDP, UnaVista-style ARMs, DTCC GTR, REGIS-TR) are mostly SFTP/file plus XML responses, some REST. The abstraction must model the *acknowledgement shape* (sync / async file / async message / portal-only) because R6 depends on it.
6. **WASM is not a v1 connector model.** WASI 0.3.0 only shipped 2026-06-11; connectors need sockets, TLS and native drivers. WASM is a good fit for sandboxed, deterministic *transform/validation/response-parser* plugins.
7. **A JVM will probably exist in the product anyway** because the FINOS CDM states only its Java distribution is complete (the ISDA DRR runs on CDM). Hosting JDBC/JMS/Debezium in that same JVM sidecar keeps the core lean. This needs confirmation from the DRR research topic.

### 3.2 Plugin and isolation models

- **Subprocess + framed messages** (Singer stdout JSON lines; Airbyte stdio, or sockets + protobuf): simple, language-agnostic, crash-isolated, serialisation overhead. Airbyte's own numbers claim 4-10x from socket mode (vendor claim).
- **gRPC over Unix socket** (Redpanda dynamic plugins; Go/Python SDKs; batch only): the vendor itself says compiled plugins are faster.
- **In-process C ABI** (ADBC driver manager loading shared libraries; Arrow C Data Interface): zero-copy, but drivers are native libraries (not a single static binary) and share the process fate.
- **WASM component model**: WASI 0.3.0 (2026-06-11) adds async streams, but no evidence connectors with TLS sockets, JDBC or IBM MQ C libraries run there. Precedent for abandonment exists (Vector). Fit: pure functions (field mappers, validators, ack/response parsers).
- **JVM sidecar** is not a "plugin model" but the pragmatic route to JDBC, JMS and QuickFIX/J.

### 3.3 Delivery semantics and replay

All sources are at-least-once unless proven otherwise. Debezium states it has no built-in deduplication. Redpanda Connect gets its guarantee from in-memory acknowledgement tracking. Airbyte emits state only after the destination commits; interrupted syncs resend uncommitted records. Event Hubs documents at-least-once and tells consumers to be idempotent. Kafka Connect source EOS (KIP-618) works only for connectors that supply replayable offsets and only in distributed mode.

### 3.4 Secrets, TLS, proxies

Vault is BUSL-1.1 (IBM licensor from the main-branch LICENSE) so a *client* integration is fine but we should not bundle the server; OpenBao is the MPL-2.0 API-compatible alternative. Cloud secret managers and Kubernetes (External Secrets Operator, Apache-2.0) cover the rest. Destination constraints seen in the wild: DTCC SFTP uses published known-host keys and a firewall/open-internet connectivity form; Bloomberg SFTP accepts only pre-registered IPs; FCA MDP manages SFTP certificates in its portal; Event Hubs presents a single stable virtual IP; Event Hubs requires TLS and SASL_SSL (OAUTHBEARER or PLAIN).

### 3.5 Outbound destinations (what the adapters must cope with)

- **FCA MDP:** SFTP gateway plus ISO 20022 XML; ARM or direct; confidential MIS; file-level codes such as FIL-104/FIL-105 appear in the commodity-position instructions (not transaction reports - do not generalise).
- **UnaVista-style ARM (venue manuals 2021-2024):** SFTP in-folder; ISO 20022 XML or CSV; <= 100,000 reports/file; unique filenames <= 60 chars (a bad name rejects the whole file); processing in upload order; cancellations before amendments; response files in XML (2021) or CSV (2024). Verify against the current spec.
- **DTCC GTR:** SFTP, web services, CSV/FpML for the Dublin entity; company-wide transports also include MQ, Connect:Direct, FTPS; whether MQ/API carries EMIR ISO XML is unconfirmed.
- **REGIS-TR:** SFTP, REST API, portal upload; instant rejection feedback via auth.092; CSV-to-XML converter offered.
- **Bloomberg:** FIX on TCP 8228, SFTP on 22 with hourly action caps (4,000 uploads, 20,000 downloads, 1,000 directory scans); ARM-specific connectivity not found.

Common pattern: transport ack (file landed) -> technical validation (schema) -> business acceptance -> reconciliation. Message names and versions drift (auth.092 .03 -> .04), so response parsers must be versioned data/plugins, not hard-coded.

### 3.6 Testing

Testcontainers (MIT; Java, Go, Rust, .NET) can run databases, Kafka, MinIO and SFTP in CI; Debezium ships an incubating Testcontainers extension. Airbyte's Connector Acceptance Tests and Meltano's `get_tap_test_class` are working examples of a shared conformance suite.

## 4. Design implications

**D1 - Connector contract (versioned, language-neutral).** Source: `spec`, `check`, `discover` (Arrow schema + stable keys), `read(state, limits)` emitting `Batch{stream, seq, arrow|bytes, source_coordinates, checkpoint}`. Destination: `spec`, `check`, `send(batch)`, `poll_acks()`. Frame as protobuf/gRPC on a Unix socket carrying Arrow IPC (borrowing Airbyte's socket-mode idea) for out-of-process; a plain trait for in-process. Backpressure = credit-based `read(limits)`.

**D2 - Ingestion ledger + raw landing zone.** One local transaction commits: raw batch (content-addressed, immutable) + ledger row (source, stream, source coordinates, content hash, schema fingerprint, connector version) + checkpoint; only then ack upstream. Record-level `ingest_key = (source_id, source_record_id, source_version|hash)`. Files are identified by path + size + mtime + SHA-256 and never moved before commit. This supplies R4 evidence, R12 duplicate control, R13 restore, and replay without re-querying sources. Retention interacts with back-reporting lookback (FCA PS26/15 cuts default lookback from five to three years from 2028 [FUTURE]).

**D3 - Database extraction strategy.** Prefer business-date, as-of extracts with control totals and stable keys over cursor-column polling (late commits, clock skew); CDC where the customer already runs it.

**D4 - Connector tiers.** A: native, first-party, each with the conformance suite and an SBOM. B: contract-compatible external executables, with adapters for Airbyte-protocol images (licence-gated), Singer taps, dlt pipelines, Camel routes in the JVM host. C: landing-zone manifests consumed by tier A.

**D5 - Runtime packaging.** Core as one artefact; JVM host and Python host as optional, separately versioned images pinned to a contract version. If the DRR confirms a JVM requirement, merge "DRR executor" and "JDBC/JMS/Debezium host" into one sidecar.

**D6 - Credentials.** Config stores only references (`vault://`, `openbao://`, `awssm://`, `azkv://`, `gcpsm://`, `file://`, `env://`), resolved at run time, never written to the evidence log; re-resolve on auth failure; certificate expiry monitored; sidecars receive credentials over the socket handshake rather than environment variables. Egress goes through a configurable proxy with per-destination identity, pinned SSH host keys and mTLS, and supports static egress IPs.

**D7 - Destination ack model.** Each destination declares `ack_model` in {sync-response, async-file, async-message, portal-only}, correlation keys (file name, UTI/transaction reference, MQ correlation ID), idempotency rules, and versioned response parsers (WASM or declarative). Rejected/unacknowledged items go to the resend queue (R6); resend must reuse or supersede keys so R12 holds.

**D8 - Schema and mapping.** Arrow schema is the internal lingua franca; mapping specs (source field -> canonical field + transform) are versioned, golden-file tested, and drift on reportable fields fails closed.

**D9 - Minimum v1 set (tier A unless noted).**
- Inbound: files (local/NAS, SFTP/FTPS, S3, ADLS Gen2, GCS) with CSV, delimited/fixed-width TXT, XML (streaming, XSD), JSON/NDJSON, Parquet; Kafka protocol (Kafka, Redpanda, Event Hubs endpoint, MSK); SQL via PostgreSQL native plus JDBC/ODBC host for Oracle, SQL Server, MySQL/MariaDB, Db2, Snowflake; HTTPS pull and webhook (OAuth2, mTLS); IBM MQ/JMS (JVM host, if target customers use MQ - confirm in discovery). Avro and Excel in v1.1.
- Outbound: SFTP (key/cert, host-key pinning, temp-name-then-rename, ordered upload, response-file polling); HTTPS REST (mTLS/OAuth2, idempotency keys); IBM MQ/JMS put with reply-queue correlation; file/object-store drop for manual or portal submission.
- Tier C in v1: CDC (customer-run Debezium Server/Kafka Connect -> Kafka), BigQuery/Databricks/Teradata/Sybase via customer-provided extracts or tier B.
- Later: SWIFT FileAct, AS2 (Camel has an `as2` component), FTPS variants, SOAP/GraphQL/gRPC sources, packaged Debezium Server profile, Pulsar, Solace (protocol support unverified here), Kinesis.

**D10 - Governance.** Pin and wrap fast-moving libraries (DuckDB 2.0, DataFusion 56, OpenDAL 0.x) behind our own traits; licence allow-list in CI; SBOM per release (the EU CRA reporting duties for manufacturers started 2026-09-11, so shipped third-party code is our exposure).

## 5. Risks and unknowns

- **Licence drift:** Redpanda's tiers and Airbyte's ELv2 have both tightened; Vault is BUSL; Columnar's "PBL" and commercial driver licences are undefined/private. Legal review needed before shipping any of these inside a product, and especially before any hosted edition (ELv2).
- **Enterprise-DB driver gap:** no open Arrow-native route for Oracle, Db2, Sybase, Teradata; JDBC/ODBC fallback must be proven for memory behaviour (a Confluent forum report shows a 6 GB worker for one query-based connector on a ~100M-row table - anecdotal).
- **Memory/CPU claims are mostly vendor or anecdote.** No head-to-head benchmark found; recommend an early spike (same 50M-row extract through Camel/JDBC, ADBC, arrow-odbc, DuckDB) with RSS and CPU gates.
- **arrow-odbc / odbc-api licences (MIT)** confirmed only via aggregators; verify before use.
- **OpenDAL SFTP:** platform limits and whether it shells out to an `ssh` binary are unverified; deployability of SFTP in a static binary is open.
- **Outbound specs are partly paywalled/confidential** (FCA MIS, TR specs, ARM specs). UnaVista details are 2021-24 vendor-venue manuals. Whether DTCC accepts MQ/API for EMIR ISO XML is unconfirmed; SWIFT for REGIS-TR is unconfirmed under Refit.
- **Regulatory moving parts:** FCA PS26/15 (effective 2028-04-03), draft schemas published 2026-10-02 and CP26/34 pending; ESMA's 2026-07-02 "report once" report is non-binding and its implied timeline (secondary source: ~2031) is unconfirmed; EMIR schema versions drift.
- **Single points:** Debezium sponsorship moved from Red Hat to IBM (secondary source, low confidence); Debezium 3.7 contains breaking Oracle changes.
- **DRR dependency:** JVM-sidecar recommendation depends on the DRR topic confirming Java-only execution.
- **Not researched:** DORA third-party ICT obligations for customers (applies since 17 Jan 2025 per general knowledge, unverified here); Solace and Pulsar specifics; Kinesis client licensing; SWIFT connectivity.
- The web-search budget was exhausted near the end; Event Hubs/Solace checks were completed with page fetches only (Solace failed).

### Corrections that would change a design decision

1. **Do not premise the architecture on "a JVM exists anyway" (Summary item 7, D5).** CDM publishes a Python distribution (finos-cdm 7.5.0, 2026-09-29) that generates Rune functions as Python; only Java-native functions are stubs. Whether DRR logic runs without a JVM is unknown. Make the shared JVM sidecar conditional on a DRR spike: run the target DRR report functions through finos-cdm and list any NotImplementedError stubs hit.
2. **EMIR destination adapters (D7, D9).** The cited REGIS-TR source supports SFTP and portal only; REST was explicitly not available at UAT launch. Do not plan a REST destination adapter for REGIS-TR without a current spec. Message identifiers and versions (auth.030, auth.108, auth.091, auth.092 at .03 or .04) are unverified beyond auth.030.001.03 and auth.092.001.03 in 2023, so keep them as versioned, configuration-driven parser data. Useful anchor: ESMA requires rejection and reconciliation feedback in ISO 20022 XML, so a schema-driven XML ack parser is the right default shape.
3. **Per-destination filename rules (D7).** The LSEG/UnaVista guide caps filenames at 40 characters including the extension (the brief said 60). Make filename length, pattern, ordering (CANC/CXL before NEW/NEWT) and max reports per file destination configuration, validated before upload, and test against the stricter value.
4. **WASM scope (Summary item 6, section 3.2).** Relax "no network connectors in WASM" to "no SQL, MQ, SFTP, FIX or raw-TLS connectors": WASI 0.3 has an outbound wasi:http client and TCP sockets, so HTTPS-based response polling or REST adapters could become sandboxed plugins later. TLS over raw sockets is still draft (wasi:tls). No change to the v1 plan.
5. **JVM baseline.** Camel 4.18 LTS runs on Java 17/21 only; Java 25 needs Camel 4.22 LTS. A Java 21 sidecar can stay on 4.18 (supported to 2027-02-17) but must move to 4.22 or a later LTS before then.
6. **ADBC and Columnar driver licensing remain unstable [FUTURE].** Release 25 is at rc0 (2026-09-21), LicenseRef-PBL is undefined, and the Foundry driver set is wider than the guide page shows. Keep the licence allow-list gate in CI and require legal review for the mssql, redshift, oracle and teradata drivers.
7. **Unconfirmed forward reference.** Drop or re-source "CP26/34 pending" until a primary FCA source is found.
