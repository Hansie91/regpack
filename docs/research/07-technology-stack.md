Markers: [2025] / [2026] = introduced or amended in that year; [FUTURE] = scheduled after 2026-10-08. ## 1. Summary

**Recommendation: build the engine on the JVM, as Java 25 LTS (HotSpot), shipped as one container or jlink image containing one modular-monolith process.** Kotlin is optional, not default. Use Rune/DRR-generated Java in-process for derivative regimes (R7). Use a CEL or decision-table layer for firm-configurable rules (R8, R9). Use JAXP/StAX streaming for XML and XSD validation (R5, R10).

Why:

1. **R7 is the decisive, asymmetric requirement.** Rune's Java generator is the only one that emits executable function code, and Rune's behaviour is "defined by what the Java generator happens to do" (rune-dsl issue #1411, opened 2026-09-25). The CDM's TypeScript distribution is data-model only. The Python generator says function generation is "not yet fully implemented". A C#/.NET port is only a proposal. DRR is consumed as Java via Maven and run as `ReportFunction<IN,OUT>`. Any non-JVM host therefore needs a JVM sidecar, which costs more in lifecycle and moving parts than the efficiency it buys.
2. **Mature XSD validation, vendor-supported connectors and rule engines are in-process on the JVM.** For Rust and Go, XSD validation means either libxml2 over C bindings (libxml2 lost its sole maintainer in September 2025) or very young single-author validators.
3. **Lifecycle (R2).** Java LTS ships every two years, with free builds supported to at least Sep 2031 (Temurin 25) and vendor support to 2030+. Go supports only the two newest majors (about one year). Rust has no LTS and a 6-week cadence. .NET 10 LTS ends 2028-11-14.
4. **The JVM efficiency gap (R1) is narrowing.** Compact object headers (JDK 25, flag) cut heap 22% and CPU 8% in SPECjbb2015. AOT cache cut startup 42% in the JEP 483 example. G1 becomes the default everywhere in JDK 27. Reporting is batch or near-real-time, not microsecond-latency, so JVM warm throughput is sufficient. This must be confirmed by a spike (section 4).

Weighted scores out of 5 (judgement, section 3): **JVM 4.4, .NET 3.6, Go 3.2, Rust 3.0**. The ranking holds if the DRR criterion is dropped (JVM 4.4, .NET 3.8, Go 3.4, Rust 3.2) and if the efficiency weights are doubled (JVM 4.3, .NET 3.7, Go 3.3, Rust 3.2).

**Flips** (detail in section 4.3): .NET if the organisation mandates .NET and DRR runs as a separate JVM service or the Rune C# generator reaches parity. Go or Rust if DRR is not executed in-process (only pre-computed outputs, or rules are re-authored in our own model) AND footprint or density dominates AND XSD validation and legacy connectors can be isolated. Rust as a sidecar only for heavy columnar reconciliation.

R4 (immutable evidence log), R6 (ack/resend queue), R9 (reason codes), R11 (cross-references), R12 (dedupe/trackability) and R13 (recovery) are architecture-level and stack-neutral. They depend on the store, outbox and hashing design. The stack only matters through driver quality, transactional outbox support and tooling.

### 3.2 Performance, memory, GC, startup
- No credible cross-language benchmark was retrievable (Benchmarks Game charts are SVG only). Treat Rust > Go ~ JVM ~ .NET on raw CPU as a general expectation (L), not a measured result for this workload.
- JVM: JDK 25 LTS has compact object headers (opt-in), JEP 515 profile warmup, and a 130 MB-class AOT cache. JDK 27 (non-LTS, GA 2026-09-15) makes compact headers and G1 default, but Java 29 LTS (Sep 2027) is the next LTS that carries them by default [FUTURE].
- Rune-generated objects are immutable with builders, so per-record allocation is high (inference, L; no source measured it). Design the pipeline to stream and bound batch size.
- Go: concurrent, non-moving mark-sweep GC (about 25% CPU during mark); `GOMEMLIMIT` is a soft limit with a 5-10% headroom recommendation. Green Tea GC is default from 1.26.
- .NET: DATAS adapts heap size (TechEmpower: about -80% working set for 2-3% throughput) and is default in .NET 9+. Native AOT cuts startup and memory but forbids dynamic loading and Reflection.Emit and implies trimming.
- Rust: no GC, lowest and most predictable memory. Costs are the compile cycle and ecosystem churn.
- GraalVM native-image would give small, fast-starting binaries, but Oracle moved it off the Java SE release train. The release calendar shows only the 25.x line (monthly feature releases; CPUs scheduled to Jan 2027), with no JDK 26-28 builds and Java 29 promised. Mandrel (Quarkus) and Liberica NIK carry 25.x. Treat native-image as an optional optimisation, never a baseline.

### 3.3 XML / XSD (R5, R10)
- JVM: JAXP validation with StAX streaming is built into the JDK (XSD 1.0). XSD 1.1 needs Xerces-J (separate package, release about 2022, maintenance-mode) or commercial Saxon-EE. ISO 20022 XML is produced by deterministic rules from ISO 20022-4:2026; the XSD version level of ESMA's schema zips was not verified (no zip opened).
- .NET: `XmlReader` + `XmlSchemaSet` streaming validation is first-party. XSD 1.1 only via SaxonCS (EE; HE from Saxon 13).
- Go: no XSD in the standard library. Options are libxml2 via cgo (`terminalstatic/go-xsd-validate`, `lestrrat-go/libxml2`) or the tiny pure-Go validators in fact 18.
- Rust: `libxml` crate wraps libxml2 (C, unsafe, inherits its CVE stream) or pure-Rust crates (fact 18). `xsd-parser` generates Rust types from XSDs (MIT, 88 stars, v1.5.0); schema-based validation is listed as planned only.
- libxml2 is XSD 1.0 only (M) and its maintenance is thin (fact 17). Do not put it on the critical path of a regulated engine.

### 3.4 Data sources and transports (R3)
- JVM wins on vendor-supported breadth: Oracle `ojdbc11`, Db2 JCC, SQL Server JDBC, jConnect/jTDS for Sybase (SAP ASE 16.0 end of mainstream maintenance reported as 2027-12-31, M), IBM MQ allclient/Jakarta, Solace JCSMP, Kafka, cloud SDKs. FFM (JDK 22) replaces JNI for any C library needing it.
- IBM MQ: use client (TCP) mode, not JNI bindings mode, so virtual threads do not pin on native frames. A search summary of IBM docs says automatic client reconnection is not supported by the base "MQ classes for Java" (the JMS classes may differ; verify, L): plan reconnect handling in the adapter.
- Solace: official Java, .NET, C, JS, Python, and Go (1.0.0) APIs; no official Rust; AMQP 1.0/MQTT are fallbacks (M).
- Go and Rust reach DB2, Sybase and IBM MQ only through cgo/C clients or ODBC, which erodes the single-binary advantage and shifts support risk to the firm.

### 3.5 Rules and expressions (R8, R9)
- CEL suits configurable reportability: sandboxed, side-effect free, non-Turing-complete, cacheable compiled programs, source positions in errors. cel-java and cel-go are the canonical implementations.
- R9 needs rule id, version, legal-reference and reason code attached to every decision. Neither CEL nor Rune provides this out of the box. It is a platform responsibility. ISDA's traceability tool (RFQ Oct 2025) shows the same need on the DRR side.
- Rune/DRR covers derivative regimes. For MiFIR-style rules not in DRR (DRR's own MiFIR/SFTR extensions were "in progress" on the ISDA page), choose between authoring in Rune (Java-only execution) or CEL plus decision tables. This is a design-spec decision, not a stack constraint.

### 3.6 Columnar processing
- Rust has the best-in-class engines (DataFusion, Polars, arrow-rs). The JVM has Arrow Java (needs `--add-opens`), DuckDB JDBC (primary tier), DataFusion Java 0.1.0 (new), and Spark where already present.
- All of these are fast-moving: DuckDB 2.0.0 is due 2026-10-21 and 1.4 LTS ends 2026-11-17, Polars just shipped breaking 2.0, DataFusion bumps majors about every two months. That conflicts with R2. Keep them behind an interface; push set-based work into the source database or a single optional analytic module.

### 3.7 Security and supply chain
- Memory safety: Java, Go, C# and Rust are all memory-safe in safe code. C++ is not. cgo/JNI/ODPI-C and Rust `unsafe` re-introduce native risk.
- SBOM: CycloneDX generators exist for Cargo, Go modules, Maven/Gradle and .NET (CycloneDX tool centre). DORA RTS 2024/1774 pushes regulated firms to track open-source libraries for critical functions (vendor summary, M). EU CRA reporting duties apply from 2026-09-11, so a vendor-shipped product needs a vulnerability-handling process now.
- FIPS: Go has the clearest native story (certificate #5247, next module pending). .NET inherits the OS. Java needs a validated provider or FIPS-mode OS stack (unverified). Rust's aws-lc-fips has no certificate yet.

### 3.8 Lifecycle and maintainability (R2)
- Java: backward-compatible, 2-year LTS cadence, several free LTS builds. Expect one upgrade (25 to 29) around Sep 2027-2028. Kotlin adds a 6-month language cadence and an 18-month stdlib support window per line.
- Rune toolchain constraint: Rune tooling builds on JDK 21 (Xtend/Xtext), while generated code is Java 8+ compatible. The runtime can sit on JDK 25 but the model build needs JDK 21 until FINOS migrates, so plan a split toolchain.
- .NET: 3-year LTS; .NET 8/9 both end 2026-11-10. Go: yearly forced upgrades but a strong source-compat promise. Rust: continuous updates, no LTS; editions are opt-in and interoperable.

### 3.9 Precedents
- Verified: DRR/Rune is production regulatory reporting built on Java (REGnosys announcement; banks named in the FINOS ORR post: JPMorgan, RBC, BNP Paribas, BMO). FINOS ORR runs DRR on Spark. Prowide ISO 20022 is a Java library with `auth` modules.
- Unverified (L): vendor blogs claim Java-to-Rust service rewrites at banks, and I found no documented bank core ledger or trading system in Rust and no regulator guidance on language choice. Go evidence is mostly non-bank.

### 3.10 Python + Arrow and C++ (qualitative)
- Python: free-threaded build officially supported in 3.14 (PEP 779, accepted 2025-06-16) with about 10% single-thread slowdown and 15-20% more memory. The Rune Python generator is incomplete. Good for analysis tooling, not the engine (virtualenv and native-wheel moving parts conflict with R2).
- C++: Xerces-C/libxml2 give XSD 1.0 only (2018-19 sources, L), manual memory safety contradicts the CISA/NSA direction, and there is no Rune path. Not recommended.

## 4. Design implications for our platform

1. **Standardise on Java 25 LTS** (Temurin or a commercial OpenJDK), no preview features, and plan the 25-to-29 move for late 2027. Java first; Kotlin only if the team insists, because the Rune output is Java.
2. **Hexagonal boundaries** around: DRR/Rune host, rule evaluator, schema validator, source connectors, and transport. Each boundary is a swap point if a flip condition triggers.
3. **Run DRR in-process** behind a `DerivativesReportingPort` that takes CDM objects and returns ISO 20022 content. Pin the DRR version per regime and record it in every decision record (R9, R4). Resolve DRR licence and Maven-repository access terms for a vendor product before committing (unknown, section 5).
4. **Configurable rules (R8):** Rune for DRR regimes; evaluate CEL (cel-java) plus versioned decision tables for the rest. Every decision persists rule id, version, legal reference, inputs hash and reason code.
5. **XML:** StAX streaming plus JAXP XSD 1.0 validation as the default. Keep Xerces-J (XSD 1.1) and Saxon-EE as optional drop-ins behind the validator port. Keep libxml2 out of the build. Store the exact outbound bytes plus hash (no re-serialisation) for R4.
6. **Connectors:** JDBC and vendor clients in-process. Isolate IBM MQ, Solace, Sybase and Db2 drivers behind adapters with their own timeouts. Use virtual threads for I/O fan-out; use bounded platform-thread pools for CPU-bound validation and avoid MQ bindings mode.
7. **Efficiency plan:** stream and bound memory; enable `-XX:+UseCompactObjectHeaders` on 25; use the AOT cache (JEP 483/515) if startup matters; avoid per-record object graphs where possible. Treat GraalVM/Mandrel native-image as a later experiment.
8. **Columnar:** no columnar engine as a core dependency; use SQL in the source system and an optional adapter (DuckDB or Arrow).
9. **Supply chain:** CycloneDX SBOM in CI, dependency-vulnerability scanning, a pinned and mirrored Maven repository, and one deployable (container with jlink runtime). This also serves DORA and CRA obligations.
10. **R14 fit:** JUnit 5, mature mocking and container-test tooling support subagent-driven TDD (Testcontainers availability not verified, L). Write Rune-dependent code behind ports so TDD works without the DRR artifact on the classpath.

### 4.3 Conditions under which the recommendation flips
| Trigger | Flip to |
|---|---|
| Governance mandates .NET and DRR can run as a separate JVM service, or Rune's C# generator gains executable functions with a conformance suite (watch finos/rune-dsl #1409, #1410, #1411 and common-domain-model #5169) | .NET 10 LTS |
| DRR is not executed in-process (only pre-computed outputs, or rules re-authored in our own CEL model) AND memory/density is the top priority AND XSD and legacy drivers can be isolated | Go (simpler hiring) or Rust (best efficiency) |
| A destination requires XSD 1.1 | Stay on JVM (Xerces-J/Saxon-EE) or .NET (SaxonCS); Go/Rust would need a Java helper |
| Large-scale reconciliation or analytics dominates | Keep JVM core; add a Rust DataFusion service or use the database engine |
| Rune toolchain or DRR licence/Maven access changes adversely | Re-run the evaluation |
| GraalVM Java 29 support lands and native-image proves materially better in our spike | Add native-image build profile, still JVM |

## 5. Risks and unknowns
- **XSD version of regulatory schemas is unverified.** ESMA publishes zips; none were opened. If any regulator or TR schema uses XSD 1.1 assertions, the validator choice narrows to Xerces-J or Saxon.
- **No workload benchmarks.** All performance statements are vendor/JEP claims or my expectation. A spike should measure DRR heap per trade, XSD validation throughput on auth.030-size batches, and MQ throughput under virtual threads.
- **DRR licence text (PDF) not read; DRR docs "implementation" page returned 404.** The Maven coordinates came from a search summary. Redistribution, vendor-use and CI-access terms are unknown.
- **GraalVM roadmap is a promise** (Java 29 support), based on a blog I could only read via a search summary (Medium returned 403). Oracle's own Java SE roadmap page also returned 403.
- **Secondary-source items (M/L):** .NET and libxml2 XSD 1.0 status, SAP ASE lifecycle dates, Solace API details, OTel table currency, Java FIPS, hiring in finance for Go/Rust, bank precedents, Kotlin/Spring support terms, Testcontainers support.
- **Upstream churn flagged for 2026-2027:** DuckDB 2.0.0 (2026-10-21), .NET 8/9 EOS (2026-11-10), Kotlin 2.5.0 (Dec 2026), Java 29 LTS (Sep 2027), CRA main obligations (2027-12-11), Ontario DRR UAT (Apr 2027).
- **Rune is "FINOS - Incubating".** Its semantics specification is only now being proposed; expect generator and tooling instability.

### Corrections that would change a design decision

1. **C#/.NET is closer to viable for Rune than the brief says (affects the Section 4.3 flip table and the .NET "DRR / Rune compatibility" score of 2).** A private C# implementation with functions and Java-reference conformance tests exists and a FINOS contribution is proposed and marked "Approved" (common-domain-model #5169, 2026-09-14). It still shows no `ReportFunction`/DRR report support, so DRR execution remains JVM-only today. The JVM recommendation survives, but the flip trigger should be tracked against #5169 and #1410, not only #1409 and #1411.
2. **DRR licence and access are now known (Section 5 and design implication 3 should be updated).** Access is requested from ISDA (CDMDRR@isda.org); artefacts come from the ISDA Maven repo with coordinates `com.regnosys.drr:rosetta-source`. The licence permits use and redistribution only "without modifications and solely as part of a Larger Work" and **requires the licensee to indemnify ISDA** for liability arising from the Larger Work. For a vendor-shipped product, legal must clear the indemnity, the no-modification rule and whether the code artefacts fall under the licence text. This is a procurement risk, not a stack risk, but it gates "run DRR in-process".
3. **Drop SAP `go-ase` from the Go/Sybase options; soften the Rust SQL Server point.** go-ase is archived and unmaintained, so Go has no maintained pure-Go ASE route (ODBC/cgo only), which reinforces the JVM connector argument. tiberius shipped 0.13.0 on 2026-09-25, so "stale" no longer holds.
4. **libxml2 is thinly maintained, not unmaintained.** Five upstream releases landed between 2025-09-15 and 2026-09-04. The argument against libxml2 on the critical path still stands for other reasons (XSD 1.0 only is unverified, C dependency, thin team), but the wording "lost its sole maintainer ... unmaintained" should be dated to September 2025.
5. **GraalVM "Java 29 support planned" is unverified.** Treat native-image as optional (the brief already does). The trigger row "GraalVM Java 29 support lands" rests on an unconfirmed promise.
6. **XSD 1.1 sourcing:** the official Xerces-J XSD 1.1 package exists but the community reports using unofficial builds, and the Frankel citation does not support the libxml2 and .NET XSD 1.0 claims. The XSD version of ESMA and ISO 20022 schemas is still unverified; a one-hour spike opening the ESMA zips would remove the largest unknown in Section 5.

None of the corrections reverses the Java 25 recommendation or the score ordering; items 1 and 2 are the ones to carry into the design specification.
