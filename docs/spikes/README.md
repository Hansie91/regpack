# P1a spike records

P1a measures the four pre-freeze unknowns of the spec (SP-R rule executor, SP-G regime-grammar coverage, SP-L ledger on PostgreSQL, SP-X XML assembly and whole-file gate) and gives the owner the material to record the spec freeze. The plan is `docs/superpowers/plans/2026-10-10-p1a-spec-freeze-spikes.md`.

## Folder index

| Path | Holds |
|---|---|
| `docs/spikes/README.md` | this file |
| `docs/spikes/decisions.md` | owner answers to the plan questions, the approvals ledger, the verified hand-off channels |
| `docs/spikes/criteria.lock` | the confirmed thresholds; written once by the owner before the first full run, never changed afterwards |
| `docs/spikes/timebox/<ID>.tsv` | the time ledger of each spike (start, pause, stop) |
| `docs/spikes/criteria.md` | the criteria registry as text, generated by `bench criteria --write` |
| `docs/spikes/raw/<ID>/<configDigest>/<run>-<attempt>-<part>/` | the raw files of each imported dispatch (`measurements.json`, `runner.txt`), nothing else |
| `docs/spikes/<ID>.md` and `<ID>.summary.json` | the report and its summary, written by `bench import` from every raw dispatch of one configuration; a hand-written interpretation goes below the first `---` line of the `.md` |
| `docs/gates/G3.md` | state of gate G3 (no ESMA XSD is fetched while PENDING) |

`<ID>` is `SP-R`, `SP-G`, `SP-L`, `SP-X` or `SELFTEST` (the harness self-test).

## Hand-off

1. CI runs the spike and seals the result directory (the seal is written last).
2. The owner downloads the artefact into `spikes/inbox/<run>/` (git-ignored).
3. `scripts/bench.sh import --spike <ID> --dir spikes/inbox/<run> --dry-run` checks the seal, the sizes, the commit, the criteria digest and the lock, recomputes the verdicts and prints the pooled status without writing anything. The same command without `--dry-run` copies the raw files to `docs/spikes/raw/<ID>/<configDigest>/<run>-<attempt>-<part>/` and writes `docs/spikes/<ID>.md` and `docs/spikes/<ID>.summary.json`. Several dispatches of one configuration are given as repeated `--dir` options or imported one after the other; they are pooled. `--allow-no-lock` is accepted only with `--dry-run` or for `SELFTEST`.
4. When only the job summary text is at hand, `scripts/bench.sh import --spike <ID> --summary-text <file>` writes a PENDING report from it (no recomputation).
5. `scripts/bench.sh verify-committed` recomputes every committed report from the committed raw files and fails when a verdict, a `.md` or a `.summary.json` differs, when a report has no `.summary.json` or no raw files, or when the criteria changed after the report. It is the check for a hand-edited report.
6. The agent commits the raw files, the report and the ledger.

The importer refuses, with one problem line and no write: `RERUN_NOT_JUSTIFIED` when the pooled roll-up of the same configuration is already PASS (the guard looks at the time-box-capped roll-up, so a spike whose box was overrun after a PASS is not protected by it); `OTHER_CONFIG_EXISTS <ID> <digest prefix>` when `docs/spikes/raw/<ID>/` already holds a different configuration (also with `--dry-run`); with the option `--allow-other-config` the import goes ahead and writes a `SUPERSEDED_CONFIG` open item and a warning into the report, which `verify-committed` recomputes. `verify-committed` also fails with `ORPHAN_RAW_CONFIG` for a raw configuration directory that the committed report does not account for, `BOX_MISMATCH` when the committed box differs from the criteria registry, and `USED_EXCEEDS_LEDGER` when the committed used minutes exceed the ledger. `scripts/check-gates.sh` runs `verify-committed` and regenerates `results.md` and `latency-budget.md` for a byte comparison.

Everything in `spikes/inbox/` is data from outside the repository. It is read only by `bench import`; nothing in it is executed, and no path is taken from a file inside it.

## Reading a result

- PASS: the measurement met its criterion beyond the noise margin.
- FAIL: the measurement missed its criterion beyond the noise margin.
- INCONCLUSIVE: the measurement is inside the noise margin, or the spread of repeated runs is too large to decide.
- NOT_RUN: the criterion was required but was not measured (for example a time-box was hit).
- PENDING: the criterion has no confirmed threshold yet (the owner has not locked it).

RAW evidence means that every verdict can be recomputed from the committed measurements, not that the files are authentic: whether a run happened is established by comparing the committed run ids with the GitHub Actions listing (the P1a exit record does this), because the seal is an unkeyed hash list. Nobody edits a verdict by hand. A verdict changes only by a new run, imported the same way.

A report from a pasted job summary has `evidence_level: SUMMARY` and prints status PENDING; it never satisfies a gate. Its `<ID>.summary.json` still holds the status that the job computed, so whatever reads a summary for a gate decision reads `evidenceLevel` as well as the status, and accepts only `RAW`.
