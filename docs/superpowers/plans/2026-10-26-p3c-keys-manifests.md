## Departures from stated before-conditions (AP-1 approves each)

(1) Spec freeze not recorded. (2) Spec 11.6 and RSV-1 (spec section 18) say "one entity KEK until then"; this plan builds one KEK per UTC year of the write instant (A3, OI-3) and so departs from that text, because with one KEK destruction would be all or nothing. The unit of destruction is that KEK cohort, not an object (no key tables, D1); if OI-3 is answered "one KEK", this departure lapses and `KekSelector.single` is the production selector. An object stays readable until the LAST retention in its cohort ends: one EMIR/SFTR/CFTC object with an open anchor, one SEAL-1 extension or one legal hold keeps the whole year readable, and an enrichment snapshot is not shredded at the end of the retention of the report that cites it unless that ends the cohort. Options for P4/P9b, none built: a deletable key table (reverses D1); cohorts per year and retention class or anchor year (new writes only); a new KEK per year adds a yearly escrow step. Not possible for objects already stored: re-wrapping into a later cohort, because the stores are write-once without delete and the KEK id and the wrapped key are part of the AAD of the data, so a different wrap is a different object; rotating key material is a KMS act under the same KEK id (P9b). (3) Spec 11.6, keys destroyed at expiry: the key-destruction job is deferred to P4 under item 3 of the spec 17.4 cut order. That cut order is conditional on a calibration that shows overrun and needs the owner's recorded confirmation. No record says the calibration triggers it (`docs/exit/P3a.md` records about 835 agent minutes against about 520 estimated, and the owner answered "Continue" to the P3b re-estimate, chat 2026-10-18); OI-10 asks for the confirmation. If the owner declines, the destruction job (an administrative KMS act plus the expiry list) moves into P3c2 and exit criterion (2) gains a clause. (4) The P3a schema document classes the data-subject index "yes, encrypted"; A9 stores keyed hashes only (document decision D4). (5) The P3 row names the slice as one; it is delivered as P3c1 and P3c2 (OI-2), so checkpoint 1 (S1), which the P3a split table gives to P3c, is complete only when P3c2 exits. (6) For P3c2, named now: the P3 row says the signer is "tested against the in-memory KMS adapter from P0 and then a real KMS key", and spec 5.2 runs it as a separate process under its own workload identity. Neither the real key nor the separate process is built (A16); the identity separation is shown against the in-memory KMS only. (7) Spec 11.6 and 5.5 list six key classes. The data-subject index adds a seventh, `INDEX_HMAC` (A4, A9, D-K5): an HMAC-SHA-256 key (lifecycle: Scope check, P9b). Alternative: reuse a `TRN_HMAC` key with the domain prefix `regpack/subject/v1`, which avoids the seventh class but couples two lifecycles. Default: separate key; AP-1 decides. (8) Spec 11.6 and the P3a hand-off "P3c removes the plain report body": the plain body is refused only by `Config.production`; the default configuration still stores one (A6). Spec 11.1 and 11.6, "natural-person columns ... per-entity data keys": the whole `report_version.body` is one envelope and the data key is per UTC day and KEK (A3, D-K2), a reading of one entity.

## Decisions made by this plan (reversible, with reasons)

- **D-K1 Envelope v1** (big-endian). `RPEN` (4) | version `01` | kind `01` OBJECT or `02` BODY | kek length (1 to 100) | kek id (`[A-Za-z0-9._-]`) | wrapped length (2 bytes, 1 to 1,024) | wrapped data key | nonce (12) | ciphertext and 16-byte tag. AAD = every byte before the nonce, then a 4-byte length and the context, so a swapped KEK id or wrapped key fails. `isEnvelope` is true exactly when `header` would succeed (magic, version 1, kind 1 or 2, KEK id length and alphabet, wrapped length 1 to 1,024, total length at least header + 12 + 16), without a key.
- **D-K2 Keys.** `ObjectCipher.seal(key, plaintext)`: draw a 32-byte data key, then a 12-byte nonce, from `Entropy` (order pinned); wrap under the KEK of `KekSelector.kekAt(clock.now())` with the wrap AAD `regpack/dek/v1|OBJECT|<kek id>|<key path>`; context = the key path (UTF-8), so an envelope moved to another key fails; zero the data key array after use (best effort: not the copies inside `SecretKeySpec`, the cipher or the heap; no record relies on it). `BodyCipher`: one data key per UTC day and KEK (wrapped once, embedded in every body of the day; each seal reads the clock once and the day, the KEK and the cache test use that instant), rotated also after `MAX_SEALS_PER_KEY = 2^30` seals (NIST limit 2^32 for random 96-bit nonces under one key [R: SP 800-38D 8.3]); wrap AAD `regpack/dek/v1|BODY|<kek id>|body`; context `regpack/body/v1|<regime>|<event identity>|<leg>|<logical hash hex>`. `open` always calls `Kms.unwrap` (no read cache) and zeroes the unwrapped key in a `finally`, on the exception paths too; the sealing instance holds the current generation key in memory until its UTC day or seal limit ends and zeroes it then (a stated residency limit: a process that sealed today can still seal with today's key if the KEK is destroyed mid-day). **KMS failures fail closed:** both ciphers map any RuntimeException of `kekAt` or `wrap` to `KeyUnavailableException` (package `dev.regpack.ports.crypto`, fixed message "the key service could not serve this request", no cause, no suppressed; on wrap an `IllegalArgumentException` can only mean an unknown KEK, e.g. `kek-2027` not yet created). On `open`: `KmsKeyDestroyedException` becomes `DataShreddedException`; an `IllegalArgumentException` of unwrap or a failed tag becomes `Envelope.AuthenticationException` (no cause); `KmsAccessDeniedException` and any other RuntimeException of unwrap become `KeyUnavailableException`. Messages and `toString` never hold a key, a key id or a path.
- **D-K3 `EncryptingEvidenceStore`** (decorator, package `dev.regpack.evidence.crypto`). Above the store port, below `DurableSeal`: the manifest rows and the intent hash stay hashes of the plaintext handed in, so P3b1's checks are unchanged; the stored bytes are the envelope. `put` of an encrypted key: read the key; if present, open it: equal plaintext (compared by SHA-256 with `MessageDigest.isEqual`) puts the stored envelope bytes again (so a second P-SEALED copy is healed, as `JournalWriter` relies on) and gives `ALREADY_PRESENT_IDENTICAL`, other plaintext is `EvidenceIntegrityException`; if absent, seal and put, and if that put loses a race (an `EvidenceIntegrityException` that is not a corruption alarm), read again and decide the same way. `get` opens and returns the plaintext with its SHA-256; non-envelope bytes under an encrypted key are an `EvidenceCorruptionException` (no downgrade). `list`, retention, hold, grade and durability pass through. A destroyed KEK is `DataShreddedException` (a `RuntimeException`, neither an outage nor a corruption alarm); `KeyUnavailableException` is mapped to `EvidenceUnavailableException` (fixed message, no cause) on `put` and `get`, and `DataShreddedException` is never mapped to an outage. `EvidenceVerifier` counts a shredded object and does not judge its hash (T6).
- **D-K4 Retention.** `RetentionEngine(rows, evidence, regime)` records a claim and then extends the store object to the maximum retain-until over all rows of the artifact, taking `EvidenceRetentionException` as satisfied; `DurableSeal` calls the optional `RetentionRegistrar` right after the sealed put, passing the `Retention` it used for that put, and before the intent put, so a shared sealed object (identical bytes) is extended by each later seal (SEAL-1); a registrar failure before the SENDING commit fails the seal closed; a row written for a seal that never commits only over-retains; the regime is the engine's (one engine per regime; P8 designs how a sender supplies it). `RetentionVerifier` compares each retention row with the store. It is the P3c1 building block of the retention check that spec 11.6 places in `verify` on P-SEALED; `verify` does not call it yet. It checks only objects that have a row (in P3c1 only sealed objects get one, from the seal hook; journal, landing and enrichment objects when their writers register them: P3d, P7a, P5); the restriction to manifest-covered objects and the call from `verify` are P3c2.
- **D-K5 Data-subject index.** Hash input `regpack/subject/v1` NUL kind NUL NFC(value) (UTF-8); `SubjectHasher` calls `Kms.hmac` with an `INDEX_HMAC` key; the value never reaches a message or a row; any `RuntimeException` of `Kms.hmac` becomes `KeyUnavailableException` (fixed message, no cause). The `SubjectHasher` constructor refuses a key whose purpose is not INDEX_HMAC (`SubjectHasherTest#aTrnHmacKeyIsRefused`). The caller canonicalises the identifier (trim, upper-case with `Locale.ROOT`, strip separators) before `hash`; the Javadoc says so.
