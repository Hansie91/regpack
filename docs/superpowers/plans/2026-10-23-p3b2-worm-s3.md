## Decisions made by this plan (reversible, with reasons)

- **D-W1 Layout.** `S3` = `regpack-evidence-s3/src/main/java/dev/regpack/evidence/s3` (`WormEvidenceStore`, `WormConfig`; the client classes in `S3/client`, named in T2 and T3). Tests below `regpack-evidence-s3/src/test/java/dev/regpack/evidence/s3` (`S3T`).
- **D-W2 Object model [R: P3, P7, P9].** Path-style `/{bucket}/{key}`; every byte of the key outside `A-Za-z0-9-._~` and `/` is written `%XX` once. Content-Type is always `application/octet-stream`. User metadata (lower-case names; text values base64url without padding unless noted): `regpack-sha256` (hex), `regpack-written-at` and `regpack-retain-until` (ISO instants, plain; the retain-until is the exact value at put), `regpack-class`, `regpack-media-type`; at most 2 KB together [R]. **Invariant V: the object under a key is its oldest data version.** `get`, a put's existence test and the retention methods use the version list of the exact key (`?versions&prefix=<key>`, entries of other keys ignored) and the `versionId` of that version. The version list of the exact key is read to its end: the adapter follows `truncated` with the next key and version-id markers, ignores entries of other keys, and takes the last data entry of the exact key's run in list order (never Last-Modified) as the oldest (P7 records that the service lists newest first; if not, stop). A page that repeats the previous markers and adds no entry, `IsTruncated` without both next markers, or more than 10,000 pages, is `EvidenceUnavailableException`; the same guard applies to the list markers of D-W4.
- **D-W3 Put [R: P7, P10, P13].** Inside a stripe lock (64 locks by key hash; the stripe locks are fields of the store object: a second store object on the same bucket models a second process, which `twoStoresRacing...` relies on, and production wiring uses one store object per bucket per JVM): (1) validate (pure: retain-until range and precision, media type and class length), list versions; (2) the key is hidden by a delete marker: `EvidenceCorruptionException`; (3) the oldest data version exists: read it with GET (not HEAD) and hash its bytes against the recorded `regpack-sha256` exactly as `get` does (a mismatch or missing metadata is `EvidenceCorruptionException`, no PUT); only then compare the recorded hash with the request's: equal gives `ALREADY_PRESENT_IDENTICAL` and **no PUT**, different gives `EvidenceIntegrityException`; (4) absent: refuse a retain-until not after the data clock, then PUT with `x-amz-content-sha256` = the hex SHA-256 of the body and `Content-MD5` = the base64 MD5 of the body [R: P5, P10], the lock headers and the metadata (the response must carry a version id, else `EvidenceUnavailableException`), then list versions again: if the own version id is not in the second listing the answer is `EvidenceUnavailableException`, never `CREATED`; the own version oldest gives `CREATED`, another older one decides as in (3) and the own version stays as a harmless extra version. If probe P10 shows that the service does not verify the payload hash, step (4) reads the own version back and hashes it (decided at T7 step 1, recorded as a deviation and in the request counts). **The race that remains:** two processes (not two threads of one store) putting different bytes under one key at once can both find their own version oldest, because the rank of a version is the server's and a slow upload may rank before a fast one that finished first [R: P13]; both are told `CREATED`. `get` returns the older-ranked version (invariant V), and if the server ranks by request start the answer of `get` can change once while the slower upload is in flight. The ledger keeps the hash of whichever writer reaches `recordObjects` first and fails the other seal closed, so when the writer whose bytes `get` does not return is first, its seal succeeds and gates an effect on bytes the port cannot return (they stay as a non-oldest locked version that the port does not return; reading it needs the raw S3 API with its version id [R]); `verify` reports the key afterwards (`HASH_MISMATCH`, `manifest-hash`). This is a stated residual hole of I10 for that attempt, not closed here: conditional writes (spec 5.2, 11.5 B.1; deferred) would close it, and no other closure was examined; `docs/exit/P3b2.md` says so in these words. `WormStoreVersionsTest` states and counts the race.
- **D-W4 get, list, delete markers [R: P7, P8].** `get`: version list, GET of the oldest data version, bytes hashed against `regpack-sha256` (`EvidenceCorruptionException` on a difference, on missing metadata, and when the newest entry of the key is a delete marker). `list` uses ListObjectVersions (prefix, key-marker = the `after` key with no version-id marker, then the returned markers), returns every key that has at least one data version, whether its newest entry is a data version or a delete marker, in key order, skips keys that hold only delete markers, and follows the markers until `limit` distinct keys are collected or the listing ends (max-keys counts versions and markers, so the loop may need several requests); it never answers short while keys remain (D-W10). A key hidden by a delete marker is listed; the caller's next `get` raises `EvidenceCorruptionException`. `list` with limit 0 returns an empty list without a request; a limit below 0 is `IllegalArgumentException` (as in the other adapters); max-keys is min(remaining, 1000). A listed key that is not a valid `EvidenceKey` is skipped, never thrown; a valid-looking foreign key without regpack metadata is listed and its `get` is an `EvidenceCorruptionException`. A hidden object that has a manifest row is `HASH_MISMATCH` `store-integrity` for `verify` and is still a locked version in the bucket; `MISSING` is a manifest row for which no object exists. No main code of the module issues a DELETE request or holds the bypass header (`NoBypassTest`, T2).
- **D-W5 Retention [R: P2, P4, P5, P12].** `PutObject` headers `x-amz-object-lock-mode` and `-retain-until-date` (whole seconds, `Z`; mode from the configuration). The date is the retain-until rounded up to whole seconds, at most `maxLockDate` (default `9999-12-31T23:59:59Z`; P12 may lower it): never shorter than the record except in the last second of year 9999. `extendRetention(key, N)`: validate N; take the key's stripe lock (`setLegalHold` also takes it); outage and missing key as for put; E = the exact value (tag if present, else metadata), L = the lock date of the oldest data version, T(N) = min(N rounded up to whole seconds, `maxLockDate`). N earlier than E: `EvidenceRetentionException`. N equal to E: nothing. Otherwise `PutObjectRetention(T(N))` ONLY if T(N) is later than L (never a shortening; the lock protects, so it comes first), then the tag `regpack-retain-until`. Reported retain-until: the exact value when its rounded form equals the lock date; the lock date when the lock is longer (an extension that crashed before its tag); when the lock date equals `maxLockDate` and the rounded-up exact value is later than `maxLockDate`, the exact value is reported; any other lock shorter than the rounded-up exact value is an `EvidenceCorruptionException` (a governance lock was shortened by a principal with the bypass permission). P2 records the exact text format of the retain-until header and the parser accepts what P2 recorded.
- **D-W6 Legal hold [R: P6].** `PutObjectLegalHold` ON or OFF on the oldest data version, read from the response headers of GET and HEAD; an absent `x-amz-object-lock-legal-hold` header is OFF (P6). A never-put key: `IllegalArgumentException("no such evidence key: <path>")` after the outage check (M28, M33).
- **D-W7 Failures.** Every outcome that is not the documented success of the call is `EvidenceUnavailableException` (message: operation, status and Code only): a transport failure, a timeout, an interrupt (flag restored), any status the call does not expect (every 3xx, never followed; every 4xx and 5xx with any Code; an unexpected 2xx or 304), an unparsable response and a missing version id. The only absence is a version list of the exact key, read to its end, that holds no data version; a 404 for a version id the list just showed is `EvidenceCorruptionException`; a 404 for a bucket is never absent and never an empty listing. The `IOException` of a transport is not chained; the `EvidenceUnavailableException` message names the operation and the exception's simple class name only. No retries in the adapter.
- **D-W8 Two clocks.** `WormEvidenceStore.open(config, dataClock, signingClock[, transport])`: the data clock gives `regpack-written-at` and the retain-until check; the signing clock gives `X-Amz-Date` and must be real time (a server refuses a request more than 15 minutes off [R]); the suites run with a `ManualClock` as data clock.
- **D-W9 Durability and grade [R: P1, P15].** `durability()` reads the bucket versioning and object-lock configuration on every call (no cache: an outage throws, as the port says), throws `EvidenceUnavailableException` unless both are on, and returns the `Durability` that `WormConfig` declares (synchronous, at least one domain). `grade()` makes the same first bucket read as `durability()` (the versioning request), throws `EvidenceUnavailableException` when it fails, does not judge the answer, and then returns the grade of the configuration: `("P-WORM", "governance")` or `"compliance"`, plus `" (unverified)"` for `UNVERIFIED_NON_AWS`. `WormConfig` refuses `COMPLIANCE` with `UNVERIFIED_NON_AWS` (spec 16 Entry) and a bucket name that breaks the S3 rules. `UNVERIFIED_NON_AWS` requires a declared `Durability` with exactly one independent failure domain (`IllegalArgumentException` otherwise); a larger count needs `SP_O_VERIFIED`. A domain counts only if the copy exists when the PUT is acknowledged; asynchronous replication counts zero. The endpoint is `scheme://host[:port]` only (no userinfo, path, query or fragment); `http` is accepted only for a literal IPv4 address in 127.0.0.0/8, `[::1]`, or exactly `localhost`, read from `URI.getHost()` without any DNS lookup; everything else needs `https`; `AWS_S3` requires the host `s3.amazonaws.com`, `s3.<region>.amazonaws.com` or the same under `amazonaws.com.cn` [R]. The API shows no replication: for a non-AWS store the declaration is the operator's, attested in the G8 record (spec 5.4); the CI service declares one domain, so the production gate (two) stays closed for it; a test that declares three does so only with `Verification.SP_O_VERIFIED` (T9).
- **D-W10 Paging.** As Port changes 1 and 2 and T5, so that the fail-open path of p3b-notes section 3 item 32 does not rest on one promise.
- **D-W11 The fake.** `FakeS3Server` (test code, JDK `HttpServer` on loopback, one per test) recomputes the SigV4 signature of every request from the raw request (403 `SignatureDoesNotMatch` otherwise) and implements the behaviours of `docs/evidence/p3b2-probe.md`, each marked `// probe: P<n>`, with fault switches (T7). `S3BehaviourContract` states those behaviours once and is bound to the fake and the service, so a fake that drifts fails at CP-2.
- **D-W12 Labels.** `REALWORM` lines (tests that run only in `evidence-worm`, against the real service; the PostgreSQL ones also against PostgreSQL) count as non-interim evidence by the rules of T6 step 1. A due I1 or I10 row still needs the `REALSTORE` line of `ledger-pg` (spec 14.1).
- **D-W13 Test data.** The `ManualClock` of the bindings starts at `2040-03-01T00:00:00Z`, so retain-until dates (2045) stay in the server's future; one bucket per test, `rp-` plus 12 hex digits of a random UUID (test code only); buckets are never emptied (the tests that send the bypass header (P5, `S3BehaviourContract`, the two verify bindings) only shorten a lock and none is expected to delete a version; the container is discarded with the job [R]).
- **D-W14 Tags.** ITs carry `@Tag("worm")`, the probe `@Tag("probe")`; `excludedGroups` is `mutant,worm,probe` in the module and gains `worm` in `regpack-postgres`.

**Sections 4 and 5.4 (I1, I10, the P-WORM profile)**

> | I1 | **Durable before effect.** No first byte to a destination, no acknowledgement to a source and no move or delete of a source file happens until the record that justifies it is durable (ledger committed with synchronous-standby acknowledgement, and bytes or journal objects acknowledged by the evidence store as durable, §5.4). The system fails closed. |
> | I10 | **The evidence tier is never rebuilt; the database is restored from backup and made current from the evidence tier.** Everything that gated an external effect is reconstructable from the evidence tier.
> an S3-compatible store (spike SP-O, §16) or Azure immutable blob (its own spike) counts as P-WORM only after its lock semantics are verified (**U**)
> governance mode (non-production only) can be bypassed by principals holding the bypass permission
> Compliance-mode retention is irreversible, so production rollout is staged
> Production wherever available (default); governance mode is not accepted for production
> retention periods are recorded as fixed and extend-only, with legal hold modelled separately
> **Durability.** An evidence write is acknowledged only when it survives the loss of one disk, volume or host. P-WORM on AWS S3 relies on the service's multi-AZ replication (**V** for AWS).
> Any other S3-compatible store counts as P-WORM only if it is configured to survive the loss of one disk, volume or host with synchronous acknowledgement (erasure coding or replication across failure domains)
> **Claims that hold only for P-WORM:** immutability, store-enforced retention, and RPO 0 for sealed bytes and journal objects on AWS S3, and on other stores only where the durability configuration above is verified.

**Sections 11, 14, 16, 17 (journal, fail-closed, tests, the P3 row, SP-O, G8)**

> Shipping is idempotent by key: the store treats a put of an existing key with the same `payload_sha256` as success and a put with a different hash as an integrity alarm (no reliance on S3 conditional writes, which are deferred, §5.2)
> No first byte leaves while the evidence tier cannot acknowledge the sealed bytes and journal object.
> run unchanged against the in-memory adapters and against real PostgreSQL 18 and both evidence profiles (P-SEALED and an S3-compatible store with object lock)
> A traceability row (§14.4) for I1, I2, I9 or I10 that cites only an in-memory test does not count.
> For I1, I2, I9 and I10 the evidence includes a real-store run (§14.1).
> then P-WORM in governance mode against an S3-compatible object-lock store (compliance mode is the same adapter, enabled per retention class in production, §5.4)
