**Architecture summary.**

- **One new JDK-only module `regpack-evidence`** (package `dev.regpack.evidence`): P-SEALED, `DurableSeal`, `SendGate`, `EpochMarker`, `EvidenceVerifier`. It depends on `regpack-model` and `regpack-ports` only; `regpack-app` does not depend on it (nothing is wired).
- **Ports change only additively** (section "Port and model changes"). The journal format, `JournalWriter` and the `Sealing` interface live in `regpack-ports`, so that the shared suites of `regpack-testkit` can bind them: testkit cannot depend on a module whose tests depend on testkit.
- **Durable before effect, in this order** (spec 11.2): validation of the request, gate, attempt id, PUT of the sealed bytes and of the `DeliveryIntent` object (each acknowledged, for P-SEALED fsynced on two volumes), one PostgreSQL unit (SENDING under the lease token, attempt row, `object_manifest` rows), then, in the transport's commit gate, the lease and epoch-marker re-check and the fenced `commit_issued` marker. Constraints stay in the database (I2); no Java pre-check of what the schema enforces.

**Tech stack.** As P0 to P3a (Java 25, Maven 3.9.16 wrapper, JUnit 6.1.3, AssertJ 3.27.7, google-java-format 1.35.0, `-Xlint:all -Werror`, hostile test JVM `tr_TR` and `Pacific/Kiritimati`, SHA-pinned actions, image `postgres:18.6-trixie@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336`). New: nothing third-party. The new job runs `docker pull|run|exec|stop|logs|rm` of that same image, with two `sudo install` lines in its script, on a GitHub-hosted runner (AP-6, as the P1a spike did under A-1).

**P3b1 exit criterion.** (1) The journal-format contract test passes, including a `RecoveryDecision` for an attempt that already has an intent. (2) The `EvidenceStore` suite passes unchanged on the in-memory adapter and P-SEALED, in the `build` jobs on Linux and Windows Server and on the development machine; it covers the put of an existing key (existing P0 methods plus the new concurrent one) and the durability-configuration check of §5.4 as far as a store can show it: `durability()` consistent with the profile, P-SEALED reports two domains only when the volume probe separates them (`SealedEvidenceStoreTest`), the production send gate refuses fewer than two (`SendGateTest`); the operator configuration of two independent volumes or hosts is attested in the G8 record, and for S3 in P3b2. (3) I1, first-byte limb (seal-and-send, spec 11.2 steps 2 to 4): the crash-point scenarios pass on in-memory ports, on an in-memory ledger with P-SEALED, and on real PostgreSQL with P-SEALED; on a primary with a quorum synchronous standby a SENDING commit is visible on the standby when the call returns, a commit whose standby wait is cancelled is not reported as durable, and a missing standby closes the gate. The source-acknowledgement and source-file limbs are covered by the existing `ToyCrashIT`/`PackToyCrashIT#acknowledgementFollowsIngestCommit` on in-memory ports and are re-proven on the real stores in P7a. (4) Storage half of I10: from the evidence tier alone the identity of every attempt that gated an effect is reconstructable, and `verify` finds each seeded fault with its own class. (5) The owner-approved V002 document and `docs/exit/P3b.md`. The P3 row is complete only when P3b2, P3c and P3d have also exited.

## Decisions made by this plan (reversible, with reasons)

- **D-E1 Key space** (renderings in T2): journal class a and b keys under `journal/<scope>/e<epoch:012d>/`, `sealed/<hex2>/<hex64>` (content-addressed: the same bytes are one object), `control/epoch/e<epoch:012d>` (restore-epoch marker). Zero padding (12 digits for the epoch and the ordinal) makes text order numeric; a shard keeps a directory under 10,000 entries.
- **D-E2 M28, M33:** `extendRetention` and `setLegalHold` of a never-put key throw `IllegalArgumentException` in every adapter (today's in-memory behaviour). There is no delete, so a listed key cannot vanish; a lost object is `verify`'s MISSING.
- **D-E3 Journal bytes:** canonical JSON `{"envelope", "payload"}`; `clock_instant` is the ledger event time, so a re-ship is byte-identical; the same `payload_sha256` under a stored key is success, another an integrity alarm; payload version 1 is strict.
- **D-E4 Seal order and failures:** validation of the request, gate, attempt id, PUT sealed, PUT intent, `beginSending` with the manifest rows. Outage: `EVIDENCE_UNAVAILABLE`, ledger untouched. Stale lease after the PUTs: two orphans, by design. Integrity alarm or manifest conflict: exception (fail closed).
- **D-E5 P-SEALED** (T5 to T7): two volume roots with marker files; `d-`/`o-`/`m-` names; `RPSEAL01` files; publish = temp, `force`, `createLink`, directory sync where possible; acknowledged after A then B; a volume without its marker is DEGRADED until `repair()`.
- **D-E6 V002** reverses the P3a classification of `object_manifest` as "partitioned by `written_on`": a daily-partitioned key cannot enforce one write-time hash per object across days (the `decision_seq` problem).
- **D-E7 Class a ordinals** are supplied by the caller (the counter belongs to the subject's row in P3d and P4).
- **D-E8 Verify:** a clean tier has no finding; an ORPHAN is not an error of the writer (a crash orphan).
- **D-E9 CI shape:** `ledger-pg` is not edited; one new job runs the "up" tests, stops the standby, runs the "down" tests, and gates on `REALSTANDBY` lines.
- **D-E10 Teeth for `DurableSeal`** are test subclasses overriding one template method each, not flag switches in the production class.
- **D-E11 The gate is a library check:** `SendGate` takes `LedgerDurability` and `EvidenceStore.durability()`; production is `(true, true, 2)`; `Requirement.none()` is named for tests.
- **D-E12 Retention at put:** `RetentionPolicy` is passed in; no production default (null fails at construction).

**Section 4 (I1, I10)**

> | I1 | **Durable before effect.** No first byte to a destination, no acknowledgement to a source and no move or delete of a source file happens until the record that justifies it is durable (ledger committed with synchronous-standby acknowledgement, and bytes or journal objects acknowledged by the evidence store as durable, §5.4). The system fails closed. |
> | I10 | **The evidence tier is never rebuilt; the database is restored from backup and made current from the evidence tier.** Everything that gated an external effect is reconstructable from the evidence tier.

**Section 5.4 (evidence store profiles)**

> Only P-WORM is called immutable or tamper-resistant; P-SEALED is tamper-evident.
> Append-only files on ordinary storage; each object is hash-sealed.
> An object found in the listing with no ledger row (a crash orphan, §7.2) is recorded in the manifest as `ledger_ref: NONE` with its hash and first-seen time and is not refused;
> It does **not** stop someone with storage access from deleting or rewriting files.
> retention periods are recorded as fixed and extend-only, with legal hold modelled separately
> **Durability.** An evidence write is acknowledged only when it survives the loss of one disk, volume or host.
> P-SEALED MUST write synchronously to two independent volumes or hosts (or to synchronously replicated storage) and acknowledge after both are fsynced.

**Section 11 (seal-and-send, journal objects, fail-closed, recovery start)**

> 2. PUT the sealed bytes and a `DeliveryIntent` journal object to the evidence tier.
> 3. One synchronous PostgreSQL transaction: delivery to SENDING (carrying `WHERE lease_token = :t`), attempt intent row, manifest entry.
> Before the first byte the sender re-checks the lease fencing token and reads the current restore-epoch marker from the evidence tier, and refuses to send if the marker differs from its own epoch (an unreadable marker fails closed).
> Envelope: `{endpoint, restore_epoch, type, schema_version, clock_instant, payload_sha256}` plus `seq` (class b) or `subject_id` and `ordinal` (class a).
> Class (a), effect-gating: `DeliveryIntent`; any `OperatorAction` or `RecoveryDecision` that authorises an external effect; and, because re-derivation of the unsent tail (§11.5 B.3) needs them, `BatchAdmitted` and the pack-activation, rollback and expiry `OperatorAction`s.
> A class (a) object is PUT before the PostgreSQL commit that depends on it, keyed by (`scope`, `restore_epoch`, `type`, `subject_id`, `ordinal`)
> Class (b), after-the-fact (all other types): written with their `delivery_event` row in the same transaction and shipped asynchronously, keyed by (endpoint, `restore_epoch`, `seq`).
> the shipped watermark is the highest acknowledged `seq`.
> Shipping is idempotent by key: the store treats a put of an existing key with the same `payload_sha256` as success and a put with a different hash as an integrity alarm
> The no-duplicate and no-lost-send guarantee depends only on class (a); class (b) narrows the in-doubt set.
> P3 fixes the schemas and adds a journal-format contract test that includes a `RecoveryDecision` for an attempt that already has an intent.
> No first byte leaves while the evidence tier cannot acknowledge the sealed bytes and journal object.
> re-ship any journal object above the shipped watermark (idempotent put, §11.2)
> A gap that remains after the shipper has caught up fails the endpoint closed until an operator records it in the restart report.

## Conventions (read before Task 1)

The P0 Conventions 1 to 11, P1a 1 to 3 and 7 to 9, P2a 1 to 10 and P3a 1 to 12 hold (shorthand `MVN`, `T <module> <selector>`, `IT <module> <selector>`, `FMT`, `COMMIT "<message>"`; Bash and PowerShell forms; P3a 9 to 12: stop conditions, checkpoints do not block, the unit prologue `Unit.begin`, SQL text and messages). Deltas:

1. **Branch and commits.** `p3b/evidence-stores`; one commit per task (T1 also commits this plan alone first). Never skip hooks. The owner merges.
2. **What runs where.** Most of this slice runs locally: `T regpack-evidence '*Test'`, `T regpack-ports '*Test'`, `T regpack-inmemory '*Test'`, `MVN verify`. The development machine is Windows 11 (NTFS): P-SEALED runs on Windows locally and on Linux and Windows Server in CI. A step that needs a server is `NOT RUN LOCALLY` and names its checkpoint.
3. **Real-store tests.** As P3a Convention 4. The ITs of the standby job carry `@Tag("durability")`, are excluded from `verify` by the module property and run only in that job (`-Dgroups=durability -DexcludedGroups=none -Dit.test=<class>`, the form of the capacity job).
4. **Files in tests.** `@TempDir` only; absolute paths; no `System.getenv` and no `user.dir` in `regpack-evidence`; no `Thread.sleep` and no `System.nanoTime` in main code (the determinism scan forbids both): waits are latches, retries are the caller's.
5. **Contract first (EF23).** A behaviour two adapters must share is first a method of a shared suite in `regpack-testkit`, red on a mutant or the first new adapter, then green on every adapter that exists. New suites get mutants in the P3a style (`mutants/*ContractTest`, `@Tag("mutant")`, named in `ContractSuiteTeethTest`).
6. **Stop conditions:** P3a Convention 9, plus any third-party dependency in `regpack-evidence`; a docker verb outside the allow-list of AP-6 (any `docker volume` included) or a `sudo` other than its two install lines; weakening a contract method to make an adapter pass; an edit of `V001__core.sql`, the approved `schema-design.md`, the specification or `spikes/`; a push without AP-2.
7. **Effort ledger.** The controller appends per task to the untracked `.superpowers/p3b-ledger.md`: implementer and reviewer runs, fix rounds, agent minutes (CI and owner waits excluded), subagent tokens, owner minutes, tests added, CI round trips (requested, done, ended, red runs before green), commit; copied into the exit record (T22).
8. **Messages.** `SealOutcome.detail`, `Finding.detail` and exception messages carry key paths, hashes and fixed reason texts (volume ids, field names, SQLSTATEs) only, never file names, business keys or payload text.

**Semantics (normative; the contract tests are the oracle).**

1. `recordObjects` is all or nothing in one unit. A key that exists with the same `sha256` is left unchanged (the first row wins, with its provenance, attempt and time); with another `sha256` it throws `ManifestConflictException` and nothing of the call is stored. `writtenAt` is the ledger `Clock`. A manifest entry's `sha256` is the hash of the object bytes as stored, not `payload_sha256` (a later caller that records a re-written journal object must obtain the stored hash and size from the store; `JournalWriter` returns neither in P3b1).
2. `beginSending` with `intent.objects()` records them with provenance WRITTEN and the attempt id in the same unit as the state change and the attempt row, after both; a conflict rolls the state change back (the delivery stays QUEUED, no attempt, no rows). A call that returns a status other than `APPLIED` records nothing.
3. `LedgerDurability.durability()`: the in-memory ledger reports `(false, 0, "in-memory ledger")` unless a test sets it; PostgreSQL follows A11.
4. `JournalWriter.write` PUTs with the retention of `RetentionPolicy` for the class name `journal`; `DurableSeal` uses `sealed` for the sealed bytes; `EpochMarker` uses `epoch`.
