# P1a Implementation Plan: Spec-Freeze Spikes (SP-R, SP-G, SP-L, SP-X) and the Measurement Harness

> **P1a implementation plan** for regpack (the four spikes that the spec-freeze definition needs, plus the measurement harness they share), written 2026-10-10 against the approved specification and the signed-off P0.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal.** Replace the placeholders that decide the spec freeze with measured, reproducible, mechanically judged results (SP-R, SP-L, SP-X) and one written, tested paper exercise (SP-G), so that the owner can record the spec freeze (spec 16) on evidence. P1a is measurement and one paper exercise, not product. It builds (1) a small, permanent measurement harness, `regpack-bench`, test-first; (2) one on-demand workflow on GitHub-hosted `ubuntu-24.04` runners; (3) the four spikes as disposable code under `spikes/`; (4) a consolidation: results table, the partial per-stage latency budget of spec 5.6, open items, the spec-freeze template and checklist, and the deferral list. SP-M, SP-S, SP-W and SP-N move to a later plan P1b; SP-E (gated by G3), SP-O, SP-V and SP-D stay deferred with their triggers (section "Deferral list").

**Architecture summary.**

- **Two homes for code.** `regpack-bench` (`dev.regpack.bench`) joins the release reactor: JDK-only, strict P0 rules, never in the distribution; it is permanent because spec 14.5 re-confirms capacity on the release candidate with the same protocol. The spikes live in `spikes/` (aggregator `spikes/pom.xml`, parent the root POM, **not** in the root `<modules>`), the only place with third-party libraries (`cel-java`, the PostgreSQL JDBC driver), each an exact coordinate; the release build, SBOM and distribution never see them (`Gates isolation`, T7).
- **Harness first.** A hand-written SplitMix64 gives byte-identical corpora on Linux and Windows. The protocol is fixed: one fresh JVM per repetition, warm-up until stable, 15 windows, a CPU, memory and disk canary, discards only for harness failure or CPU steal.
- **A noise rule that bounds noise within one VM.** A criterion is judged on the exact one-sided 95% order-statistic bounds of the median of at least 7 forks, widened by `m = max(10%, canary spread)`: PASS needs the lower bound at least `threshold x (1 + m)`, FAIL needs the upper bound below `threshold / (1 + m)`, the rest is INCONCLUSIVE, and `m` above 50% is INCONCLUSIVE both ways. A PASS of a noisy criterion from a single VM is rendered `PASS (single VM)`; the interpretation states that between-VM variance is not covered.
- **Hand-off for a public repository whose job logs need a sign-in.** Each CI job writes one result directory and **seals it last** (`manifest.sha256` is the final write), uploads it as an artefact and writes the job summary. The agent can read run, job and artefact listings, not logs or artefact downloads, so the owner downloads the artefact into the git-ignored `spikes/inbox/` (or pastes the job summary: a `PENDING` report that can never satisfy a gate). `bench import` verifies the manifest, recomputes every verdict, keeps the small raw files and pools **every** dispatch of one configuration.
- **Reuse of P0.** The ports (`Expression`, `RuleProgram`, `MeteredExecutor`, `Tier1Explainer`, the in-memory ledger), `Json`, `Sha256` and the P0 gates.
- **Gate G3.** SP-X measures against a **self-authored synthetic schema** (shape in X1); no ESMA artefact is fetched or committed; `Gates g3` (T7) fails the build if ESMA- or ISO 20022-looking schema content appears.
- **Reference environment** (owner decision): GitHub-hosted `ubuntu-24.04`, standard public runners (4 vCPU, 16 GB RAM, 14 GB SSD, x64), on demand through `workflow_dispatch`; the runner specification is captured in every report. Numbers are conservative and noisy; production sizing is re-confirmed on the release candidate (spec 5.6, 14.5).

## Criteria of the four spikes

Protocol rules (normative, tested): **P-1** one repetition is one fresh JVM, forks run one after another. **P-2** warm-up in windows of 2 s ends after 3 consecutive windows whose relative range is at most 3%, or at 60 s (then the fork is `unstable` and kept; more than 20% unstable forks make the series INCONCLUSIVE). **P-3** 15 windows after warm-up; a fork's statistic is the median of its window rates. A latency criterion's fork statistic is instead the nearest-rank p99 of the samples of that fork, window or block; the report states the sample count per statistic (R-4 5,000; L-2 about 41, so effectively the window maximum; L-9 and L-10 200) and labels any p99 of under 100 samples as a maximum. ## Spike SP-R: expression layer and executor gate (R1 to R4)

**Question** (spec 16, quoted above): do `cel-java` semantics (decimal, date, null, error) suffice, and does the reference interpreter meet the gate (at least 10k records/s/core on a 200-rule pack; p99 `explain` under 1 s; pack hot-swap time measured; the per-record budget and the poison-circuit defaults set)?

**Design and why it answers the question.** Two kinds of evidence. *Do the semantics suffice* is behavioural, so the oracle is neither implementation: 47 vectors authored from the spec text (6.2, I3, 6.6, 7.3, 6.8), each MUST (the spec says it), SHOULD (a sensible reading) or DECIDE (the spec is silent and the layers differ; the owner decides at the freeze). Both candidates implement the P0 `Expression` port: the bought `cel-java` and the in-house CEL-shaped subset over `BigDecimal` (the spec's fallback); a vector that `cel-java` passes only through function syntax is recorded FUNCTIONAL, never hidden. *Does the interpreter meet the gate* is a measurement: a generated 200-rule pack (10 tables of 20 rows, hit policy FIRST) runs through a disposable table interpreter (`RuleProgram` under the P0 `MeteredExecutor`) over a ring of 262,144 distinct records on 4 threads under the T3 protocol, in the **worst-case shape S2** (every row of every table evaluated for every record, so no record mix can flatter the gate). "Per core" is read as **per thread with all four vCPUs busy** (a 4-vCPU runner usually has two physical cores, recorded from `lscpu`) and the one-thread rate and the rate per physical core are reported beside it (`executorGateReadings`, Q3). The budget and poison defaults come from calculators with tests. Hot swap is the time from "signed pack bytes in memory" to "first record evaluated under the new pack" under load, with the two invariants of spec 6.5 step 6.

**Data.** `TradeRecordGen` ring of 262,144 records (seed 1); `RulePackGen` packs of 50, 200, 500 and 5,000 rules in S2 (S1 as stretch); 1,000,000 clean records for the budget study. The 50, 500 and 5,000-rule sweep is informational (PLAN). **Exit criteria:** R-1 to R-7 required; R-3 and R-8 informational. **What FAIL means:** R-1b failing means `cel-java` is not adequate and the spec says "otherwise a minimal in-house subset" (decision INHOUSE; no stack flip). R-2 failing for every layer means the gate failed: spec 5.3 flip (faster executors); the freeze then fixes the executor as "interpreter plus closure-compiled scalar" and P2a's scope grows (an owner decision). R-5 failing is a defect of batch-context pinning and goes to the owner before P2a. **Time-box** 1 day. **Entry gates:** none (G3 and G4 do not touch SP-R). **Approvals:** the cel-java set, A-2. **Stop conditions:** a transitive dependency outside the admitted list; a MUST vector whose expected result you doubt (vectors change only with the owner, before any run).

## Spike SP-X: XML writer, per-record XSD and the whole-file gate (X1 to X3)

**Question** (spec 16, quoted above): XML writer MB/s, per-record wrapper XSD versus sampled, whole-file gate throughput; at the burst, a whole day inside the T+1 margin; the per-stage latency numbers; the per-record XSD policy.

**Design.** The assembly stage costs, per record, a StAX write and a per-record wrapper XSD validation (the early quarantine gate) and, per file, one streaming whole-file XSD validation (the L6 gate); each is measured per thread under the T3 protocol (X-4). The capacity is then measured **integrated** (X-1): four threads, each looping whole file cycles of 10,000 records (about 28 MB; the gate and hash cost per record is linear in file size) through the writer, the per-record validation under the policy, the file write, the SHA-256 seal and the file gate, the rate counted over whole cycles so that no phase falls outside the measurement, because a harmonic combination of component rates ignores allocation, memory bandwidth and the file write. The 100,000-record file stays in X-4. The per-record policy is decided by a cost model that includes the failure path (X-2): with every record validated no file ever fails; with sampling fraction `s`, a defect survives with probability `(1 - s)`, fails the file gate and costs a bisect of about `k log2(n/k)` sub-file validations plus a rebuild. `PolicyModel.capacity = threads / (1/writer + s/perRecordXsd + 1/fileGate + defectRate x (1 - s) x bisectSecondsPerDefect + pFail x (1/writer + 1/fileGate))` with per-thread rates (seconds per record in the rate terms; the gate rate is from the 100,000-record measurement), `pFail = 1 - (1 - defectRate x (1 - s))^100000` the chance that a 100,000-record file fails the gate and is rebuilt once, and `bisectSecondsPerDefect` excluding the rebuild; X-2 uses the **lower bounds** of the component estimates, X-3 the **point estimates** (medians) against the integrated ALL run. **The schema is self-authored (gate G3).** Its shape is a declared assumption (X1) because it cannot be compared with the real ESMA schemas before G3 clears; the report says so, and SP-E (deferred, gated) rechecks it: if any statistic differs by more than a factor of two, SP-X re-runs with a re-shaped schema (RF9).

**Data:** `TradeRecordGen` mapped to the 65-field structure, the other fields from `SplitMix64` streams; defects from a seeded `DefectInjector`. **Exit criteria:** X-1 to X-6. **What FAIL means:** spec 5.6 names XML build and XSD validation as likely bottlenecks.
